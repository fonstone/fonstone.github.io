## 0. 为什么需要编排范式

单 Agent 能完成简单任务，但面对现实世界的复杂需求——多步骤推理、跨系统协作、长时运行流程——单 Agent 的能力边界很快触顶。Agent 天然倾向于走最短路径：跳过规范、忽略边界条件、在长对话中累积上下文垃圾。没有编排约束的 Agent，就像没有红绿灯的十字路口。

编排范式不是一个"更好用"的工程选项，而是**从本质上决定了 Agent 系统的可控性、可观测性和可演进性**。选错范式，后面所有的优化都是在错误的基座上盖楼。

本文拆解五种主流编排范式，帮你根据团队规模、技术栈和任务复杂度做出正确选择。

## 1. 状态机范式

### 1.1 原理

状态机范式将 Agent 工作流建模为**有限状态自动机**——每个步骤是一个状态，状态之间的转换由明确的条件触发。整个流程在编译期就确定了拓扑结构，运行时只能沿着预定义的路径推进。

更先进的实现采用**有向无环图（DAG）**扩展传统状态机：节点代表计算步骤，边代表数据依赖，调度器自动识别可并行的节点并发执行。

<MermaidDiagram chart={`flowchart LR
    subgraph StateMachine["状态机：线性推进"]

        SM_ANALYZE --> SM_DESIGN["DESIGN<br/>方案设计"]
        SM_DESIGN --> SM_IMPL["IMPLEMENT<br/>编码实现"]
        SM_IMPL --> SM_VERIFY["VERIFY<br/>验证测试"]
        SM_VERIFY --> SM_ARCHIVE["ARCHIVE<br/>归档沉淀"]

    subgraph DAG["DAG：并行+依赖"]

        D_INIT --> D_A2["代码画像"]

        D_A2 --> D_DESIGN
        D_DESIGN --> D_I1["前端实现"]

    style DAG fill:#e8f5e9
`} />

核心机制：

| 机制 | 说明 |
|-----|------|
| **状态定义** | 每个节点有明确的输入/输出schema、前置条件和退出条件 |
| **转换守卫** | 状态间转换必须满足条件，否则阻塞或降级 |
| **持久化** | 当前状态和中间产物写入文件系统，支持断点恢复 |
| **可观测** | 每一步的输入/输出/耗时/Token消耗都在日志中可追踪 |

### 1.2 代表项目

**LangGraph**（LangChain 生态）

LangGraph 是状态机范式的标志性项目。核心抽象是 `StateGraph`：节点是函数或 Runnable，边是条件分支。支持循环（用于 Agent 自反思）、子图嵌套、以及人类在环（human-in-the-loop）的断点注入。

```python
from langgraph.graph import StateGraph, END

graph = StateGraph(AgentState)
graph.add_node("analyze", analyze_fn)
graph.add_node("plan", plan_fn)
graph.add_node("execute", execute_fn)
graph.add_node("reflect", reflect_fn)

graph.add_edge("analyze", "plan")
graph.add_conditional_edges("plan", route_fn, {
    "execute": "execute",
    "reflect": "reflect",
})
graph.add_edge("execute", END)
graph.add_edge("reflect", "analyze")  # 自反思循环
```

**Bee Agent Framework**（IBM）

IBM 的 Bee 框架采用类似的图结构定义 Agent 工作流，强调企业级可观测性和可扩展性。

**AI Team**（腾讯）

[前文](/knowledge/ai/harness-engineering-knowledge-base) 分析的 AI Team 16 阶段状态机就是典型应用——文件系统即状态机，每个阶段产物持久化，支持从任意断点恢复。

### 1.3 优缺点

| 维度 | 优势 | 劣势 |
|-----|------|------|
| 可控性 | ✅ 执行路径完全确定，每个步骤可审计 | ❌ 流程变更需要修改状态机定义 |
| 可观测 | ✅ 每步输入/输出/耗时全可追踪 | — |
| 调试 | ✅ 状态明确，断点恢复容易 | ❌ 复杂条件分支多了之后状态爆炸 |
| 并行 | ✅ DAG 变体支持并行节点 | ❌ 传统线性状态机不支持并行 |
| 灵活性 | ❌ 新增步骤需要修改图定义 | — |
| 适用 | ✅ 流程确定、步骤间有强依赖的任务 | ❌ 探索性、开放式任务 |

### 1.4 典型工程推荐

| 场景 | 推荐 | 理由 |
|-----|------|------|
| 多步骤代码生成 | LangGraph + ReAct | 流程确定、需要自反思循环 |
| 企业级工作流 | Bee Agent Framework | 可观测性和可扩展性优先 |
| Harness 知识沉淀 | 16阶段状态机（AI Team） | 知识注入→消费→提取的完整闭环 |
| CI/CD 管道 | Dagger / Temporal + Agent | 确定性优先、断点恢复刚需 |

## 2. 角色驱动范式

### 2.1 原理

角色驱动范式的核心思想：**给 Agent 赋予一个角色（Role/Persona），角色的职责决定了 Agent 的行为边界和知识范围**。不同角色的 Agent 组成一个"团队"（Crew），通过对话或任务传递完成复杂目标。

    PM["📋 产品经理<br/>PM Agent<br/>需求拆解 & 优先级"]
    ARCH["🏗️ 架构师<br/>Architect Agent<br/>技术选型 & 方案设计"]
    DEV["💻 开发者<br/>Developer Agent<br/>编码实现"]
    QA["🔍 测试工程师<br/>QA Agent<br/>测试用例 & 验证"]
    
    PM -->|"需求文档<br/>& 任务清单"| ARCH
    ARCH -->|"架构方案<br/>& 接口定义"| DEV
    DEV -->|"代码产物<br/>& 测试说明"| QA
    QA -->|"Bug 报告<br/>& 验证结果"| DEV
    QA -->|"验收通过"| PM
    
    style PM fill:#e3f2fd
    style ARCH fill:#e8f5e9
    style DEV fill:#fff3e0
    style QA fill:#fce4ec

核心机制：

| 机制 | 说明 |
|-----|------|
| **角色定义** | 每个角色有目标（goal）、背景故事（backstory）、可用工具（tools）和职责边界 |
| **任务委派** | 任务有明确的输入/输出期望和验收标准，从一个角色流向下一个 |
| **协作协议** | 角色间的信息传递方式：广播、点对点、接力传递 |
| **监督者** | 可选的 Manager 角色负责任务调度和冲突仲裁 |

### 2.2 代表项目

**CrewAI**

CrewAI 是角色驱动范式的典型代表。核心抽象是 `Crew` → `Agent` → `Task` 三层结构：

```python
from crewai import Agent, Task, Crew, Process

researcher = Agent(
    role="高级研究分析师",
    goal="发现AI领域前沿技术",
    backstory="你是一位资深技术分析师...",
    tools=[search_tool, scrape_tool],
)

writer = Agent(
    role="技术内容作者",
    goal="将复杂技术概念转化为清晰易懂的文章",
    backstory="你擅长将深奥的技术话题写得引人入胜...",
)

research_task = Task(
    description="分析2026年Agent编排最新趋势",
    agent=researcher,
    expected_output="包含5个关键趋势的详细分析报告",
)

write_task = Task(
    description="基于研究撰写技术深度文章",
    agent=writer,
    expected_output="2000字深度技术文章",
)

crew = Crew(
    agents=[researcher, writer],
    tasks=[research_task, write_task],
    process=Process.sequential,  # 或 hierarchical
)
```

**AutoGen**（微软）

AutoGen 强调"对话驱动"——多个 Agent 围绕一个任务展开多轮对话，通过对话逐步推进目标。支持人类参与对话，适合需要人机协作的场景。

**MetaGPT**

MetaGPT 将软件开发的完整角色体系编码为 Agent 团队：产品经理→架构师→项目经理→工程师→QA工程师。每个角色接收上游角色的产出作为输入，输出标准化的文档。MetaGPT 的特点是**角色间的合约通过标准格式文档传递**，减少了信息丢失。

### 2.3 优缺点

| 维度 | 优势 | 劣势 |
|-----|------|------|
| 可理解性 | ✅ 角色分工直观，团队成员容易理解 | — |
| 职责隔离 | ✅ 每个角色聚焦单一职责 | ❌ 角色划分不当导致职责重叠或空洞 |
| 灵活性 | ✅ 新增角色比新增状态更自然 | ❌ 角色间协议需要精心设计 |
| Token 消耗 | ❌ 每个角色独立上下文，总消耗高 | — |
| 一致性 | ❌ 多轮对话中角色可能偏离设定 | — |
| 调试 | ❌ 对话链路长，追踪"谁说了什么导致什么"困难 | — |

### 2.4 典型工程推荐

| 场景 | 推荐 | 理由 |
|-----|------|------|
| 内容创作管线 | CrewAI (sequential) | 研究→写作→审核的角色分工清晰 |
| 软件开发模拟 | MetaGPT | 完整的软件团队角色体系 |
| 人机协作研究 | AutoGen | 对话驱动、人类可随时介入 |
| 数据分析流程 | CrewAI (hierarchical) | Manager 角色统筹多数据源分析 |

## 3. 事件驱动范式

### 3.1 原理

事件驱动范式将 Agent 工作流建模为一个**事件总线**——Agent 订阅感兴趣的事件类型，当事件发生时触发对应的处理逻辑。Agent 之间不直接调用，而是通过发布/事件解耦。

<MermaidDiagram chart={`flowchart TB
    subgraph EventBus["事件总线 / 消息代理"]
        BUS[("🔄 事件总线<br/>Event Bus")]
    end
    
    subgraph Agents["Agent 集群"]
        A1["🔍 数据采集 Agent<br/>订阅: task.created"]
        A2["🧠 分析 Agent<br/>订阅: data.collected"]
        A3["✍️ 生成 Agent<br/>订阅: analysis.completed"]
        A4["📝 审核 Agent<br/>订阅: content.generated"]
        A5["📢 发布 Agent<br/>订阅: content.approved"]
    end
    
    A1 -->|"publish<br/>data.collected"| BUS
    BUS -->|"dispatch<br/>data.collected"| A2
    A2 -->|"publish<br/>analysis.completed"| BUS
    BUS -->|"dispatch<br/>analysis.completed"| A3
    A3 -->|"publish<br/>content.generated"| BUS
    BUS -->|"dispatch<br/>content.generated"| A4
    A4 -->|"publish<br/>content.approved"| BUS
    BUS -->|"dispatch<br/>content.approved"| A5

    style A1 fill:#e3f2fd
    style A2 fill:#e8f5e9
    style A3 fill:#fff3e0
    style A4 fill:#fce4ec
    style A5 fill:#f3e5f5
`} />

核心机制：

| 机制 | 说明 |
|-----|------|
| **事件定义** | 每种事件有明确的 schema（类型、载荷、元数据） |
| **发布/订阅** | Agent 声明自己关心什么事件，不关心谁产生事件 |
| **事件路由** | 总线负责将事件路由到所有订阅者，支持过滤和转换 |
| **异步处理** | 事件处理是异步的，不阻塞上游 Agent |
| **死信队列** | 处理失败的事件进入死信队列，支持重试或人工介入 |

### 3.2 代表项目

**AG2**（原 AutoGen 2.0）

AG2 引入了事件驱动的 Agent 通信模型。Agent 不再通过多轮对话协作，而是通过**结构化事件**传递信息。每个 Agent 是一个事件处理器，定义自己订阅的事件类型和处理逻辑。

**Temporal + Agent**

将 Temporal 的持久化工作流引擎与 Agent 结合。Temporal 负责事件编排、重试、超时和状态持久化，Agent 负责具体的 LLM 调用和工具使用。这种组合在企业级场景中特别强大。

**Instructor + Anthropic MCP**

Model Context Protocol（MCP）定义了一种事件驱动的工具调用协议——Agent 通过事件通知工具可用性变化，工具通过事件上报执行结果。

### 3.3 优缺点

| 维度 | 优势 | 劣势 |
|-----|------|------|
| 松耦合 | ✅ Agent 之间无直接依赖，替换/新增不影响其他 | ❌ 事件链路不直观，调试需要追踪事件流 |
| 扩展性 | ✅ 新增 Agent 只需订阅事件，无需改动现有 | — |
| 异步 | ✅ 非阻塞执行，天然支持长时运行 | ❌ 异步调试困难，事件时序问题难复现 |
| 容错 | ✅ 单个 Agent 失败不影响全局 | ❌ 事件风暴（过多事件同时触发）需要背压机制 |
| 可观测 | ❌ 事件流需要专门的可观测基础设施 | — |

### 3.4 典型工程推荐

| 场景 | 推荐 | 理由 |
|-----|------|------|
| 微服务编排 | Temporal + LangGraph Agent | Temporal 负责编排和持久化，Agent 负责智能决策 |
| 实时数据处理 | AG2 + Kafka/RabbitMQ | 高吞吐事件流 + Agent 智能处理 |
| 物联网设备管控 | MQTT + Agent | 事件驱动天然适配设备事件 |
| 企业审批流 | Temporal + Human-in-the-loop | 长时等待、断点恢复、超时处理 |

## 4. SDK 封装范式

### 4.1 原理

SDK 封装范式的核心思想：**用声明式 API 将 Agent 开发的常见模式封装为高层抽象，开发者用链式调用或配置即可构建工作流，无需理解底层状态管理**。

<MermaidDiagram chart={`flowchart LR
    subgraph 传统["传统方式：命令式编排"]
        T1["手动管理状态"]
        T2["手写错误处理"]
        T3["手动追踪上下文"]
        T4["手写 Agent 通信"]
        T1 --> T2 --> T3 --> T4
    end
    
    subgraph SDK["SDK 封装：声明式编排"]
        S1["链式 API 调用"]
        S2["内置重试/回退"]
        S3["自动上下文管理"]
        S4["内置 Agent 通信"]
        S1 --> S2 --> S3 --> S4
    end
    
    传统 -.->|"封装"| SDK
    
    style 传统 fill:#ffcdd2
    style SDK fill:#c8e6c9
`} />

核心机制：

| 机制 | 说明 |
|-----|------|
| **链式调用** | `.prompt().tool().output()` 风格的流畅 API |
| **声明式配置** | 用 YAML/JSON/TOML 定义 Agent 行为，而非手写编排逻辑 |
| **内置 Guardrails** | 输入验证、输出校验、超时控制等作为一等公民 |
| **自动上下文** | SDK 自动管理对话历史、工具调用结果等上下文 |

### 4.2 代表项目

**OpenAI Agents SDK**

OpenAI 在 2025 年底推出的 Agents SDK，将 Agent 开发封装为声明式 API：

```python
from openai import Agent, Runner

agent = Agent(
    name="assistant",
    instructions="你是一个有帮助的助手",
    tools=[web_search, code_interpreter],
)

result = await Runner.run(agent, messages=[...])
```

核心概念：`Agent`（定义角色和工具）、`Runner`（执行引擎，管理状态和上下文）、`Handoff`（Agent 间的任务交接）。

**Vercel AI SDK**

Vercel 的 AI SDK 走得更远——它不仅是 Agent 开发框架，还是一个完整的 AI 应用开发工具链。核心抽象是 `generateText`、`streamText`、`generateObject` 等声明式函数，配合 React Server Components 实现服务端 AI 流。

```typescript
import { generateText } from 'ai';

const result = await generateText({
  model: openai('gpt-4o'),
  tools: { weather: weatherTool },
  prompt: '北京明天天气如何？',
});
```

**LlamaIndex Workflows**

LlamaIndex 的 Workflows 用事件驱动的方式封装了 RAG 管线的常见模式：

```python
from llama_index.core.workflow import Workflow, StartEvent, StopEvent, step

class MyWorkflow(Workflow):
    @step
    async def my_step(self, ev: StartEvent) -> StopEvent:
        result = await do_something(ev.input)
        return StopEvent(output=result)
```

**Pydantic AI**

Pydantic AI 强调类型安全和结构化输出——用 Pydantic 模型定义 Agent 的输入输出，SDK 自动处理验证和序列化。

### 4.3 优缺点

| 维度 | 优势 | 劣势 |
|-----|------|------|
| 开发效率 | ✅ 声明式 API 大幅降低编排代码量 | — |
| 上手门槛 | ✅ 几行代码即可启动，学习曲线平缓 | — |
| 类型安全 | ✅ Pydantic AI 等提供编译期校验 | ❌ 部分SDK缺乏类型提示 |
| 灵活性 | ❌ 被封装的抽象层限制自定义能力 | ❌ 脱离封装层时需深入源码 |
| 锁定风险 | ❌ 强依赖特定SDK的抽象和运行时 | — |
| 调试 | ❌ 封装层遮挡底层行为，黑盒调试 | — |
| 适用规模 | ✅ 中小规模应用快速启动 | ❌ 大规模分布式场景力不从心 |

### 4.4 典型工程推荐

| 场景 | 推荐 | 理由 |
|-----|------|------|
| 快速原型验证 | OpenAI Agents SDK | 最简 API，几行代码启动 |
| 全栈 AI 应用 | Vercel AI SDK | 前后端一体，流式处理一流 |
| RAG 管线 | LlamaIndex Workflows | RAG 场景最成熟的抽象 |
| 类型安全的 Agent | Pydantic AI | 输入输出模型驱动，验证严格 |
| 企业级多步骤流 | AWS Step Functions + Bedrock | AWS 生态集成的原生方案 |

## 5. 低代码范式

### 5.1 原理

低代码范式将 Agent 编排从代码空间移动到**可视化画布**——通过拖拽节点、连接边、配置参数来构建工作流。本质上是状态机或 DAG 的图形化表达，但开发者不需要写编排代码。

<MermaidDiagram chart={`flowchart LR
    subgraph 开发者视角["开发者视角：拖拽配置"]
        V1[/"📝 对话输入"\] --> N1["🤖 意图识别<br/>LLM Node"]
        N1 --> N2["🔍 知识检索<br/>RAG Node"]
        N2 --> N3["🧠 生成回答<br/>LLM Node"]
        N3 --> N4["✅ 输出<br/>输出 Node"]
        N1 --> N5["🔧 工具调用<br/>Tool Node"]
        N5 --> N3
    end

    subgraph 平台视角["平台视角：编译为运行图"]
        R1["意图识别 → RAG检索 → 生成回答"]
        R2["意图识别 → 工具调用 → 生成回答"]
        R1 --> R2
    end

    style 开发者视角 fill:#e8f5e9
    style 平台视角 fill:#e1f5fe
`} />

核心机制：

| 机制 | 说明 |
|-----|------|
| **可视化编辑器** | 拖拽式画布，节点连接的直观表达 |
| **节点市场** | 预置 LLM、RAG、工具调用、条件判断等常见节点 |
| **版本管理** | 工作流可版本化、回滚、A/B 测试 |
| **监控面板** | Token 消耗、延迟、成功率等实时可视化 |
| **一键发布** | 从画布到线上 API 的端到端流程 |

### 5.2 代表项目

**Dify**

Dify 是低代码 Agent 平台的标杆项目。核心功能：

- **工作流画布**：可视化的节点拖拽编辑器，支持 LLM 节点、知识库检索、代码执行、条件判断、HTTP 请求、变量赋值等
- **RAG 管线**：内置文档解析、分块、向量化和检索的完整管线
- **Agent 模式**：支持 ReAct、Function Calling 等推理策略
- **API 发布**：一键将工作流发布为 REST API

**Coze**（字节跳动）

Coze 的定位是"AI Bot 构建平台"：

- **Bot 画布**：比 Dify 更轻量的拖拽式编排
- **插件市场**：大量预置插件（搜索、图片生成、日程管理等）
- **多平台发布**：一键发布到飞书、微信、Discord 等
- **工作流**：支持条件分支、循环、子工作流

**FastGPT**

FastGPT 更偏技术向的低代码：

- **知识库驱动**：核心围绕知识库构建，RAG 能力很强
- **工作流编排**：支持 HTTP 请求、代码执行、AI 对话、条件判断等
- **API 优先**：所有功能都暴露为 API，适合嵌入到自有产品

**Flowise**

Flowise 是 LangChain 的可视化封装：

- **Chain 画布**：将 LangChain 的 Chain/Agent 抽象为可视化节点
- **聊天气泡组件**：内置前端聊天界面
- **嵌入友好**：生成的 Agent 可通过 iframe 或 API 嵌入任何网页

### 5.3 优缺点

| 维度 | 优势 | 劣势 |
|-----|------|------|
| 门槛 | ✅ 非技术人员也能构建 Agent 工作流 | ❌ 复杂逻辑表达力有限 |
| 速度 | ✅ 几分钟搭建一个可用的 Agent | — |
| 可视化 | ✅ 流程一目了然 | ❌ 复杂工作流画布变得难以维护 |
| 调试 | ✅ 可视化断点和变量查看 | ❌ 深层问题（如 LLM 幻觉）无法在画布层面解决 |
| 定制 | ❌ 受限于平台提供的节点类型 | ❌ 无法使用团队已有的代码/基础设施 |
| 锁定 | ❌ 强绑定平台运行时和数据格式 | ❌ 迁移成本高 |
| 可扩展 | ❌ 高并发、复杂状态管理力不从心 | — |

### 5.4 典型工程推荐

| 场景 | 推荐 | 理由 |
|-----|------|------|
| 内部知识问答 | FastGPT | 知识库能力强，API 优先 |
| 客服机器人 | Dify | 完整的工作流 + RAG + API 发布 |
| 快速 Demo / POC | Coze | 最快上手，多平台发布 |
| 技术团队嵌入 AI 能力 | Flowise | 基于 LangChain，代码可导出 |
| 教育/培训场景 | Dify + 自定义工具 | 低门槛 + 可扩展平衡 |

## 8. 混合编排实战

现实项目中，单一范式往往不够。以下三种混合模式经实践验证有效：

### 8.1 状态机 + 事件驱动：宏观确定 + 微观灵活

<MermaidDiagram chart={`flowchart TB
    subgraph Macro["宏观：状态机编排"]
        INIT["INIT"] --> ANALYZE["ANALYZE"]
        ANALYZE --> DESIGN["DESIGN"]
        DESIGN --> IMPLEMENT["IMPLEMENT"]
        IMPLEMENT --> VERIFY["VERIFY"]
        VERIFY --> ARCHIVE["ARCHIVE"]
    end
    
    subgraph Micro["微观：事件驱动"]
        E1[("data.collected")]
        E2[("analysis.done")]
        E3[("review.requested")]
        E4[("review.approved")]
        
        E1 --> E2 --> E3 --> E4
    end
    
    ANALYZE -->|"进入阶段时<br/>发布阶段事件"| E1
    IMPLEMENT -->|"内部任务完成时<br/>发布完成事件"| E3
    E4 -->|"事件触发<br/>进入下一状态"| VERIFY
    
    style Macro fill:#e1f5fe
    style Micro fill:#fff9c4
`} />

**适用场景**：主流程用状态机保证确定性（如 AI Team 的16阶段），阶段内部用事件驱动处理异步子任务（如代码审查、外部服务调用）。

**实践经验**：AI Team 的 Harness 架构就是这种模式——16 阶段状态机作为宏观骨架，每个阶段内部的 Agent 协作用事件驱动处理。

### 8.2 角色驱动 + SDK封装：场景明确 + 开发高效

用 CrewAI 定义角色和任务流程，每个角色内部用 OpenAI Agents SDK 或 Vercel AI SDK 封装具体的 LLM 调用和工具使用。

```python
# 角色驱动定义流程
researcher = Agent(role="研究员", ...)
writer = Agent(role="作者", ...)
crew = Crew(agents=[researcher, writer], tasks=[...])

# 每个角色的具体实现用 SDK 封装
class ResearcherAgent:
    def run(self, input):
        result = Runner.run(research_agent, messages=[...])
        return result
```

**适用场景**：团队已有角色分工习惯，各角色内部的 Agent 逻辑用 SDK 快速实现。

### 8.3 低代码 + 状态机：业务编排 + 工程兜底

用 Dify 等低代码平台处理业务用户可配置的部分（如知识问答流程、审核流程），用 LangGraph 状态机处理需要高可靠性的核心逻辑（如支付流程、部署流程）。

### 趋势一：从硬编码到自适应编排

当前编排范式都是"人定义流程、Agent 执行流程"。未来的方向是**Agent 根据任务特性自主选择编排策略**——简单任务用线性流程，探索性任务用角色驱动，需要灵活性的场景用事件驱动。这需要更强的模型能力，也正是 [Harness Engineering](/knowledge/ai/harness-engineering-knowledge-base) 所探讨的"知识引导而非流程约束"的方向。

### 趋势二：从单范式到混合范式

没有一种范式解决所有问题。未来的框架会把多种编排范式作为可选策略——同一个框架中，你可以为不同子任务选择状态机、角色驱动或事件驱动。LangGraph 已经在这样做：核心是状态机，但支持嵌套子图（可视为角色驱动），支持人类在环（事件驱动式的异步审批）。

### 趋势三：从中心化到去中心化

当前的编排都是中心化的——有一个编排器控制所有 Agent。未来可能发展出去中心化的 Agent 网络：Agent 自组织、自协商、自协调，按需形成临时团队。Swarm 和 AutoGen 的多 Agent 对话模式是这一方向的雏形。

### 趋势四：从代码编排到知识编排

当前编排逻辑写在代码里。正如 [前文](/knowledge/ai/harness-engineering-knowledge-base) 所述：**工作流是手段，知识是目的**。未来的编排逻辑可能从代码走向知识库——编排规则存储为结构化知识条目，Agent 在执行时从知识库查询编排策略，而非硬编码在代码中。

## 10. 总结与推荐

### 10.1 一句话总结每种范式

| 范式 | 一句话 |
|-----|--------|
| 状态机 | **流程确定、步骤可审计**——适合"知道每一步该做什么"的场景 |
| 角色驱动 | **分工明确、协作自然**——适合"知道谁该做什么"的场景 |
| 事件驱动 | **松耦合、高扩展**——适合"不知道什么时候会发生什么"的场景 |
| SDK封装 | **开发高效、上手简易**——适合"想快一点把Agent跑起来"的场景 |
| 低代码 | **门槛极低、可视可见**——适合"让不懂代码的人也能构建Agent"的场景 |

### 10.3 选型检查清单

在做最终决策前，问自己这五个问题：

1. **团队有工程背景吗？** 没有 → 低代码；有 → 继续
2. **任务流程是确定的还是探索性的？** 确定 → 状态机或SDK封装；探索 → 角色驱动或事件驱动
3. **需要断点恢复和持久化吗？** 需要 → 状态机（LangGraph）或 Temporal
4. **Agent 之间是强依赖还是松耦合？** 强依赖 → 角色驱动；松耦合 → 事件驱动
5. **需要非技术人员参与构建吗？** 需要 → 低代码平台

最后，记住一个原则：**从最简单的范式开始，只在遇到瓶颈时才增加复杂度**。不要因为事件驱动"更先进"就在5人团队的项目里用它——过早引入复杂编排，比没有编排更危险。
