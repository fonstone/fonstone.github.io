## 1. 什么是 AI Agent

### 1.1 定义

基于 LLM 的智能体（Agent）是一个能够**自主理解环境、进行规划决策、并执行行动以达成特定目标**的计算系统。其核心特征是使用 LLM 作为"大脑"进行复杂的推理和决策。

与传统的 LLM 问答不同，Agent 具备**自主性**和**循环执行**的特点——它能主动地、持续地与环境或工具交互，直到完成任务。

### 1.2 四大核心组件

| **工具使用模块** | 扩展 Agent 能力边界——调用 API、执行代码、与物理世界交互 |

## 2. ReAct 框架

ReAct（Reason and Act）是 Agent 领域最基础、最重要的行为框架，通过让 LLM 协同生成**推理轨迹（reasoning traces）**和**任务相关的行动（actions）** 来实现复杂任务。它模仿人类"**思考 → 行动 → 观察 → 思考...**"的循环模式。

<MermaidDiagram chart={`flowchart TB
    subgraph Loop["🔄 ReAct 循环"]
        T["💭 Thought<br/>分析目标与观察"]
        A["⚡ Action<br/>Action: [Tool, Input]"]
        O["👁 Observation<br/>工具返回结果"]
    end

    Start((开始)) -->|用户目标| T
    T -->|决定下一步| A
    A -->|调用工具| O
    O -->|更新上下文| T
    O -->|任务完成| End((结束))
`}/>

**工作流程**：

1. **思考（Thought）**：LLM 分析当前任务目标和已有信息（观察），生成内心独白，例如："我需要查找一下今天新加坡的天气。我应该使用搜索工具。"
2. **行动（Action）**：LLM 决定并生成可执行的行动，格式化为 `Action: [Tool_Name, Tool_Input]`
3. **观察（Observation）**：Agent 执行器解析行动并实际调用工具，将返回结果反馈给 LLM

### 2.1 ReAct 与 CoT 的结合

ReAct 中的 Thought 本质上是一种**动态的、交互式的思维链**。传统 CoT 是一次性生成所有思考步骤再得出答案，而 ReAct 的思考是**每一步行动前**进行的、**基于最新观察结果**的思维链：

| 特性 | 传统 CoT | ReAct |
|------|----------|-------|
| 推理方式 | 一次性线性生成 | 动态交互式，每步行动前思考 |
| 信息依据 | 仅凭自身知识 | 基于实时工具返回的最新观察 |
| 错误修正 | 出错则全盘失败 | 可分析失败原因并尝试不同方案 |
| 适用场景 | 静态推理问题 | 动态环境、多工具交互 |

## 3. 规划能力

规划能力是衡量 Agent 智能水平的核心指标。目前主流方法从简单到复杂分为多个层次：

<MermaidDiagram chart={`flowchart TB
    subgraph Implicit["🔤 基于提示的隐式规划"]
        direction TB
        CoT["Chain-of-Thought<br/>线性思维链"]
        ReActP["ReAct<br/>思考-行动-观察循环"]
    end
    subgraph Search["🔍 基于搜索的显式规划"]
        direction TB
        ToT["Tree-of-Thoughts<br/>思维树 - 多路径探索"]
        GoT["Graph-of-Thoughts<br/>思维图 - 路径合并与循环"]
    end
    subgraph Decomp["📂 基于任务分解的规划"]
        direction TB
        Planner["规划器 LLM<br/>分解为依赖图"]
        Executor["执行器 LLM<br/>逐一完成子任务"]
    end

    Simple((简单任务)) --> CoT
    Complex((复杂任务)) --> ToT
    Complex --> Planner
    ToT -.->|泛化| GoT
`}/>

### 3.1 基于提示的隐式规划

| 方法 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **CoT** | "Let's think step by step"引导线性思考 | 实现简单，无需修改模型 | 线性不可回溯，一步出错全盘失败 |
| **ReAct** | 思考-行动-观察动态循环 | 鲁棒性强，支持纠错 | 需要工具执行环境 |

### 3.2 基于搜索的显式规划

**Tree of Thoughts（ToT）**：将规划过程构建为一棵"思维树"。从初始问题出发，LLM 生成多个并行的思考路径（树的分支），采用树搜索算法（广度优先或深度优先）探索最优解。每个思维节点由 LLM 自己评估打分，选择最有希望的路径继续扩展。允许模型进行**探索、评估和回溯**。

**Graph of Thoughts（GoT）**：对 ToT 的进一步泛化。思维过程是图状的，支持：
- **合并（Merge）**：不同思维路径可以汇合，整合多个子问题的解
- **循环（Cycle）**：思维过程可以迭代地优化和精炼

### 3.3 基于任务分解的规划

训练或提示 LLM 充当"规划器"，将主任务显式分解为依赖图或步骤列表，再由"执行器"逐一完成子任务。结构清晰但预先分解的计划缺乏对动态变化的适应性。

## 4. 记忆系统

记忆模块是 Agent 打破 LLM 上下文窗口限制、实现持续学习和个性化的关键。设计 Agent 的记忆系统通常会模仿人类的记忆机制，分为短期记忆和长期记忆。

<MermaidDiagram chart={`flowchart TB
    subgraph STM["📝 短期记忆 (Short-Term Memory)"]
        Ctx["上下文窗口<br/>LLM Context Window"]
        Buf["缓冲区管理<br/>ConversationBufferMemory"]
        SP["暂存器 Scratchpad<br/>Thought-Action-Observation"]
    end
    subgraph LTM["📚 长期记忆 (Long-Term Memory)"]
        VE["向量嵌入<br/>Embedding Model"]
        VD["向量数据库<br/>Pinecone / FAISS"]
        KG["知识图谱<br/>Neo4j"]
    end
    subgraph RAGFlow["🔄 RAG 工作流"]
        Store["存储: 文本→向量→入库"]
        Retrieve["检索: 查询→相似度搜索"]
        Use["使用: 检索结果→LLM Prompt"]
    end

    Agent((Agent)) -->|当前会话上下文| Ctx
    Agent -->|跨任务知识| VD
    VD --> Retrieve
    Retrieve -->|增强上下文| Agent
`}/>

### 4.1 短期记忆

- **LLM 上下文窗口**：最直接的短期记忆载体，所有最近的交互都放入 Prompt
- **缓冲区管理**：
  - `ConversationBufferMemory`：存储完整的对话历史
  - `ConversationBufferWindowMemory`：只保留最近的 K 轮对话
  - `ConversationSummaryBufferMemory`：过长时用 LLM 动态总结，节省 Token
- **暂存器（Scratchpad）**：记录 ReAct 框架中的"Thought-Action-Observation"轨迹，是 Agent 逐步推理的关键

### 4.2 长期记忆

长期记忆的核心是"**存储**"和"**检索**"，最主流的技术路线是 **RAG（Retrieval-Augmented Generation）** 范式：

**存储流程**：当 Agent 获得有价值的信息时，使用嵌入模型将其转换为高维向量，存入向量数据库。

**检索流程**：Agent 将当前任务或问题转换为查询向量，在向量数据库中进行相似度搜索（余弦相似度或点积），找出最相关的历史记忆。

**关键工具**：
- **向量数据库**：Pinecone、ChromaDB、FAISS、Weaviate
- **嵌入模型评估基准**：MTEB（Massive Text Embedding Benchmark）是目前最权威的评测基准
- **传统数据库/知识图谱**：对于结构化或关系型数据，使用 SQL 或图数据库（如 Neo4j）进行精确查询

## 5. Tool Use 与 Function Calling

LLM 学会调用外部 API 或工具，是其从一个纯粹的"语言模型"转变为一个"行动执行者"的关键一步。主流的实现方式是 **Function Calling**。

<MermaidDiagram chart={`sequenceDiagram
    actor User as 用户
    participant LLM as LLM Agent
    participant Ctrl as 控制代码
    participant API as "外部工具 / API"

    User->>LLM: 今天新加坡天气怎么样
    Note over LLM: 分析意图：需要天气信息
    Note over LLM: 匹配工具 get_current_weather
    LLM->>Ctrl: 输出 JSON 函数调用
    Note over Ctrl: 解析 JSON name/arguments
    Ctrl->>API: 执行 get_current_weather
    API->>Ctrl: 返回天气数据
    Ctrl->>LLM: 将结果作为新上下文输入
    LLM->>User: 新加坡今天晴天 32C
`}/>

### 5.1 Function Calling 五步流程

1. **工具定义与注册**：以结构化模式（JSON Schema）向 LLM 描述可用工具，包括函数名称、函数描述（自然语言，LLM 据此判断何时使用）、参数列表
2. **LLM 决策与意图识别**：将用户提问连同所有已注册的工具描述一起发送给 LLM，LLM 分析意图并决定是否调用工具
3. **生成结构化调用指令**：LLM 输出特殊的 JSON 对象，包含要调用的函数名称和参数
4. **外部执行与结果返回**：控制代码解析 JSON，在外部环境实际执行函数，返回结果
5. **整合结果并生成最终回复**：将工具返回结果作为新上下文再次发送给 LLM，LLM 生成最终回答

## 6. Agent 微调

单纯的提示驱动 Agent（zero-shot Agent）在复杂或特定领域任务上稳定性和效率往往不够理想。微调是让 Agent 变得更可靠、更高效的关键步骤。

### 6.1 核心思想

微调 Agent 能力的核心是**教会模型如何更好地"思考"和"使用工具"**，本质上是一种**行为克隆（Behavioral Cloning）**。微调的数据集不是简单的（输入, 输出）对，而是一系列高质量的**决策轨迹（decision-making trajectories）**。

### 6.2 数据集收集方法

**使用教师模型生成合成数据**（最主流高效的方法）：
1. 定义任务和工具集
2. 创建任务样本 Prompts
3. 使用强大模型（如 GPT-4o）作为教师，在 ReAct 框架下执行任务
4. 记录完整轨迹：每一步的"思考（Thought）"和"行动（Action）"
5. 过滤清洗：筛选掉执行失败或质量不高的轨迹

其他方法包括人工编写/修正轨迹、从真实用户交互中收集数据。

## 7. 主流框架对比

### LangChain vs LlamaIndex

| 维度 | LangChain | LlamaIndex |
|------|-----------|------------|
| **核心哲学** | 通用 LLM 应用"编排"框架，关注**工作流构建** | 专注外部数据的"数据"框架，关注**数据流管理** |
| **核心抽象** | Chains、Agents、Memory、Callbacks | Data Connectors、Indexes、Retrievers、Query Engines |
| **最擅长场景** | 复杂多步骤 Agent，多工具协作 | 高性能 RAG 系统，复杂数据索引与检索 |
| **应用举例** | 研究助手、客服 Agent、自动化流程 | 技术文档 QA、金融分析、个人知识管理 |

**选型策略**：
- **逻辑编排驱动**（复杂逻辑编排和多工具协作）→ **LangChain**
- **数据驱动**（构建强大知识库和问答能力）→ **LlamaIndex**
- **实际中常结合使用**：LlamaIndex 构建知识库检索工具 → 接入 LangChain Agent

### RAGFlow 等其他平台

RAGFlow、Haystack 等更像"开箱即用"的 RAG 应用平台，提供自动化和可视化界面：
- **选择 LangChain/LlamaIndex 的场景**：高度定制化需求、需要深度控制每一个环节、开发者为核心的团队
- **选择 RAGFlow/Haystack 的场景**：快速原型验证、追求最佳实践、技术团队规模有限

## 8. 多智能体系统

### 8.1 相比单 Agent 的优势

1. **分工与专业化**：为每个 Agent 设定不同角色和专长（如产品经理 Agent、程序员 Agent、测试 Agent）
2. **并行处理与效率**：分解子任务同时处理，缩短总时间
3. **鲁棒性与冗余**：单 Agent 故障不影响整体系统
4. **视角多样性与创新**：不同 Agent 从多角度审视问题，通过辩论和协商激发创造性

    Coordinator -->|分配子任务| Dev

### 8.2 引入的新复杂性

1. **通信协议与语言**：需要标准化通信协议和消息格式，确保 Agent 间能相互理解意图
2. **协调与协作机制**：任务分配、领导决策、冲突解决，需要集中式"指挥官"或分布式协商协议
3. **社会行为与动态**：信任、欺骗、联盟等复杂社会现象可能出现
4. **系统状态维护与一致性**：确保所有 Agent 对环境有一致的、最新的认知
5. **信用分配**：评估各 Agent 在团队任务中的贡献或责任

### 8.3 A2A 框架

A2A（Agent-to-Agent）框架与普通 Agent 框架的**关键区别**在于抽象层次：

- **普通 Agent 框架**（如 LangChain）关注"**个体的实现**"——如何构建能干活的个体（应用层）
- **A2A 框架**关注"**群体的交互标准**"——让所有个体互相交流的"社会规则"（协议层）

A2A 试图定义一套通用的标准、协议和语言，使得不同开发者、使用不同技术栈构建的 Agent 能够相互发现、理解和交互。

## 9. Embodied Agent（具身智能体）

当 Agent 从纯粹软件环境（调用 API）进入真实或模拟的物理环境（机器人、游戏）时，称之为**具身智能体（Embodied Agent）**，有五个本质区别：

| 维度 | 软件 Agent | 具身 Agent |
|------|-----------|------------|
| **感知** | 结构化、符号化信息（JSON） | 非结构化、高维、带噪声的传感器数据 |
| **状态可观测性** | 完全可观测 | 部分可观测（只能看到局部视野） |
| **行动空间** | 离散、确定（API 调用） | 连续、随机（电机误差、摩擦力） |
| **实时性** | 回合制、异步 | 实时持续感知-决策-行动 |
| **安全后果** | 可逆、有限 | 物理性、不可逆、可能危险 |

## 10. 安全与对齐

### 10.1 六个保障层次

1. **核心模型对齐**：使用 RLHF、DPO、Constitutional AI 等技术使 LLM 遵循"有用、诚实、无害"原则
2. **工具与权限管理**：最小权限原则、工具白名单、读写执行权限控制、资源限制
3. **人类在环（HITL）**：高风险操作前 Agent 生成执行计划并等待人类批准；人类实时监控
4. **沙箱化**：Agent 生成的代码在 Docker 容器或虚拟机中执行，隔离破坏范围
5. **明确的规则与护栏**：硬编码规则、正则过滤器（如禁止 `rm -rf /`）
6. **持续的红队测试与审计**：组织专门团队从各种角度攻击 Agent，详细记录行为轨迹进行事后分析

### 10.2 红队测试（Red Teaming）

红队测试是源自网络安全的**对抗性测试**方法，在 AI 领域指：
- **发现安全漏洞**：设计"越狱提示"绕过安全审查；模拟提示注入攻击劫持 Agent
- **发现偏见**：暴露刻板印象、测试政治与社会偏见、揭示代表性不足问题

## 11. RAG（检索增强生成）

RAG 是一种"**先检索，后生成**"的模式，将信息检索与文本生成相结合，增强 LLM 的能力。

### 11.1 RAG 解决的问题

1. **知识的静态性与过时性**：知识截止于训练数据时间点
2. **幻觉（Hallucination）**：在不确定时捏造事实
3. **缺乏专业领域知识与私有知识**：微调注入知识成本高、效果有限

### 11.2 完整流水线

<MermaidDiagram chart={`flowchart TB
    subgraph Offline["📦 离线阶段：数据准备 / 索引"]
        Load["数据加载<br/>PDF / HTML / 数据库"] --> Split["文本切块 Chunking"]
        Split --> Embed["嵌入 Embedding<br/>文本→向量"]
        Embed --> Store["Pinecone / ChromaDB<br/>向量数据库"]
    end
    subgraph Online["🌐 在线阶段：查询与推理"]
        Query["用户提问"] --> QEmbed["查询嵌入<br/>相同嵌入模型"]
        QEmbed --> Retrieve["向量检索<br/>相似度搜索 Top-K"]
        Retrieve --> Rerank["重排序 Re-rank<br/>Cross-Encoder"]
        Rerank --> Augment["增强 Prompt<br/>原始问题 + 检索结果"]
        Augment --> Generate["LLM 生成<br/>基于上下文的回答"]
    end

    Store -->|流向在线阶段| Query
`}/>

**离线阶段（数据准备）**：
1. **数据加载**：从 PDF、网页、数据库、Notion 等数据源加载原始文档
2. **文本切块**：将长文档切割为语义完整的文本块（chunks）
3. **嵌入**：使用嵌入模型（BERT、BGE、M3E）将文本块转换为高维向量
4. **存储**：将文本块内容和向量存入向量数据库

**在线阶段（查询推理）**：
1. **用户提问**并转换为查询向量
2. **向量检索**：计算相似度，找出 Top-K 最相关文本块
3. **重排序（可选）**：用 Cross-Encoder 精细打分，选出 Top-N
4. **增强与生成**：将检索结果与原始问题拼接为增强提示，喂给 LLM

### 11.3 文本切块策略

切块大小（Chunk Size）和重叠长度（Overlap）的选择需要在多个因素间权衡：

| 策略 | 优点 | 缺点 |
|------|------|------|
| **大块**（如 1024 tokens） | 上下文丰富 | 噪声增加、检索精度下降、成本高、Lost in the Middle |
| **小块**（如 128 tokens） | 检索精确、信息密度高 | 上下文不足、语义割裂 |

**经验法则**：重叠长度设为切块大小的 10%-20%；从 `chunk_size=512, overlap=64` 基线开始迭代优化。复杂场景可采用**多尺度切块**策略。

### 11.4 嵌入模型选择

参考 **MTEB/C-MTEB 排行榜**，选择在 **检索（Retrieval）** 任务上得分高的模型。评估指标：
- **nDCG@k**：综合衡量相关性和排名
- **Recall@k**：召回率
- **MRR**：第一个相关文档排名

**增强检索器**：
- **混合搜索（Hybrid Search）**：BM25（关键词精确匹配）+ 向量搜索（语义相似度）相结合
- **重排序（Re-ranking）**：两阶段——先用快速方法召回 Top 50，再用 Cross-Encoder 精细重排为 Top 5
- **小块引用大块（Small-to-Large）**：用小块检索获取高精度，用大块上下文保证完整性
- **图索引（Graph Indexing）**：LLM 提取实体和关系构建知识图谱，支持多跳推理

**优化查询**：
- **多查询检索（Multi-Query Retrieval）**：LLM 从不同角度生成多个查询，合并检索结果
- **HyDE**：先让 LLM 生成"假设性答案"，用这个答案的嵌入去检索
- **子问题查询（Sub-Querying）**：复杂问题分解为多个子问题，分别检索汇总

**高级 RAG 范式**：
- **Self-RAG**：首次检索生成后，LLM 反思评估，主动生成新查询进行二次检索
- **FLARE（自适应检索）**：生成过程中逐 token 预测不确定性，在不确定时"即时"检索
- **多源数据 RAG**：Agent 智能决定从向量库、知识图谱、SQL 数据库、搜索引擎等不同来源检索

### 11.6 "Lost in the Middle"问题

LLM 在处理长上下文时，倾向于更好地回忆**开头和结尾**的信息，而忽略**中间部分**的信息。

**缓解方法**：
1. **文档重排序**：将最相关的文档放在开头和结尾
2. **减少检索文档数量**：严格控制 Top-K 的 K 值
3. **指令化提示**：明确指示模型关注所有上下文
4. **微调 LLM**：构建要求利用中间信息才能回答的数据集进行训练

### 11.7 RAG vs 搜索系统

| 特征 | 搜索系统 | RAG 系统 |
|------|---------|----------|
| **任务** | 找文档（Find Documents） | 给答案（Give Answers） |
| **输出** | 文档列表（List of sources） | 自然语言答案（Synthesized answer） |
| **用户角色** | 主动阅读和总结 | 被动获得成品答案 |
| **核心组件** | 索引器 + 排序器 | 索引器 + 排序器 + 生成器（LLM） |

### 11.8 RAG 评估体系

**检索阶段**：
- **Context Precision**：检索结果的"信噪比"
- **Context Recall**：相关文档的召回全面性
- **nDCG@k**：综合相关性和排名
- **MRR**：第一个相关文档排名

**生成阶段**：
- **忠实度/可溯源性（Faithfulness）**：答案是否完全基于上下文
- **答案相关性（Answer Relevancy）**：是否直接回答用户问题
- **答案正确性（Answer Correctness）**：是否事实准确

**自动化框架**：RAGAS、ARES、TruLens——使用 LLM-as-a-Judge 思想自动计算上述指标。

### 11.9 RAG 部署挑战

1. **数据处理复杂性**：异构数据源的分块策略泛化、知识库实时更新
2. **性能瓶颈**：检索+生成两步延迟、大规模嵌入和 LLM API 成本
3. **端到端评估**：生产环境缺少带标准答案的数据集
4. **"无答案"处理**：系统应具备拒绝回答的能力，而非强行生成错误答案
5. **安全与隐私**：企业级访问控制、提示注入防护

## 12. 模型评估与 Agent 评估

### 12.1 传统指标为何失效

BLEU、ROUGE 等传统指标基于 n-gram 词汇重合度，对现代 LLM 存在以下局限：
1. **语义理解缺失**：近义词表达得分低，而词汇重合但逻辑混乱的句子得分高
2. **无法评估事实准确性**：无法检测事实性错误（幻觉）
3. **忽略多样性与创造性**：惩罚不同于参考答案但同样优秀的回答
4. **长文本评估差**：对连贯性、逻辑性、结构性无能为力
5. **无视推理过程**：只能比较最终答案，无法评估思维链步骤

### 12.2 主流综合基准

| 基准 | 侧重点 | 形式 | 评估目的 |
|------|--------|------|----------|
| **MMLU** | 知识广度与学科问题解决 | 57 科目四选一 | 知识渊博程度 |
| **Big-Bench** | 能力边界与涌现能力 | 200+ 多样化任务 | 通用智能水平 |
| **HumanEval** | 代码生成与编程 | 164 手写编程问题 | 编写正确代码的能力 |
| **GSM8K** | 数学推理 | 小学数学应用题 | 思维链推理能力 |
| **HellaSwag** | 常识推理 | 情境续写选择 | 常识理解能力 |

### 12.3 LLM-as-a-Judge

使用一个强大的 LLM（裁判模型）评估被测试 LLM 的输出质量。

**工作流程**：提供评估提示给裁判模型，包含用户问题、待评估回答、评估准则 → 裁判输出分数和解释。

**优点**：可扩展性与效率高、一致性、可定制化。

**潜在偏见**：
- **位置偏见**：偏爱第一个呈现的答案
- **冗长偏见**：给更长更详细的回答打高分
- **自我偏好/风格偏见**：偏爱与自身风格相似的回答
- **有限的知识与推理能力**：裁判模型本身也可能犯错
- **过于"宽容"**：对有害内容判断比人类更宽容

### 12.5 Agent 专用基准

| 基准 | 专注领域 | 关键特征 |
|------|----------|----------|
| **WebArena** | 网页浏览与操作 | 复刻真实网站（电商、论坛），基于网页状态判断 |
| **AgentBench** | 通用 Agent 能力 | 8 个环境：Linux 终端、SQL 数据库、知识图谱、游戏 |
| **GAIA** | 真实工具组合使用 | 多步推理 + 多工具组合，对人类简单对 AI 困难 |
| **SWE-bench** | 代码修复 | GitHub Issue → 代码补丁 |
| **OSWorld** | 操作系统操控 | 文件操作、命令执行等 |

**基准构建方法**：
1. **环境构建**：Docker 沙箱化、本地托管网站副本、模拟 API 服务器
2. **任务构建**：高层目标形式、覆盖多种能力、可程序化验证的成功标准
3. **评估构建**：评估脚本自动检查环境最终状态

### 12.6 持续监控与运维

已部署的 LLM 应用需要应对**数据漂移**（用户输入分布变化）和**模型漂移**（预测能力下降）：

**四步闭环**：

1. **采集与日志**：记录完整交互数据、嵌入用户反馈机制（顶/踩、打分）
2. **自动化监控**：监控代理指标（问题长度、回答长度、工具调用失败率）、定期抽样用 LLM-as-a-Judge 评估
3. **人工审核与分析**：审计坏案例、根本原因分析
4. **反馈闭环与迭代**：失败案例加入评估集/微调数据集、定期微调、A/B 测试

## 13. 构建复杂 Agent 的核心挑战

1. **规划与推理的鲁棒性**：LLM 推理链条脆弱，容易在执行过程中迷失目标、陷入无效循环
2. **可靠且可复现的评估**：开放式任务无唯一正确答案；环境动态导致结果不可复现；评估成本高
3. **成本、延迟与可扩展性**：复杂任务需数十甚至上百次 LLM 调用，高成本高延迟制约大规模部署
4. **安全与可控性**：权限管理困难、提示注入攻击、自主行为不可预测
