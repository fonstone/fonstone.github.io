周五下午，一个同事把一段需求贴进编码 Agent，让它改登录模块。Agent 改完了，测试也过了，合并之后才发现它顺手把错误码的枚举重排了一遍，下游服务全对不上。需求里没写别动枚举，Agent 也没理由不动。事后复盘能确认的只有一件事，约束没写进它读得到的地方。

这个系列里八篇文章都在处理同一类问题，把人脑子里默认的约束写成 Agent 读得到的文件，并在合并前加一道能拦住它的检查。最早的一篇从规范文件下手，把需求先写成结构化规格再交给模型。后面几篇把踩过的坑做成技能包和团队知识库，让 Agent 按场景自己取用。再往后，检视 Agent 和确定性流水线负责在合并前拦住问题。最后一篇处理模型输出本身的不稳定，用 schema 和 Hook 把不确定性收进可维护的工程约束里。八篇前后隔了几个月写完，做法换过几轮，串得起来的还是那个问题，约束放在哪一层。

推荐读法从 OpenSpec 和 Skills 两篇开始，先看清约束写成什么形式模型才读得到，再读多 Agent 协作那篇，理解分工之后规范怎么分摊。HarmonyOS Skill 和 Harness 知识库可以接着读，前一篇讲单个知识包怎么组织，后一篇讲团队怎么维护一套分层存储。检视 Agent 全景适合在动手搭流水线之前翻，里面有一份工具清单和 c-CRAB 的评估结果。OpenCodeReview 架构那篇拆得更细，读完能照着拼一套 diff 解析加评论定位的流程。大模型不确定性那篇放在最后，它解释前面所有约束为什么仍会被模型绕过去，以及结构化输出能补上的那一段。

这八篇是 2026 年 11 月之前写下的做法。OpenSpec 和 Skills 的文件格式都改过版本，读的时候把当时的版本号一起看，比记住某个目录名有用。
