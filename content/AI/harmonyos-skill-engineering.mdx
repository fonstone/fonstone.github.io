# HarmonyOS Skill 工程化：AI Coding 时代的实战经验沉淀范式

## 一、工程概览

### 1.1 项目定位

HarmonyOS-Skill 是一套从 **三个真实鸿蒙原生 App 开发实战**（潮玩展柜 + 熬夜修仙 + 鲸播 OrcaPlayer，全部已上架应用市场）沉淀出来的 **HarmonyOS NEXT 开发 Skill 集合**，覆盖 ArkUI 状态管理 / 桌面服务卡片 / 视频播放与媒体 / NAS 串流 / IAP / 元服务 / 测试 / 真机打包 / 应用市场上架等核心场景。

截至 2026 年 7 月，仓库已积累 **44 个 skill**（从 3 个实战 App 的 60+ bug 修复记录和 472 个真机测试用例中提炼），每个 skill 都是"问题场景 + 反模式 + 正确代码模板 + 验证方法"的完整知识包。

核心卖点是 **"AI Coding 友好"**——把踩过的坑、查过的官方文档、试过的方案沉淀成 AI 助手可直接消费的 skill 知识包，让下一个鸿蒙项目少走弯路。

### 1.4 实战案例：三个真实 App 的 Skill 沉淀

该仓库的 skill 来自三个已上架的鸿蒙原生 App，每个 App 覆盖不同的技术维度：

#### 1.4.1 潮玩展柜 — ArkUI 状态管理 + 桌面卡片 + IAP

首个实践项目（已上架华为应用市场）：用户拍照 → AI 端侧抠图 → 数字展柜展示 → 桌面服务卡片。

**沉淀的 skill 重点**：
- **@Observed/@ObjectLink 全链路**：对象数组嵌套时 UI 不更新的根因
- **透明背板 5 件套**：桌面卡片背景透明的完整配置链
- **IAP 集成**：应用内购买的双协议签署 + Profile 重生成
- **Core Vision Kit 端侧 AI 抠图**：完全离线零成本的 AI 能力

#### 1.4.2 熬夜修仙 — 元服务 + 跨进程同步

第二个实践项目（HarmonyOS 元服务，AGC 审核通过）：以修仙等级反讽包装的熬夜记录元服务。

**沉淀的 skill 重点**：
- **元服务 API 网关**：`@atomicservice` 标记 / 编译 11706010 / 平台硬边界
- **卡片刷新配额与 AGC 合规**：刷新方式选择与审核通过策略
- **跨进程 preferences 同步**：卡片 ↔ 主 App 双进程数据一致性
- **AGC 多轮拒审根治**：改时钟测时长 / 正文对比度 / 卡片快照错误码 13

#### 1.4.3 鲸播 OrcaPlayer — 视频播放 + NAS 串流 + 复杂上架

第三个实践项目（已上架应用市场）：发烧友级本地全能视频播放器，双内核全格式播放 + NAS 串流。

**沉淀的 skill 重点**：
- **双内核播放架构**：AVPlayer 硬解 + ijkplayer 软解兜底
- **字幕全链路**：内封/外挂字幕轨、libass 交叉编译、GBK/Big5 编码探测
- **NAS 串流**：WebDAV 硬解出画 + SMB 桥接 + 4MB 预读
- **HUKS 凭据加密**：AES-256-GCM 三段式会话
- **普通 App 三轮拒审根治**：审核实验室网络 / "开通中"判功能未完成 / IAP 预检门控

### 1.5 快速上手教程

#### 步骤 1：将 Skill 库接入项目

```bash
cd your-harmonyos-project
git submodule add https://gitee.com/chen_jeff/harmony-os-skill.git .skills
```

这会在你的项目中创建 `.skills/` 目录，包含全部 44 个 SKILL.md。

#### 步骤 2：让 AI 助手消费 Skill

在开发时告诉 AI：

> 我在写鸿蒙桌面服务卡片，刷新失败但 build() 跑了，参考 `.skills/skills/` 找找有没有相关 skill。

AI 会自动按 `description` 字段做语义匹配，加载 `harmonyos-form-transparent` 等相关 skill。

#### 步骤 3：人肉查阅

遇到具体问题时直接搜索对应主题。每个 skill 结构一致：

1. 何时使用此 skill → 2. 核心结论 → 3. 反例 ❌ → 4. 正确做法 ✅ → 5. 验证方法 → 6. 相关 skill → 7. 参考资料

#### 步骤 4：沉淀新经验

修复 Bug 后，按模板写成新 skill 并提交 PR，将个人经验转化为团队资产：

```bash
# 创建新 skill 目录
mkdir -p .skills/skills/<category>-<problem-slug>
# 编写 SKILL.md（参照 4.2 节模板）
# 提交到仓库
git add .skills/
git commit -m "feat(skill): 新增 <问题> 的解决经验"
git push
```

**设计原理**：传统的知识库（Notion、Wiki）是人写的、人看的，AI 无法高效消费。HarmonyOS-Skill 的设计核心是将"人脑经验"转化为"AI 可检索、可推理、可执行"的结构化知识包。

### 2.2 Frontmatter：语义触发引擎

每个 `SKILL.md` 顶部用 YAML frontmatter 标记元数据：

```yaml
---
name: arkui-observed-objectlink-chain
description: 在编写 ArkUI 鸿蒙代码遇到「修改对象数组里某个元素的属性后 UI 不更新 / 
  build() 跑了但 Image 不刷新 / 杀 App 重启才正常」、或设计列表项数据响应式刷新方案时使用。
---
```

**关键设计原则**：
- `description` 不写"这是什么"，而是写"**在什么场景下使用、解决什么问题**"
- 埋入 **症状关键词**（"UI 不更新""白底""权限错"），让 AI 做语义检索时命中率最高
- 埋入 **场景关键词**（"首次集成""从 X 迁移""卡在 Y"）
- 控制在 100-200 字，信息密度高

### 2.3 六段式模板：认知闭环

所有 skill 严格遵守同一骨架：

    B --> C["3️⃣ 反例 ❌<br/>错误写法 + 根因"]
    C --> D["4️⃣ 正确做法 ✅<br/>可复制代码模板"]
    D --> E["5️⃣ 验证方法<br/>可观测证据"]

    style A fill:#fff3e0,stroke:#e65100
    style B fill:#e1f5fe,stroke:#0288d1
    style C fill:#ffebee,stroke:#c62828

    style E fill:#f3e5f5,stroke:#7b1fa2

**认知闭环原理**：
1. **触发检测**：让 AI 知道"什么时候该用这个知识"
2. **结论先行**：先给正确答案，避免 AI 试错
3. **反例警示**：展示 AI 容易生成的错误代码 + 根因——传递判断力，而非知识点
4. **正解复现**：给出可直接复制的代码模板
5. **验证闭环**：强调可观测证据（"杀 App 重进正常 vs 运行时变更异常"），杜绝假性修复
6. **知识联网**：交叉引用把同源根因串联

### 2.4 验证方法设计

作者特别强调 **验证证据**，反对"build() 跑了就算修好"。典型验证范式：

| 验证场景 | 正确验证方法 | 错误验证方法 |
|----------|-------------|-------------|
| UI 刷新修复 | Image 加 .onAppear 打日志 → 路径变更才算真修复 | "build() 跑了" |
| IAP 集成 | iap.queryProducts 不报权限错才算 Profile 通过 | "编译通过" |
| 状态追踪修复 | "杀 App 重进正常 vs 运行时变更异常"差异大 | 只测一次 |

### 3.2 部署架构：Submodule 解耦

采用 `git submodule` 而非复制粘贴，核心优势：

1. **版本追踪**：skill 库独立版本，项目锁版本不随 skill 更新意外变动
2. **集中更新**：skill 库更新后，项目 `git submodule update` 即可获得全部最新知识
3. **解耦治理**：skill 库与业务代码互不依赖，不同项目可共享同一 skill 库
4. **PR 协作**：团队可向 skill 库贡献新 skill，沉淀集体经验

### 3.3 消息过覆盖率

项目通过 **472 个测试用例真机全绿** 来验证 skill 的正确性。每个 skill 的验证方法中明确规定了如何确认修复有效。测试覆盖确保：
- 知识不存疑：每个 skill 的结论至少经过一次真机验证
- 修改可追溯：60+ bug 记录原始材料，每个 fix 有迹可循
- 质量有基线：上架 App 验证过的方法论，非纸上谈兵

## 四、经验总结与可复用方法论

### 4.1 核心方法公式

```
1 个 skill = 1 个反复出现的具体坑
```

**判断是否值得沉淀**：
- 同一个坑你或 AI 踩过 ≥ 2 次
- 官方文档把关键约束藏在不起眼处
- AI 默认生成的代码是错的（训练库过时）

### 4.2 通用 SKILL.md 模板

```markdown
---
name: <tech>-<module>-<problem-slug>
description: <技术栈> <模块> <问题> — 在遇到<症状关键词>/<报错码>时使用。
---

# <标题：问题 + 正确方案>

## 何时使用此 skill
<列出触发条件>

## 核心结论
<一句话正确答案>

## 反例 ❌
<错误代码 + 根因>

## 正确做法 ✅
<可复制代码模板>

## 验证方法（必做）
<可观测证据>

## 排错清单（可选）
<按优先级排序的检查项>

## 常见误区（可选）
<误区 vs 真相 表格>

## 相关 skill
<交叉引用>

## 参考资料
<官方文档链接>
```

### 4.3 六条核心原则

1. **粒度精准**：一个 skill 解一个坑，不写大而全。粒度小 → AI 检索命中后上下文短、token 省；粒度小 → 易维护、易增量沉淀

2. **结构固定**：六段式模板保证质量下限与 AI 消费一致性。无论谁写、哪个模块，读者（人或 AI）一看就懂

3. **反例驱动**：用"AI 会犯的错"反向定义正确方案。不是罗列 API，而是传递判断力——让 AI 知道"为什么会错"比"正确答案是什么"更重要

4. **验证闭环**：强调可观测证据，杜绝假性修复。验证方法不是可选项，是必选项

5. **语义触发**：Frontmatter description 用"场景 + 症状"语言，让 AI 零配置自动检索。不写"这是什么"，写"什么情况下用"

6. **实战沉淀**：来自真实上架 App，非纸上谈兵。每个 skill 背后都有一个真机验证过的 Bug 修复记录

### 4.4 填补三类信息断层

| 断层类型 | 例子 | Skill 解法 |
|---------|------|-----------|
| 训练库截止前的旧 API | `consumeOwnedPurchase` 已改名 `finishPurchase` | 记录最新 API + 兼容方案 |
| 官方文档藏关键约束 | "必须手动签名"藏在透明卡片最末 | 以 checklist 形式列出所有前置条件 |
| 社区资料质量参差 | CSDN 旧贴 / 商业推广混杂 | 提供实测验证过的一手结论 |

### 4.5 迁移到其他技术栈

本仓库的方法论不限于鸿蒙，可迁移到任何"AI 训练库滞后 / 官方文档分散 / 社区资料参差"的技术栈：
