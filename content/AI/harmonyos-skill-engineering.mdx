# AI Coding 工程化双范式：Skill 知识库 + Spec 流程规范深度解析

## 一、AI Coding 工程化的两个核心问题

AI 辅助编码正在从"聊天式问答"走向"工程化协作"。但在实际落地中，两个致命问题始终无法回避：

        A1["AI 训练库<br/>截止于某个时间点"] --> A2["新 API / 新框架<br/>AI 不知道"]
        A2 --> A3["生成过时代码<br/>编译失败 / 行为错误"]
    end

    subgraph P2["问题二：流程失控"]
        B1["自然语言需求"] --> B2["AI 直接生成代码"]
        B2 --> B3["跳过需求澄清<br/>跳过方案设计"]
        B3 --> B4["返工率高<br/>无法追溯"]
    end

    style P1 fill:#fff3e0,stroke:#e65100
    style P2 fill:#ffebee,stroke:#c62828
`} />

针对这两个问题，开源社区出现了两类互补的解决方案：

| 范式 | 代表项目 | 核心思路 | 解决什么问题 |
|------|---------|----------|------------|
| **Skill 知识库** | harmony-os-skill | 实战经验结构化为 AI 可消费的知识包 | 知识断层：AI 不知道最新 API 和踩坑经验 |
| **Spec 流程规范** | spec-for-ai | 五阶段白盒工作流管控 AI 输出 | 流程失控：AI 跳过规划直接写代码 |

本文综合解析两种范式的设计原理、实现机制与工程实践，并展示如何融合使用。

## 二、范式一：Skill 知识库（以 harmony-os-skill 为例）

### 2.1 项目定位

HarmonyOS-Skill 是一套从 **三个真实鸿蒙原生 App 开发实战**（潮玩展柜 + 熬夜修仙 + 鲸播 OrcaPlayer，全部已上架应用市场）沉淀出来的 **HarmonyOS NEXT 开发 Skill 集合**，覆盖 ArkUI 状态管理 / 桌面服务卡片 / 视频播放与媒体 / NAS 串流 / IAP / 元服务 / 测试 / 真机打包 / 应用市场上架等核心场景。

截至 2026 年 7 月，仓库已积累 **44 个 skill**，每个 skill 都是"问题场景 + 反模式 + 正确代码模板 + 验证方法"的完整知识包。

核心卖点是 **"AI Coding 友好"**——把踩过的坑、查过的官方文档、试过的方案沉淀成 AI 助手可直接消费的 skill 知识包。

### 2.3 核心设计原理：Frontmatter 语义触发

每个 `SKILL.md` 顶部用 YAML frontmatter 标记元数据，AI 助手靠 `description` 字段做语义匹配判断何时触发：

```yaml
---
name: arkui-observed-objectlink-chain
description: 在编写 ArkUI 鸿蒙代码遇到「修改对象数组里某个元素的属性后 UI 不更新 / 
  build() 跑了但 Image 不刷新 / 杀 App 重启才正常」、或设计列表项数据响应式刷新方案时使用。
---
```

**设计原理**：
- `description` 不写"这是什么"，而是写"**在什么场景下使用、解决什么问题**"
- 埋入 **症状关键词**（"UI 不更新""白底""权限错"），让 AI 做语义检索时命中率最高
- 埋入 **场景关键词**（"首次集成""从 X 迁移""卡在 Y"）

**认知闭环原理**：
1. **触发检测**：让 AI 知道"什么时候该用这个知识"
2. **结论先行**：先给正确答案，避免 AI 试错
3. **反例警示**：展示 AI 容易生成的错误代码 + 根因——传递判断力，而非知识点
4. **正解复现**：给出可直接复制的代码模板
5. **验证闭环**：强调可观测证据（"杀 App 重进正常 vs 运行时变更异常"），杜绝假性修复
6. **知识联网**：交叉引用把同源根因串联

## 三、范式二：Spec 流程规范（以 spec-for-ai 为例）

### 3.1 项目定位

**Spec-Driven AI Coding（规范驱动 AI 开发）标准化工具集**，核心目标解决传统 AI 编码三大致命问题：

1. **上下文丢失**：对话会话重置、历史需求仅存聊天记录，AI 无法长期记忆项目约束
2. **输出不可控**：同需求多次生成代码差异巨大，无统一项目规范约束 AI
3. **无追溯无协作**：团队无法复盘 AI 生成逻辑、变更动机，代码评审缺失"为什么这么写"依据

核心思想：**把需求、行为契约、技术约束、任务清单固化为可版本管理的结构化 Spec 文档，作为 AI 唯一可信输入源，实现"先规范、后编码、可校验、可归档"的白盒 AI 开发流程**。

### 3.3 隔离存储结构

项目初始化 `spec init` 自动生成两套隔离目录，**完全分离业务代码与 AI 规范文档**：

```
项目根目录
├── specs/        # 全局基准规范（Single Source of Truth）
│   ├── api/
│   ├── db/
│   └── frontend/
├── changes/      # 增量变更提案（每个需求一个文件夹）
│   └── add-user-login/
│       ├── proposal.md  # 需求动机、范围（Why）
│       ├── spec/        # Delta 增量行为契约（What）
│       ├── design.md    # 技术方案（How）
│       └── tasks.md     # 任务清单（Step）
├── archive/      # 已完成变更归档
├── .spec-config.yaml    # 全局配置
└── .specignore          # 忽略文件
```

**关键存储机制：Delta Spec（增量规范）**
- 不重写全量系统规范，仅记录本次变更**新增/修改/删除**行为
- 变更完成归档时，引擎自动执行 Diff 合并，增量更新全局 `specs/` 基准库
- 存量老项目友好，无需一次性梳理全部系统行为，支持小迭代逐步完善规范

**五阶段详解**：

1. **Proposal 阶段（需求澄清）**：仅允许讨论需求范围，禁止 AI 输出任何代码。守卫规则在此阶段识别越界行为并拦截。

2. **Spec 行为契约阶段**：生成 Delta Spec，用标准化 GIVEN/WHEN/THEN 描述所有业务场景、边界用例、异常行为。这是后续代码生成和校验的唯一依据。

3. **Design 架构设计阶段**：输出技术选型、组件分层、数据库变更、接口定义、待修改文件清单。核心价值是提前锁定技术方案，避免 AI 自由发挥。

4. **Task 拆解阶段**：把大需求拆分为最小可验证子任务，AI 按任务逐条执行，单任务出错可单独回滚。

5. **Implement & Verify 阶段**：按 Task 清单生成代码，内置 Spec 校验器比对行为是否匹配契约，最后人工确认后归档合并。

### 3.5 边界守卫 GuardRails 实现原理

传统 LLM 天然有"拿到需求直接写代码"的倾向，本项目通过三层硬约束拦截：

1. **阶段状态锁**：每个变更文件夹写入元数据 `.spec-meta.yaml` 标记当前阶段
2. **提示词硬拦截**：内置分层系统提示词，每个阶段绑定专属约束 Prompt
3. **后置规则校验**：AI 输出后引擎正则/语义检测，若检测到代码块直接驳回

### 3.6 底层能力模块

| 模块 | 功能 | 实现要点 |
|------|------|----------|
| Spec 文档引擎 | 模板渲染 + 语法校验 + Delta 合并 | 自定义 Markdown 模板、GIVEN/WHEN/THEN 解析器 |
| LLM 模型抽象层 | 多模型统一封装 + 分层提示词工厂 | 屏蔽 OpenAI/Claude/通义千问 API 差异 |
| AST 解析器 | 提取项目上下文 | 多语言 AST 解析（TS/JS/Python/Java/Go） |
| 代码生成工具链 | 安全文件操作 + Spec 校验 + 回滚 | 自动识别逻辑缺失、接口参数不一致 |

### 3.7 完整执行流程演示

需求示例：新增用户邮箱登录功能

1. `spec propose "新增邮箱密码登录，支持验证码找回密码，不支持第三方登录"`
2. 引擎调用 AST 解析器读取项目现有用户表、登录接口
3. LLM 在 Proposal 阶段守卫约束下生成 `proposal.md`，界定范围
4. 人工确认后进入 Spec 阶段，生成 GIVEN/WHEN/THEN 全场景契约
5. 确认后生成 `design.md`：定义 UserLogin 接口、验证码表、加密工具复用
6. 自动拆分 `tasks.md` 清单（创建接口、数据库迁移、前端登录页、异常拦截）
7. `spec apply` 逐条完成 Task 代码生成
8. `spec verify` 自动校验代码行为是否匹配 Spec，识别遗漏验证码过期逻辑
9. 修复后 `spec archive`——Delta 引擎自动合并登录相关 Spec 到全局基准

## 四、两种范式的对比与融合

### 4.1 核心差异

| 维度 | Skill 知识库（harmony-os-skill） | Spec 流程规范（spec-for-ai） |
|------|-------------------------------|---------------------------|
| **核心问题** | AI 知识断层：不知道最新 API 和踩坑经验 | AI 流程失控：跳过规划直接写代码 |
| **解决思路** | 提供高质量参考知识，让 AI 直接消费 | 定义结构化工作流，管控 AI 输出过程 |
| **交付物** | 44 个独立的 SKILL.md 知识包 | 五阶段 Spec 文档 + 校验规则引擎 |
| **AI 交互方式** | 语义匹配 → 加载 SKILL.md → AI 自行参考 | 阶段守卫 → LLM 调用 → 输出后校验 |
| **护城河** | 知识数量与质量（实战验证过） | 流程严谨性（不可跳过的阶段管控） |
| **适用场景** | 特定技术栈的常见坑（鸿蒙、新框架） | 长期迭代项目需要追溯和协作 |
| **使用成本** | 低（git submodule 一行接入） | 中（需要人工确认每个阶段） |

### 4.2 互补关系

两者不是替代关系，而是解决不同层面的问题：

**融合方式**：在一个项目中同时使用两者——
- `spec-for-ai` 管控开发流程（确保 AI 先规划再编码）
- `harmony-os-skill` 在 AI 编码时提供领域知识参考（确保 AI 知道鸿蒙最新 API 和常见坑）

例如，在 spec-for-ai 的 Implement 阶段，AI 生成鸿蒙代码时会自动去 `.skills/skills/` 中检索是否有相关 skill 可以借鉴，从而同时获得流程规范和领域知识。

### 4.3 共同的设计原则

尽管解决的问题不同，两者在工程化设计上有惊人的相似性：

| 设计原则 | Skill 实现 | Spec 实现 |
|----------|-----------|-----------|
| **结构化存储** | 每个 skill 独立目录 + YAML frontmatter | specs/ + changes/ 隔离目录 + Delta Spec |
| **增量演进** | 小迭代逐步新增 skill，不要求一次性完整 | Delta Spec 记录增量变更，逐步完善系统规范 |
| **版本追踪** | git submodule 管理 skill 版本 | 内置 spec add/commit/log/diff 独立版本命令 |
| **验证闭环** | 每个 skill 包含验证方法（可观测证据） | spec verify 自动校验代码是否匹配 Spec |
| **低接入成本** | git submodule 一行接入 | spec init 一键初始化 |

### 4.4 选择建议

| 团队类型 | 推荐方案 | 理由 |
|----------|----------|------|
| 新框架/新 SDK 开发者 | Skill 知识库 | 知识断层是最大瓶颈，快速积累踩坑经验 |
| 长期迭代商业项目 | Spec 流程规范 | 需要追溯、协作、质量管控 |
| 两者兼有 | 融合使用 | Spec 管控流程，Skill 提供领域知识 |
| 小型一次性 Demo | 都不需要 | 规范编写成本超过收益 |

## 五、可复用的工程化方法论

### 5.1 核心公式

```
AI Coding 工程化 = 流程规范（Spec）× 领域知识（Skill）
```

两者相乘而非相加——缺少任一个，另一个的效果都会大打折扣。

### 5.2 Skill 编写判断标准

- 同一个坑你或 AI 踩过 ≥ 2 次
- 官方文档把关键约束藏在不起眼处
- AI 默认生成的代码是错的（训练库过时）

### 5.3 通用模板

```markdown
---
name: <tech>-<module>-<problem-slug>
description: <技术栈> <模块> <问题> — 在遇到<症状关键词>/<报错码>时使用。
---

## 何时使用此 skill
<列出触发条件>

## 核心结论
<一句话正确答案>

## 反例 ❌
<错误代码 + 根因>

## 正确做法 ✅
<可复制代码模板>

## 验证方法（必做）
<可观测证据>

## 相关 skill
<交叉引用>

## 参考资料
<官方文档链接>
```

### 5.4 六条核心原则

1. **粒度精准**：一个 skill 解一个坑，不写大而全
2. **结构固定**：六段式模板保证质量下限与 AI 消费一致性
3. **反例驱动**：用"AI 会犯的错"反向定义正确方案，传递判断力
4. **验证闭环**：强调可观测证据，杜绝假性修复
5. **语义触发**：Frontmatter description 用"场景 + 症状"语言，让 AI 零配置自动检索
6. **增量演进**：不要求一次完整，小步迭代逐步完善

AI Coding 正在从"聊天式问答"走向"工程化协作"。这个转变需要两样东西：**知识**（AI 不知道的，我们告诉它）和 **流程**（AI 容易跳过的，我们约束它）。

- **harmony-os-skill** 示范了如何把实战经验结构化为 AI 可消费的知识包
- **spec-for-ai** 示范了如何用五阶段工作流和阶段守卫管控 AI 输出过程

两者不是竞争关系，而是 AI Coding 工程化的两个必要支柱。当一个项目同时拥有结构化的领域知识和规范化的开发流程时，AI 辅助编码才能真正从"玩具"走向"生产力工具"。
