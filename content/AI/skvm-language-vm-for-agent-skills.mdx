## 1. 问题：技能不应因切换模型而断裂

<MermaidDiagram chart={`mindmap
  root((Agent 技能移植困境))
    碎裂["技能碎裂"]
      skill1["同一技能在不同模型上行为不一致"]
      manual["N技能 × M模型 = N×M 手动适配"]
      version["模型版本更新使提示词失效"]
    效率["效率低下"]
      static["静态提示词无法从执行中学习"]
      no_cache["重复代码模式无法缓存"]
      no_feedback["没有从生产运行到技能优化的反馈回路"]
    成本["成本爆炸"]
      token["每次调用都消耗完整上下文 Token"]
      brittle["脆弱的提示词需要大量试错调优"]
`}/>

LLM Agent 越来越多地将**技能（Skill）**作为可复用的组合单元。然而，当前系统把技能当作原始上下文处理，导致：

| 困境 | 根因 | 后果 |
|------|------|------|
| 技能跨模型断裂 | 不同模型能力差异巨大 | 同一技能在强模型可用、弱模型失效 |
| 手动调优不可扩展 | N × M 组合爆炸 | 每次模型更新都需重写提示词 |
| 没有运行时学习 | 提示词是静态文本 | 重复代码模式不缓存，无反馈循环 |

**SkVM 的核心洞察**：借鉴传统编译器和虚拟机设计——把技能当作**源代码**，把 LLM 当作**异构处理器**，用编译和运行时技术实现"一次编写，到处高效运行"。

每个原语可在三个难度级别测试：

| 级别 | 含义 | 测试策略 |
|------|------|---------|
| L3 | 完全胜任——处理复杂实例 | 先测 L3，通过则 L2/L1 免测 |
| L2 | 中等胜任——处理标准实例 | L3 失败后测试 L2 |
| L1 | 基本胜任——处理简单实例 | L2 失败后测试 L1 |
| L0 | 无能力——连简单实例也失败 | L1 也失败 |

这种**渐进式测试**策略最小化 API 调用成本：如果一个模型通过了 L3，就不再测试 L2 和 L1。

### 3.2 TCP（目标能力画像）

TCP 是对模型+框架组合的能力画像，存储为 JSON：

```json
{
  "gen.code.write": { "level": 2, "scores": { "L3": 0.33, "L2": 0.83 } },
  "tool.file.read":  { "level": 3, "scores": { "L3": 1.0 } },
  "reason.plan":     { "level": 1, "scores": { "L3": 0.0, "L2": 0.17, "L1": 0.67 } }
}
```

关键理解：**TCP 是 per-(model, adapter) 的**——同一个模型在不同 Agent 框架下能力表现不同，因为框架提供的工具、格式约束、系统提示都不同。

### 3.3 SCR（技能能力需求）

SCR 描述技能需要什么原语能力、以及在什么级别上需要。它由编译器 Pass 1 从 `SKILL.md` 自动提取，并可包含**替代实现路径**：

    SCR --> REQ1["主路径需求<br/>gen.code.edit: L2"]
    SCR --> REQ2["替代路径需求<br/>gen.code.write: L3<br/>(如果 edit 不可用)"]
    SCR --> REQ3["工具需求<br/>tool.file.read: L2<br/>tool.exec: L1"]

**核心洞察**：TCP 和 SCR 之间的缺口决定了需要什么编译变换——没有缺口意味着技能可以原样运行。

### 4.1 Pass 1：能力缺口分析

Pass 1 是编译器的核心——它解决"这个技能在这个模型上能不能跑"的问题：

| 缺口类型 | 条件 | 策略 |
|----------|------|------|
| 硬缺口 (L0) | 模型完全不具备该能力 | **替换**：使用替代原语路径 |
| 弱缺口 | 模型具备但低于需求级别 | **补偿**：添加脚手架、示例、分解步骤 |
| 无缺口 | 模型能力满足需求 | **不变换** |

示例：一个技能要求 `gen.code.edit: L2`，但目标模型只有 `L1`。编译器会补偿——添加更多示例、将编辑操作分解为读-写两步、增加格式约束提示。

### 4.2 Pass 2：环境绑定

Pass 2 把技能从"通用描述"变成"可运行包"：

```bash
# 自动生成的幂等安装脚本示例
#!/bin/bash
set -e
pip install --quiet requests  # 技能依赖的 Python 包
curl -sL https://example.com/tool -o /usr/local/bin/tool  # 二进制工具
chmod +x /usr/local/bin/tool
```

这意味着 AOT 输出不仅是"给模型更好的指令"，还是一个**自包含的可部署技能包**。

### 4.3 Pass 3：并发提取

Pass 3 分析技能的工作流结构，识别并行执行机会：

| 并行类型 | 全称 | 示例 |
|----------|------|------|
| DLP | 数据级并行 | 同时处理多个独立文件 |
| ILP | 指令级并行 | 流水线化独立步骤 |
| TLP | 任务级并行 | 并发执行独立子任务 |

**三遍顺序有意义**：Pass 1 改变技能"做什么"，Pass 2 改变"需要什么环境"，Pass 3 改变"如何调度"。乱序会使后续分析基于过时假设。

## 5. 运行时优化

### 5.1 JIT-Boost（代码加固）

<MermaidDiagram chart={`flowchart TD
    SCAN["扫描技能包<br/>headless agent 分析全文"]
    SCAN --> CANDIDATES["生成 boost-candidates.json<br/>代码签名/关键词/参数模板"]
    
    EXEC["运行时执行技能"]
    EXEC --> HOOK["运行时钩子<br/>监控 LLM 调用"]
    HOOK --> MATCH{"匹配已知签名?"}
    MATCH -->|"否"| LLM["调用 LLM<br/>正常路径"]
    MATCH -->|"是: 连续 N 次"| PROMOTE
    
    CANDIDATES --> PROMOTE["加固模式提升"]
    PROMOTE --> BYPASS["绕过 LLM<br/>直接执行模板<br/>零 LLM 调用"]
    BYPASS --> SUCCESS{"执行成功?"}
    SUCCESS -->|"是"| FAST["加速完成"]
    SUCCESS -->|"否"| DEMOTE["降级回 LLM 调用<br/>自动回退"]
    LLM --> NORMAL["正常完成"]

    style SCAN fill:#e1f5fe
    style BYPASS fill:#c8e6c9
    style DEMOTE fill:#fff9c4
`}/>

JIT-Boost 的核心思想是**代码加固（Code Solidification）**——类似于 JVM 的 JIT 编译将热点字节码编译为本地机器码。当一个代码模式被 LLM 连续重复执行多次后，SkVM 将其"加固"为直接执行的模板，绕过 LLM 调用：

- **零 LLM 调用**：已加固的模式在运行时完全绕过 LLM
- **自动降级**：加固失败时自动回退到 LLM 调用
- **模型无关**：加固状态按技能存储，与具体模型无关

实测效果：**19-50x 延迟降低**（对于重复性操作模式）。

JIT-Optimize 是**提案驱动的编辑循环**，不是原地突变。三种证据来源：

| 来源 | 参数 | 说明 |
|------|------|------|
| `synthetic` | `--task-source=synthetic` | 合成任务，自闭环 |
| `real` | `--task-source=real` | 使用基准测试任务 |
| `log` | `--task-source=log` | 从已有会话日志分析，不重跑 |

### 6.2 Agent 适配器体系

SkVM 通过 `AgentAdapter` 接口支持多种 Agent 框架：

| 适配器 | 框架 | 说明 |
|--------|------|------|
| `bare-agent` | 内置 | 最小 Agent 循环，5 个工具，用于画像和测试 |
| `opencode` | OpenCode CLI | 解析 NDJSON 事件流 |
| `openclaw` | OpenClaw CLI | 管理临时 Agent 实例 |
| `hermes` | Hermes CLI | 保留完整 token 和成本元数据 |
| `jiuwenclaw` | Jiuwenclaw CLI | JSON-RPC 通信 |

适配器配置模式：
- **managed**：SkVM 在沙箱中创建新的最小配置（如新 openclaw agent），干净基线，不依赖宿主状态
- **native**：SkVM 克隆用户现有框架配置（如 `~/.openclaw/agents/<name>`），需要本地已配置

## 8. 实践指南

```bash
# Step 1: 画像目标模型能力
skvm profile \
  --model=openrouter/qwen/qwen3.5-35b-a3b

# Step 2: AOT 编译技能
skvm aot-compile \
  --skill=path/to/skill-dir \
  --model=openrouter/qwen/qwen3.5-35b-a3b \
  --adapter=bare-agent \
  --pass=1,2,3

# Step 3a: 合成任务自调优
skvm jit-optimize \
  --skill=path/to/skill-dir \
  --task-source=synthetic \
  --optimizer-model=openrouter/anthropic/claude-sonnet-4.6 \
  --target-model=openrouter/qwen/qwen3.5-35b-a3b

# Step 3b: 或从已有日志优化
skvm jit-optimize \
  --skill=path/to/skill-dir \
  --task-source=log \
  --logs=path/to/session.jsonl \
  --optimizer-model=openrouter/anthropic/claude-sonnet-4.6

# Step 4: 评测
skvm bench --model=openrouter/qwen/qwen3.5-35b-a3b

# Step 5: 审查 & 部署
skvm proposals list
skvm proposals serve      # Web 审查界面
skvm proposals accept <id>
```

### 10.2 局限与挑战

| 挑战 | 说明 |
|------|------|
| 画像成本 | 26 原语全量画像约 20 分钟，但有缓存和预构建画像 |
| 编译器质量 | SCR 提取依赖 LLM，可能遗漏需求 |
| JIT-Boost 依赖模式频率 | 只有重复出现的代码模式才能被加固 |
| 适配器覆盖 | 目前支持 5 种框架，更多框架需自行实现适配器 |
| 评估噪声 | LLM 输出的随机性需要多轮运行平均 |

### 10.3 未来方向

1. **更多原语和更细粒度画像**：从 26 原语扩展到更细的能力维度
2. **跨技能优化**：多个技能组合时的全局优化
3. **增量画像**：模型更新后只重测变化的原语
4. **更多 Agent 框架支持**：扩展适配器生态
5. **自适应编译**：运行时根据实际表现动态调优编译策略

## 11. 总结

SkVM 是 LLM Agent 技能可移植性领域的里程碑式工作。它借鉴传统编译器和虚拟机的设计智慧，创造性地解决了"同一技能在不同模型上行为不一致"这一核心问题：

- **26 原语画像**：将模糊的"模型能力"量化为可测量的 TCP
- **三遍 AOT 编译**：从能力缺口分析到环境绑定到并发提取，系统性适配
- **JIT 加固**：重复模式绕过 LLM，19-50x 延迟降低
- **JIT 优化**：提案驱动的技能改写，越弱的模型提升越大
- **40% Token 降低**：通过分层加载和加固减少无效调用

SkVM 证明了一个深刻洞察：**LLM Agent 的技能可移植性问题，本质上是一个编译器问题**。
