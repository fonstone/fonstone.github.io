> 内核 Agent 的技术栈核心是可复现验证环，不是模型本身。这篇以论文、LKML 邮件和内核文档为底稿，把技术栈、应用和社区政策摆在一起，数字都标得出来源。

## 一、先看内核特殊在哪

Syzbot 是 Google 维护的内核自动模糊测试服务。RGym 论文引用它的数据，Linux 内核这边已修复的 bug 超过 6500 个，待处理的超过 1500 个。fuzz 发现 bug 的速度早就超过人修 bug 的速度。2026 年，一批 agent 系统把目标对准这个 backlog，从修崩溃、给 syzkaller 生成规格、定位故障，到直接在 LKML 上做补丁评审。写这篇之前，我把内核 Agent 的论文、LKML 邮件和内核文档逐条对过一遍，论文和社区里自报的数字会单独标注。

仓库里已有一篇讲 LLM 辅助内核开发一般情况的文章，这篇聚焦 agent 化之后的系统、基准和社区政策，两篇可以对着读。

## 二、技术栈原理

内核 Agent 的技术栈可以拆成四块，可复现验证环、上下文工程、agent 编排、评测基准。前两块是内核区别于通用软件工程的地方。

### 1. 可复现验证环

哥伦比亚大学和 Google 合作的 kGym 平台把内核 bug 修复包装成三个动作，编译内核版本、给有 bug 的内核打补丁、跑崩溃复现程序。agent 只是这套平台的用户，模型想出一个补丁，平台负责验证它到底修没修好。

kAgent 在 kGym 之上复刻了内核开发者的排查循环。看执行日志，生成基于执行的假设，合成候选补丁，跑完整构建和复现程序，迭代修正。论文把配套工具叫 kGym++，三个瓶颈点得很具体。

- 上下文压力。一个崩溃日志可能几千行。
- 迭代延迟。一次全量内核构建以分钟计。
- 日志噪声。sanitizer 输出里大部分信号无用。

kGym++ 的解法是对象缓存 kCache，只重编被修改的文件，论文报告内核构建时间平均缩短 42.69%。

![可复现验证环](/images/kernel-agent/verify-loop.png)

KernelGPT 的验证反馈更轻。它生成 syzkaller 规格后，用 syz-extract 和 syz-generate 的报错信息定位不准确的描述，让 LLM 照着错误修。Live-kBench 评测补丁时崩溃不确定，连跑 25 次复现确认补丁真的消除了崩溃。三套系统殊途同归，agent 的每次修改都要过一遍可复现的执行证据。

### 2. 上下文工程

内核的规模是通用软件工程基准的几十倍。Linux v5.8 有超过 6.9 万个文件、2800 万行代码，LinuxFLBench 论文说它的规模是 SWE-bench 最大项目的 30 倍以上。内核 bug 没有自然语言报告，上下文只能从源码和运行时痕迹里挖。

KernelGPT 的切入点是 syscall 规格。它先定位 syscall 的 handler 函数，从内核源码里取出相关类型定义喂给 LLM，生成 syzkaller 描述。遇到嵌套类型就标记为未知，下一轮再分析。作者的洞见是，LLM 预训练阶段见过海量内核代码和文档，规格生成需要的知识已经在那里面，剩下的是把它引导出来。生成与校验的循环见图，报错直接送回模型改。

![KernelGPT 规格生成与校验流程](/images/kernel-agent/kernelgpt-flow.png)

SyzGPT 把检索做成了依赖驱动。它先用 LLM 从文档里提取 syscall 之间的依赖关系，再按依赖检索代码生成种子，论文报告种子有效率 87.84%。

kAgent 的上下文来自执行。它从崩溃痕迹和选择性追踪里提取高信号函数调用子集，压缩成能推理的执行日志，再基于执行生成假设。日志噪声这条瓶颈，正是选择性追踪要解决的对象。

内核仓库自己也在给 agent 准备上下文。Sasha Levin 的 RFC 补丁把各家的 AI 助手配置统一成符号链接，指向一份 Documentation/AI/main.md。

### 3. Agent 编排与角色

kAgent 是 workflow-based agent，编排顺序按内核开发者排查崩溃的习惯来，看日志、假设、补丁、复现、修正。论文对每一步做了消融，证明每个环节都贡献分数。

RGym 用两个 agent 配合。Function Exploration Agent 自主看代码，形成自己对根因的理解，Simple Agent 按 bug 类型用调用栈定位直接出补丁，两者共用 GPT-4o 基线。两个 agent 单独通过率都是 15.38%，组合到 30%，其中 12 个只有探索 agent 能解，说明不同策略能互补。分工见图。

![RGym 双 agent 分工](/images/kernel-agent/rgym-orchestration.png)

编排解决不了的问题在定位。定位是决定修复成败的前置环节，多文件崩溃尤其吃这一环，细节见应用一节。

### 4. 评测与污染

内核 Agent 的评测基准这几年立了一批。kBenchSyz 来自 kGym 平台，LinuxFLBench 有 250 个真实故障定位任务，RGym 从 6088 个 syzbot bug 里筛出 143 个可复现的 KASAN bug，Live-kBench 首批 534 个内核 bug。

| 基准 | 构成 | 我核到的数字 |
| --- | --- | --- |
| kBenchSyz | 真实 syzbot 崩溃，构建加复现平台 | kAgent 无定位修复率 54.5% |
| LinuxFLBench | 250 个真实内核故障定位任务 | 最好 agent 文件级 top-1 41.6% |
| RGym | 6088 个 syzbot bug 筛出的 143 个 KASAN bug | 两 agent 组合通过率 30% |
| Live-kBench | 首批 534 个内核 bug，每周从 syzbot 抓取 | 知识截止前 bug 高约 25% |

基准数字要先分清子集。RGym 的 143 个要求同时有修复提交、复现程序、崩溃报告和内核配置，还必须在修复提交的父版本上复现。筛选本身就排掉了大部分 backlog。

Live-kBench 发现了一个更尖锐的问题。模型在知识截止前见过的 bug 上表现好得多，等效补丁率高约 25%，静态基准因此会高估 agent 处理新鲜 bug 的能力。它靠每周从 syzbot 抓新 bug 对冲，bug 筛选用 5 次复现尝试，补丁评测跑 25 次复现。这些细节决定数字能不能信。筛选链和污染对冲画在一起。

![评测数据筛选与污染对冲](/images/kernel-agent/benchmark-filter.png)

## 三、典型应用

### 1. 崩溃修复

fuzz backlog 的消化是第一个场景。kAgent 在 kBenchSyz 上报告，无定位信息时能修复约 54.5% 的崩溃，给正确文件提示能到 65%。RGym 组合通过率 30%。数字看着不高，对照的是真实 backlog 里连复现都要手工的崩溃。

单文件和多文件的差距是共同洼地。kAgent 非 oracle 设置下，单文件崩溃修复 142 个里成 60.16%，多文件 43 个里只成 23.25%。崩溃跨多个文件时，上下文和定位都开始失灵。

这些修复率直接影响维护者 backlog 的消化速度。kAgent 和 RGym 的补丁还要过 maintainer 的评审才能进树，agent 产出的是候选，不是成品。

### 2. 模糊测试增强

KernelGPT 给 3903 个 syzkaller 已有 syscall 之外新增了 532 个规格，占 13.6%，还有 294 个新类型，总成本 34 美元。论文报告它目前发现 24 个新 bug，12 个已修，11 个分配了 CVE，生成的规格已经被合并进 syzkaller，是开发团队主动要的。

SyzGPT 面向低频 syscall，对比 7 个主流 fuzzer，平均覆盖率提升 17.73%，低频 syscall 覆盖率提升 58%，漏洞发现提升 323.22%，独立发现 26 个未知 bug，11 个被确认。这些数字都是论文自报。

这条线的价值在于让 fuzzer 更准，不是更快。规格和种子决定 syscall 序列能走多远，补上缺失的规格，等于给整个 fuzzing 战线扩了地。

### 3. 故障定位

故障定位是内核 Agent 最弱的环节，也是研究最集中的环节。LinuxFLBench 的结论，现存 agent 文件级 top-1 只能到 36.8% 到 41.6%，比它们在 SWE-bench 上的表现掉 16.7% 到 31.9%。定位失败，通常卡在抓不到相关文件和覆盖不了完整根因。

并集视角更说明问题。LinuxFLBench 把几个主流 agent 的定位结果并起来，250 个 bug 里只有 146 个能被成功定位，召回 58.4%。每个 agent 都能独解一部分，说明策略互补，也说明没有一个接近完整。

LinuxFL+ 是这套基准顺出来的补法，用工具化引导帮 agent 检索相关文件，论文报告把各 agent 的定位准确率普遍提升 7.2% 到 11.2%。方向很明确，补定位比换模型更划算。

### 4. 社区真实落地

内核社区是最早把 LLM 用进流程的组织之一。2025 年 7 月，Sasha Levin 给内核仓库提交 RFC 补丁，加统一 AI 助手配置，CLAUDE.md、.cursorrules、copilot-instructions 等七个文件做成符号链接，指向 Documentation/AI/main.md，八处文件、78 行新增。规则里写内核编码规范、开发流程、署名和许可证，示例署名用 `Co-developed-by: Claude claude-opus-4-20250514`。

补丁评审是跑得最前的场景。Sashiko 这个 LLM 评审 bot 跑在 linux-kernel 主列表加 47 个相关列表上，输出概率性，大补丁质量下降，还会被 commit log 带偏。Torvalds 在 2025 年底维护者峰会上说，LLM 目前主要用在识别 CVE 候选、stable 回移候选和补丁评审，他举了 Andrew Morton 的例子，一份机器评审的补丁把他想提的问题全找到，还多找了几条，他评价说 stunning。

stable 回移也在用。Sasha Levin 的 AUTOSEL 补丁说明里开始出现 LLM 生成的回移解释，开头直接标注 LLM Generated explanations, may be completely bogus。

Torvalds 的态度 2026 年变得很明确。5 月他在 7.1-rc4 邮件里警告，AI 检测 bug 的报告把安全列表淹了，重复太多，想加价值的人要别只报重复问题，在 AI 成果之上再添真实价值。7 月中旬他在 linux-media 列表上直接说，Linux 不是反 AI 的项目，有意见的人可以 fork。8 月他在 7.2-rc7 邮件里写，这个周期的新常态是大量修复，其中很多来自各种 AI 工具的评审。

政策在同步收紧。2025 年底维护者峰会的共识四条。

- 人要对补丁负责。
- 纯机器生成的补丁不受欢迎。
- 维护者保留接受或拒绝权。
- 工具使用要披露。

Greg Kroah-Hartman 在 2026 年 8 月给 staging 子系统定了更严的规矩，LLM 生成的 staging 补丁一律拒收，除非是真实安全修复且必须在真实硬件上测试过。他说哪怕最好的工具，结果里至少三分之一是错的或有害的。政策推进的时间线见图。

## 四、边界与结论

把论文数字和社区政策放一起看，内核 Agent 的边界由验证环和社区政策共同划定。验证环把多文件修复挡在 23% 上下，静态基准把真实能力高估 25%，社区政策把纯机器补丁挡在合并线外。

数据影响谁。崩溃修复率决定内核维护者 backlog 的消化速度，KernelGPT 找到的 24 个 bug 影响跑那些驱动的设备用户，Sashiko 影响每个往 LKML 投稿的贡献者，staging 政策影响想拿内核练手的初学者。

## 结语

Torvalds 在 2026 年 7 月那句可以收尾。Linux 不是反 AI 的项目。但内核仓库对机器补丁的规定写得和代码一样清楚，署名、硬件测试、维护者决定权，一条都不含糊。机器发现、机器评审、人署名、人合并，这条分工在 2026 年已经写进了内核自己的文档和邮件列表。
