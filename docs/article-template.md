# 技术科普长文结构模板

本文档管结构、蓝图、逐节写法、具体实践和标题。材料关、证据层级、语言禁令和审稿见 `docs/writing-guide.md`。讲解手法和类比库见 `docs/explanation-patterns.md`。

短文章（1200 字以下）可以只用写作指南。长文先按本文档搭骨架，再按写作指南过材料关和终审。

## 一、六段结构

六段是内容结构，不是正文标题。正文标题从每节内容里长出来，带编号，概括这一节的结论或问题。

| 段 | 任务 | 写法 | 读者得到什么 |
|---|---|---|---|
| 1 开场 | 抓住读者，交代主题 | 一个具体场景、问题或反差，先概念后数字 | 知道文章在讲什么，为什么值得读 |
| 2 原理与类比 | 讲清核心机制 | 一句话结论，机制图或公式，一个主类比，映射加边界 | 建立直觉，知道关键约束 |
| 3 痛点 | 写上一代方案的具体缺口 | 症状、账本、谁受影响，缺口和解法一一对应 | 知道为什么需要新方案 |
| 4 解法 | 这一代怎么补 | 每个解法写缺口、动作、收益、新代价 | 知道方案怎么工作，代价是什么 |
| 5 具体实践 | 让读者能上手 | 代码、配置、参数、步骤、排错、验证 | 能复现，或直接用到自己的系统 |
| 6 收口 | 给判断尺子 | 适用边界、代价、落地提醒 | 能带走一个判断 |

第四段是文章的主体。一个解法一节，每节只回答一个问题。节与节之间靠因果推进，不靠“首先、其次、最后”排队。

## 二、蓝图

蓝图是内部工作文件，不进成稿。动笔前把它填完，P2 之后冻结论点。要改论点，回到这里重画问题链。

### 2.1 一句话论点

用一句话说清这篇文章要让读者接受什么判断。比如“这项技术把缓存压小，瓶颈从算力转到带宽，后面的优化围绕访存展开”。

论点必须能用正文里的证据支撑，不能是口号。

### 2.2 问题链

每一节回答上一节留下的问题。把这条链写成表，写不出来就说明结构还没想清。

| 节 | 读者带着什么问题进来 | 这一节回答什么 | 留下什么新问题 | 证据 ID |
|---|---|---|---|---|
| 开场 | 这篇文章和我有什么关系 | 一个具体场景和全文论点 | 为什么会这样 | E1 |
| 原理 | 它怎么工作 | 核心机制和关键约束 | 上一代卡在哪 | E2 |
| 痛点 | 上一代为什么不够 | 具体失败和账本 | 这一代怎么补 | E3 |
| 解法一 | 这一代怎么补 | 缺口、动作、收益、代价 | 还剩什么问题 | E4 |
| 解法二 | 还剩什么问题 | 缺口、动作、收益、代价 | 还有什么没解决 | E5 |
| 实践 | 我怎么用到自己的系统 | 代码、配置、验证 | 什么时候不该用 | E6 |
| 收口 | 什么时候不该用 | 边界和尺子 | 无 | E7 |

### 2.3 痛点解法映射

痛点有几个，解法就配几个。多一个或少一个，读者都会觉得断裂。

| 痛点 | 证据 ID | 对应解法 | 收益 | 新代价 |
|---|---|---|---|---|
| 显存装不下 | E3 | GQA/MLA | KV 从 320GB 降到 40GB | 质量要验，kernel 要改 |
| 单步读得慢 | E4 | FlashAttention/FlashDecoding | 少跑几趟 HBM | kernel 要按硬件选 |
| 碎片多 | E5 | PagedAttention | 吞吐 2 到 4 倍 | 块大小要调 |
| 长上下文算不完 | E6 | NSA/DSA | 64K 下 9 到 11.6 倍 | 要预训练，kernel 专用 |

### 2.4 实践件

实践必须和原理里的量对上。代码算的，就是前面那个 40GB；配置改的，就是前面那个 KV 头数。

| 原理里的量 | 实践怎么算或怎么改 | 预期结果 | 失败时先查什么 |
|---|---|---|---|
| 每 token KV 字节数 | 读 config，套公式 | 320KB | `num_key_value_heads` 是否读对 |
| 128K KV 总量 | 乘序列长度 | 40GB | 是否把每层数当总量 |
| 一步 decode 读取量 | 乘带宽，算下界 | 约 21.5ms | 带宽是否换成自己的卡 |

### 2.5 类比地图

一篇长文只立一条主线。每个类比给映射和边界，删掉类比后机制段仍然成立。具体写法和类比库见 `docs/explanation-patterns.md`。

| 节 | 生活场景 | 映射 | 边界 |
|---|---|---|---|
| 原理 | 图书馆写长文 | 书库是 HBM，书桌是 SRAM，参考书是 KV | 不解释 Tensor Core 和 softmax |
| 解法一 | 合订本 | MQA/GQA/MLA 压 KV | 不解释质量怎么学出来 |
| 解法二 | 一次搬一摞书 | FlashAttention 分块 | 不解释 kernel 调度 |
| 解法三 | 按页借书 | PagedAttention 分页 | 不减少书的页数 |
| 解法四 | 先看目录再精读 | NSA 三分支 | 选择是块级、可学习的 |

### 2.6 图表地图

每张图回答一个问题。图前有引导句，图后有解释。节点名和正文术语对得上。

| 节 | 图类型 | 图回答什么问题 | 节点和边 | 图后解释 |
|---|---|---|---|---|
| 原理 | 流程图 | 数据从哪来、到哪去 | 输入、量化、打包、kernel | 哪一步在离线，哪一步在线上 |
| 解法 | 架构图 | 各模块怎么配合 | 模块、依赖、数据流 | 哪个模块是瓶颈 |
| 实践 | 时序图 | 一次调用怎么走 | 请求、调度、计算、返回 | 哪一段是等待 |

### 2.7 证据映射

每个关键声明都要能指到证据 ID。指不到的声明，在蓝图阶段删掉或降级。

| 节 | 用到的证据 ID | 支撑什么声明 |
|---|---|---|
| 原理 | E2 | KV 公式和容量账 |
| 痛点 | E3 | 碎片和吞吐数字 |
| 解法 | E4 | 方法的机制和收益 |
| 实践 | E5 | 代码和验收指标 |

### 2.8 冻结

蓝图填完，停一下。检查三件事。

1. 一句话论点能不能被正文证据支撑。
2. 问题链有没有断点，每一节是否回答上一节留下的问题。
3. 痛点解法映射是否一一对应，实践件是否和原理里的量对上。

三件事都过，冻结论点，进初稿。后面要改论点，回到 P2 重画，不在初稿里偷偷换题。

## 三、逐节写法

### 1 开场

先给一个具体场景，场景里带出主题和核心概念。也可以先用一句话点题，再进场景。第一段尽量有主语和动作，读者才知道谁在做什么。

先说清对象是什么、规模多大、关键差异在哪，再说它卡在哪。参数挂在因果上，不裸列。

场景可以是部署现场、一次报错、一个显存账本、一个用户问题。数字放在概念之后，为解释服务。不要一上来堆一串数字，也不要用一个孤零零的数字当第一段。

公众号长文常用“角色 + 数字 + 后果”开场。比如“你拿到一张 80GB 卡，想把 70B 模型塞进去。权重 35GB，KV 40GB，batch 只能停在 1。上线后每 token 延迟被 KV 读取拖到几十毫秒。”读者先看到一个具体的人和一个具体的后果，再听机制。

开头用了类比，就在第三段前后补一句边界。开头承诺的问题，正文必须接住。

### 2 原理与类比

先把机制讲清楚，再上类比。顺序不能反。

原理段至少做四件事。

- 给一句话结论。读者读完这一段，能用一句话说出它怎么工作。
- 给一个位置。它在系统里接在谁前面、接在谁后面，上下游的边界在哪。
- 给关键约束。哪个资源有限，哪个步骤不能省，哪个假设会失效。
- 给一个可核验的量。公式、参数、带宽、延迟、显存，至少有一个，让读者能自己算。

数字要换算。总时延除以层数，总显存除以 token 数，带宽乘时间，把数字变成读者能感知的预算。换算本身改变理解。

类比段做三件事。

- 给映射。生活对象对应哪个技术对象，动作对应哪个机制。
- 给边界。这个类比不解释什么，防止读者推过头。
- 回到技术本体。类比之后马上接机制，不能比喻完就走。

具体写法和类比库见 `docs/explanation-patterns.md`。

### 3 痛点

痛点要具体。写清上一代方案在什么条件下失效，谁多花了时间，谁多付了钱，哪条路径被堵住。

痛点数量和解法数量一致，通常三到四个。每条有来源。痛点要和后文的解法一一对应。开头讲显存装不下，后文不能全讲调度；开头讲长上下文算不完，后文不能只讲显存碎片。

没有真实案例，就用有来源的失效模式，不编“很多团队都踩过这个坑”。不写“你有没有遇到过”这类泛化提问。

### 4 解法

每个解法小节固定五步。

- 钩子。一个具体动作、数字，或者一个失败场景。
- 原理。技术怎么做的，关键约束是什么。
- 类比。给映射，也给边界。主类比已经覆盖的，不重复。
- 收益。带数字，或者带可核验的对比。写清基线、条件、适用规模。
- 代价。牺牲了什么，换 shape、换版本、换负载时会不会失效。

每个解法都要回答上一节留下的问题，写完再留下一个问题给下一节。没有上一代的失败，就不要写“某某提出了”。

### 5 具体实践

这是技术科普和论文摘要的分界线。读者要能拿着这一段去试。

实践可以是一段可运行的代码、一份真实配置、一组参数选择、一套排查步骤，或者一个验证方案。至少给一种。

写实践时守住四条。

- 代码要能跑。给输入、输出和依赖，不写伪代码冒充代码。
- 配置要真。参数名、所在文件、改变什么，写清楚。
- 步骤要有预期结果。每一步做完，读者应该看到什么；看不到时，先查哪里。
- 验证要可复现。同一模型、同一精度、同一 batch、同一序列长度分布，先 warm up，再测 p50 和 p99。

实践必须和前面的原理对上。代码算出来的数，要能解释前面那个 40GB 是怎么来的；配置改的那个参数，要能对应前面说的 KV 头数。

实践段最好给三样东西。

1. 一段能跑的代码或一份真配置。
2. 一张验收指标表，写清看什么、怎么量、什么算好。
3. 一张常见坑表，写清症状和正确做法。

### 6 收口

结尾给一把尺子，再给一条落地提醒。

收口标题要概括这篇文章的判断或边界，写成名词性结论，不用“先看”“先算”“先问”这类操作指令，也不写“回到某个类比”“结语”“总结”。类比可以在正文里回扣，标题不承担回扣。

尺子要能迁移到别的优化点，比如“先算每 token 的 KV 字节数，再算一步 decode 的读取量，最后看长上下文下注意力占多少时间”。落地提醒要具体，比如“拿自己的序列长度分布、batch、KV 头数和精度重跑一遍”。

结尾不重新摘要全文，不升华。最后一段删掉再读，如果文章更有力，就让文章提前结束。

### 图表

技术长文至少配一张 Mermaid 图。原理图、架构图、流程图、时序图，选一种最能降低理解成本的。图前有引导句，图后有解释。图不是装饰，表不是目录。删掉图后正文仍然成立。

## 四、解法小节模板

```md
## 第几类技术，补哪个缺口

这一节只回答一个问题，读者带着什么疑问进来。

钩子。一个具体动作、数字或失败场景。

原理。技术怎么做的，关键约束是什么。

收益。带数字或可核验的对比，写清基线和条件。

代价。牺牲了什么，换 shape、换版本、换负载时会不会失效。

**一句过渡。上一笔账压下来了，但还剩什么问题。**
```

如果主类比在这一节还成立，就补一句映射和边界。主类比不适用，不要硬套，直接讲机制。

## 五、标题规则

标题从内容里长出来，带编号，概括这一节的结论或问题。下面这些写法可用。

- `一、一步 decode，时间花在哪`
- `二、四笔账，128K 到底贵在哪`
- `三、四类技术，各管一笔账`
- `四、你的模型到底要多少 KV`
- `五、回到图书馆，带走一把尺子`

不要用这些写法。

- `一、原理`
- `二、痛点`
- `三、解法`
- `四、具体实践`
- `五、收口`

标题要能让读者只看目录就知道这一节会回答什么。标题里可以带数字、对象、动作或问题，不要只放抽象名词。

收口标题单独一条。它要概括全文的判断或边界，写成名词性结论，比如“四笔账，一条选型线”“三层十一格的代价账本”“推理优化的重心转向搬运和状态”。不写“回到搬家”“回到图书馆”“结语”“总结”，也不用“先看”“先算”“先问”这类操作指令。

## 六、风格参照

学公众号长文的五个动作。

1. 开头给一个具体场景，带角色、数字和后果。
2. 全文先给一句话论点，再给一个短大纲。
3. 小节标题用带编号的结论句或问题。
4. 关键判断加粗，一段只留一个重点。
5. 实践段给坑、验收指标和一张能带走的表。

学这些动作，不学翻转句、口头禅和编造的戏剧冲突。

## 七、结构自检

初稿写完，先过这一张表。语言、证据和审稿见 `docs/writing-guide.md`。

- [ ] 六段齐全，每段只回答一个问题。
- [ ] 开场有一个具体场景，带角色、数字或后果。
- [ ] 全文有一句话论点和一个短大纲。
- [ ] 问题链没有断点，每节回答上一节留下的问题。
- [ ] 痛点和解法一一对应，没有多一个，也没有少一个。
- [ ] 每个解法有缺口、动作、收益、新代价。
- [ ] 具体实践至少有一种，和原理里的量对得上。
- [ ] 实践段有验收指标或常见坑，读者能带走一张表。
- [ ] 标题带编号，概括内容，没有“痛点”“解法”“收口”。
- [ ] 收口标题是名词性结论，概括判断或边界，不是回到类比、结语、总结，也不是先看、先算、先问。
- [ ] 关键判断有加粗，段落一眼能看出重点。
- [ ] 至少一张 Mermaid 图，图前有引导，图后有解释，删掉图后正文仍然成立。
- [ ] 每节至少新增一个机制、一个反例、一个代价或一个边界。
- [ ] 关键知识点先给总览表或路线图，再逐层展开。
- [ ] 基础原理和硬核细节之间有过渡，用阅读路径分层，不贴水平标签。
- [ ] 结尾给了尺子和落地提醒，没有重新摘要全文。
- [ ] 删掉三分之一后，事实和判断基本不变。

## 八、一页纸骨架

新建文章时，复制下面这段，再按六段结构填。标题按你的题目换，下面只是示例。

```md
---
title: ""
description: ""
date: ""
tags: []
---

开场。一个具体场景，带角色、数字和后果，交代主题和核心概念。

## 一、这一步到底在算什么

核心机制。一句话结论，一个关键约束，一个可核验的量。

一个主类比，给映射和边界，然后回到技术本体。

## 二、旧方案卡在哪

上一代方案的具体缺口。谁多花了时间，谁多付了钱，哪条路径被堵住。

## 三、第一类技术，先补哪个缺口

钩子。一个具体动作、数字或失败场景。

原理。技术怎么做的，关键约束是什么。

收益。带数字或可核验的对比，写清基线。

代价。牺牲了什么，换 shape、换版本、换负载时会不会失效。

## 四、第二类技术，再补哪个缺口

同样的结构。每节只回答一个问题。

## 五、你的系统到底要多少

一段能跑的代码，或一份真实配置，或一套步骤和验证方案。

一张验收指标表，一张常见坑表。

## 六、什么时候不该用

适用边界。一把可以带走的尺子。一条具体的落地提醒。
```
