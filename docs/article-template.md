# 技术长文写作模板与流程

本工程 content/ 下的技术长文，用两份文档配合。

- `docs/writing-guide.md` 管证据、禁令、终审。材料够不够、数字能不能写、哪些句子不能出现，以它为准。
- 本文档管结构、语感、类比、数字口径和发布流程。它把最新一篇 CANN × DeepSeek V4 文章的行文方式，和《技术长文写作模板》的六段式合到了一起。

短文章（1200 字以下）可以只用写作指南。长文建议先按本文档搭骨架，再按写作指南过材料关和终审。

## 一、最新文章的行文风格

最新一篇是 `content/AI/cann-deepseek-v4-inference-optimization.mdx`。它的写法可以拆成十三条。

1. **开头先交代主题，再给身体经验或数字。** 先用一两句话说明文章在讲什么、核心概念是什么，再用一个场景或数字把读者带进来。最新一篇 CANN 文章第一段是“想象你是一家餐厅唯一的厨师，一道菜要过 43 道工序，每道工序只给你 225 微秒”，第二段才给 9.66 毫秒、43 层、225 微秒的预算。读者先知道要看什么，再有体感，最后看到数字。数字不单独承担开场。

2. **数字必须换算。** 9.66 毫秒除以 43 层，得到 225 微秒；128K 序列除以 128，得到 1024 个块；32 个 CSA 条目乘 1024，得到 32K。数字不是装饰，换算本身改变理解。

3. **先立主角，再提难题。** 先说 V4-Flash 是 284B 总参、13B 激活、43 层、三种注意力、mHC 4 路、MoE 从 256 个路由专家里选 6 个，再说 PagedAttention 的均匀分页假设为什么失效。参数挂在因果上，不裸列。

4. **每个解法固定五步。** 钩子、原理、类比、收益、代价。Compressor 先讲拆开跑要多几次 GM 往返，再讲融合后中间结果留在片上；HCPre/HCPost 先算 4 路、1 路的读写量，再讲片上合并；AICPU 先讲回 Host 算会打断流水，再讲芯片上常驻 Scheduler。

5. **类比成体系，而且带边界。** 全文用一组生活场景解释不同模块，餐厅和供应链是主线，美食街、中央厨房、编辑部审稿、物流、立交桥、剧院分座员、冰箱、图书馆、拍电影、工厂、演出时刻表、固定搭配词典按节补充。每个类比后面跟一句“这个比方只解释 X，不解释 Y”，防止读者把生活经验推过头。

6. **收益和代价成对出现。** 融合算子换来更少的 GM 往返，代价是 kernel 绑定量化、布局和流水，换 shape 就要另写模板；多流换来重叠，代价是同步和资源争抢；低精度换来带宽和算力，代价是逐层精度回归；V4.1 换来更低的 KV 占用，代价是 kernel 的输入布局、压缩比和 Cache 生命周期都要重写。

7. **数字按口径分层。** 官方 recipe、技术报告、单算子数据、自算，各说各的。文章单列“这些数字怎么读”，把 Offline 模式、MTP 接受率、强制 EPLB、单卡吞吐和 global batch 的区别讲清楚。

8. **句子短，动词实。** “捏成 1 路”“撑回 4 路”“吃掉了一大块”“把时间抢回来”“把跑腿和排队的时间省出来”。少用 `进行了优化`、`实现了提升` 这类名词化写法。

9. **图表只在降低理解成本时出现。** 三张 Mermaid 图分别讲一层的数据流、KV Cache 的分块、CP 的 zig-zag；六张表分别讲模块压力、落盘三档、AICPU metadata、量化配方、Decode 并行和 benchmark 口径。图前有引导句，图后有解释，图不是装饰。

10. **结尾给尺子和口径，不做全文摘要。** 最后给一句可以带走的判断，“它减少了哪一类搬运，又增加了哪一类状态”，再给一条落地提醒，“上线前拿自己的序列长度分布和 MTP 接受率重跑一遍”。

11. **第一人称只用于判断和承认拿不准。** 材料核对写成客观动作，比如“CANN 的 V4 推理 recipe、DeepSeek-V4 技术报告和 V4.1 实践文档放在一起，关键数字逐条核对”。不写成“我拿……对了一遍”的工作日志，不编故事，不假装亲历。

12. **承认材料不均衡。** “模型结构的数据很完整，CANN 侧的整网逐项 ablation 几乎没有。”读者知道哪些结论硬，哪些结论只能停在单算子或定性判断。

13. **方法按演进链排，不按知识点排。** 先写上一代的具体缺口，再写这一代补了什么，最后写新代价。关键知识点先给总览表，再逐层拆机制。章节之间用上一节留下的问题承接。

压缩成一句。先交代主题和核心概念，再用一个具体场景或数字开场，用换算把数字变成体感，用“模型出题、逐条解法、收益代价、口径提醒”推进，用一把可带走的尺子收口。

## 二、六段式骨架

《技术长文写作模板》给的是六段式。放到本工程，可以落成下面这张表。六段不是六个一级标题，第四段会展开成多个解法小节。

| 段 | 任务 | 写法 | 最新文章对应 |
|---|---|---|---|
| 1 开场 | 先交代主题，再抓住读者 | 主题句加一个数字、场景或反差，数字为概念服务 | 沙盘三层十一格；70B 从 140GB 压到 35GB |
| 2 换算 | 让数字可感 | 除法、对比、折算成“几趟” | 9.66ms / 43 层；27% 和 10% |
| 3 主角与难题 | 说清是什么、难在哪 | 身份句、规模数字、关键差异、具体痛点 | V4 的层结构；PagedAttention 失效 |
| 4 逐条解法 | 解释怎么解 | 每条五步，钩子、原理、类比、收益、代价 | KV Cache、融合、多流、精度、并行、V4.1 |
| 5 数字怎么读 | 防误读 | 表格、口径、限定条件 | benchmark 表、Offline、MTP、EPLB |
| 6 收口 | 给尺子 | 可迁移判据、落地提醒 | 搬运和状态；重跑自己的分布 |

第四段是文章的主体。一个解法一节，每节只回答一个问题。节与节之间靠因果推进，不靠“首先、其次、最后”排队。

## 三、写作流程

流程沿用六阶段门禁，把模板的检查点嵌进去。

| 阶段 | 产出 | 门禁 | 工具 |
|---|---|---|---|
| P1 范围 | 读者卡点、主副手法、目标长度 | 说得出读者在哪一步停下来 | `docs/explanation-patterns.md` |
| P2 材料关 | 至少五件具体材料、来源表、待核清单 | 无 L4；每个数字有出处 | `docs/writing-guide.md` |
| P3 蓝图 | 一句话论点、六段骨架、解法地图、类比地图、数字表 | 每条解法有收益和代价；每个类比有边界 | 本文档 |
| P4 成稿 | 初稿 | 每段新增事实、机制、例子或反例；硬禁令为零 | `docs/writing-guide.md` |
| P5 终审 | 修改稿 | 检测脚本为零；六维审查；数字复核 | `scripts/check_prose.py` |
| P6 交付 | 成稿、来源、构建 | 页面生成；搜索索引更新 | `npm run build` |

### P1 范围

先回答三个问题。读者是谁，他卡在哪，这篇文章只解决哪一个卡点。再定主手法和副手法，主手法负责开头和主线，副手法只补一个缺口。最后定长度，长文按 4000 到 8000 汉字估，材料不够就缩短，不靠重复解释灌字数。

### P2 材料关

长文至少五件可指认来源的材料。材料表至少七列，编号、来源、层级、能支撑什么、不能支撑什么、计划用途、风险。材料清单是内部工作文件，不进成稿。

同时建一份待核清单，记下所有出现两次以上的数字，包括层数、hidden size、专家数量、压缩倍率、top-k、卡数、序列长度、TPOT、吞吐。发布前逐条对原表。

### P3 蓝图

蓝图只写六样东西。

1. 一句话论点。比如“V4 把计算和缓存压小，瓶颈转到离散访存、调度和通信，CANN 的优化围绕这三类开销展开”。
2. 六段骨架。每段写一句任务，不写正文。
3. 解法地图。每个解法对应哪一个瓶颈，收益是什么，代价是什么。
4. 类比地图。全文用哪一条主意象，每一节用哪一个场景，每个场景的边界在哪。
5. 数字表。每个数字的来源、口径、换算、计划放在哪一段。
6. 逻辑链和深浅过渡。每个解法接住上一节留下的哪个问题，解决后留下什么新代价；基础结论、机制、字节和 kernel 细节分别放在哪一段，过渡句是什么。

蓝图阶段就要排除没有来源的声明。成稿里不留“待核验”“TBD”这类标记。

### P4 成稿

按六段骨架写。每个解法小节固定五步。

- 钩子。具体动作、数字，或者一个失败场景。
- 原理。技术怎么做的，关键约束是什么。
- 类比。给映射，也给边界。
- 收益。带数字，或者带可核验的对比。
- 代价。牺牲了什么，换 shape、换版本、换负载时会不会失效。

每写完一段问一句，读者现在最想知道什么。下一段必须增加新东西，新事实、新机制、新例子、新区别或新后果。同一观点换说法不算推进。

方法类文章按“上一代缺口、这一代动作、新代价”推进。每个小节从上一节留下的问题开始，写完再留下一个问题给下一节。关键知识点先给总览表或路线图，再逐层展开，别把表格当成解释。

### P5 终审

先跑 `python scripts/check_prose.py <稿件路径>`，硬禁令清零。再按写作指南的六个维度过一遍，事实、材料、结构、禁令、语感、讲解有效性。

数字复核单独做一遍。重点看四类错误。

- 把墙钟分摊说成纯计算耗时。
- 把 global batch 和单卡吞吐直接相乘相除。
- 把单算子加速比加到整网 TPOT 上。
- 跨平台比吞吐，而两边的精度方案不同。

### P6 交付

成稿只留正文、图表和必要的来源。内部材料表、蓝图、审查记录不进成稿。写完跑一次 `npm run build`，确认 MDX 能编译、页面能生成、搜索索引更新。需要提交时再按仓库的提交习惯提交。

## 四、风格规则

### 4.1 开头

开头先交代主题。用一两句话告诉读者这篇文章在讲什么，核心概念是什么，读者为什么值得往下读。主题句要具体，不写“随着大模型的发展”“本文将深入分析”。

主题句之后，再用一个数字、一个反差或一个具体场景把读者带进来。数字是证据，不是开场的主角。不要一上来堆一串数字，也不要用一个孤零零的数字当第一段。每个数字后面要接它改变了什么理解，或者它让谁多花了多少时间。

比如写 AI 算法沙盘，可以先说“这张沙盘纵向三层，横向四类场景，一共十一格，每格写着一笔开销的名字”，再拿 70B 模型从 140GB 压到 35GB 举例，说明装得下不等于跑得快。读者先知道文章在讲什么，再看数字，才不会在一堆 GB 和倍数里迷路。

反例是开头先甩一串数字，比如“35GB。70B 的模型，140GB，35GB，4 倍。”读者还不知道这篇文章要讲什么，先被数字挡住了。数字要等主题句把问题立起来之后再进来。

主题句之后马上给换算、例子或背景，不让读者停在半空。开头用了类比，就在第三段前后补一句边界。

开头自检。

- 第一段能不能用一句话说出文章的主题。
- 核心概念有没有在出现术语之前解释。
- 数字是不是都在为概念服务，有没有连续三个以上数字没有解释。
- 把第一段单独拿出来读，句子是否完整通顺。

### 4.2 段落

第一句是结论或钩子，不是背景铺垫。一段只做一件事，讲动作、讲机制、讲例子或讲判断。连续三段只做同一件事，合并或删掉。

段落长短要有高低差。十个字的句子可以挨着四十个字的句子。不要每段都用短判断收尾，也不要连续四段都是一句话。

### 4.3 小节

每个解法小节按五步走。小节结尾可以留一句能被单独引用的话，但不要写成口号。比如“能提前算的才提前算，有依赖的一律留在原地”，它对应的是 AICPU 的调度边界，不是空泛的总结。

### 4.4 类比

一篇长文只立一条主线。主线可以是一类生活场景，不必是同一个物件。AI 基础设施文章可以用后厨和供应链作主线，具体到某一节可以换成物流、立交桥、剧院，但一节里不要换两次。操作系统文章可以用图书馆、邮局、叫号机，嵌入式文章可以用工位、流水线、门铃，自动驾驶文章可以用多目击者描述同一场景。

每个类比必须给三样东西。

1. 映射。生活对象对应哪个技术对象，动作对应哪个机制。
2. 边界。这个类比不解释什么，防止读者推过头。
3. 回归。类比之后马上回到技术本体，不能比喻完就走。

类比不承载数字。数字单独给，比喻负责懂，数字负责信。删掉类比后，机制段仍然成立，这个类比才是解释性的，不是装饰性的。

### 4.5 数字

每个数字至少带两样东西，来源和参照。来源分五类，官方 recipe、技术报告、第三方实测、单算子微基准、自算。参照可以是除法、百分比、基线对比或折算成“几趟”。不同口径的数字不能直接比较，Offline 模式不含 Serving 调度，MTP 接受率随数据集变，单算子数字不能加到整网，跨平台吞吐受精度方案影响。文章里出现跨口径比较，明写“不能直接对比”。

自算的数字写清推算过程。比如“9.66ms 除以 43 层，平均每层 225µs”，不要写成“每层计算耗时 225µs”。

### 4.6 结尾

结尾给一把尺子，再给一条落地提醒。尺子要能迁移到别的优化点，比如“先问它减少了哪一类搬运，又增加了哪一类状态”。落地提醒要具体，比如“上线前拿自己的序列长度分布和 MTP 接受率重跑一遍”。

结尾不重新摘要全文，不升华到时代、文明、未来。最后一段删掉再读，如果文章更有力，就让文章提前结束。

### 4.7 中文

先说谁做了什么，再补时间、原因和条件。一句话里三四个“的”，先找做事的人。删掉一半连词。中文小句靠语序和事理相接。

动词直接写。`进行优化` 写成 `改顺了`，`实现提升` 写成 `从 71.84µs 降到 49.14µs`。动作、数字、原话已经把意思写出来就停住，不追一句解释。

硬禁令按写作指南执行。正文不用冒号、破折号、翻案句、三项以上同构排比、黑话、借喻包装、洞察路标。结尾不升华。

### 4.8 第一人称

“我”只用于下判断和承认拿不准。材料核对写成客观动作，不写成作者的个人工作日志。不用于编造亲历、情绪和对话。

可以写“三份材料放在一起核对，数字对不上”“我拿不准这一点”“公开材料里没有逐项 ablation”。不要写“我拿三份材料对了一遍”“我查了……”“我当时就在现场”“我记得那天”。

## 五、类比库

这张表按主题复用。一篇文章只选一条主线，主线里的场景可以换，但不要一段换一个完全不同的意象。

| 主题 | 固定意象 | 映射 | 边界 |
|---|---|---|---|
| 访存和搬运 | 物流、中转站、中央厨房 | GM 往返等于配送车往返，融合等于一趟跑全程 | 不解释 Cube 和 Vector 的核间分工 |
| 精度分层 | 冰箱 | 冷藏是滑窗 KV，冷冻是压缩 KV，罐头是权重 | 不解释同一张量内部的分层 |
| 调度和流水 | 剧院分座员 | AICPU 是门厅常驻的分座员 | 不解释 tiling 信息怎样跨层复用 |
| 缓存分层 | 图书馆分馆 | HBM 是桌面，DDR 是书架，SSD 是地下书库 | 不解释每一层的带宽和命中代价 |
| 并行策略 | 工厂车间 | DP 是各配模具，EP 是全厂一套，TP 是分工 | 不解释 all_to_all 和 reduce_scatter 的转换 |
| 投机解码 | 编辑部审稿 | 草稿是实习生稿，拒绝是白板擦掉 | 不解释接受率随数据集变化 |
| 稀疏访存 | 前台查卡片 | scalar 查地址等于查卡片找货架号 | 不解释边界检查和离散访存的具体开销 |
| 图模式 | 演出时刻表 | ACLGraph 是时刻表，编译缓存是复印存档 | 不解释动态 shape 下为什么 Prefill 不适合整图捕获 |
| 算子融合 | 后舱提前拆包装 | 片上 UB 是车后舱 | 不解释 tiling 和同步 |
| 多流并行 | 两口灶同时开火 | stream 是灶台 | 不解释 event 同步和流间依赖 |
| 残差多路 | 多车道汇一车道 | 4 路到 1 路再到 4 路 | 不解释 Res Mapping 的双随机约束 |
| Engram 记忆表 | 固定搭配词典 | n-gram 哈希是查词典 | 不解释哈希冲突和 n-gram 构造 |
| 进程调度 | 叫号机 | 就绪线程是排队的人，运行队列是等候区 | 不解释优先级反转 |
| 内存管理 | 书桌和书架 | 缓存是书桌，主存是书架 | 不解释多核缓存一致性和 TLB shootdown |
| 中断处理 | 门铃 | 中断是门铃，ISR 是开门 | 不解释中断延迟和嵌套 |
| 总线仲裁 | 路口红绿灯 | 仲裁器是红绿灯，主设备是车 | 不解释公平性和饥饿 |
| 传感器融合 | 多个目击者描述同一场景 | 多传感器是多个目击者，标定是统一口径 | 不解释时间同步和标定误差 |

使用规则。

1. 一篇长文只选一条主线。主线可以是一类生活场景，不必是同一个物件。主线之外的类比最多一个，用来补主手法够不到的缺口。
2. 每个类比只解释一个核心结构，不要一个类比解释三个概念。
3. 类比后面必须接技术解释。删掉类比后机制段不存在，说明类比替代了正文。
4. 类比里不出现材料没有的数字、情绪和对话。

## 六、严谨性护栏

发布前逐条过。

1. 三种口径分开标注。厂商离线自测、第三方实测、单算子微基准。跨口径比较处明写“不能直接对比”。
2. 推算和官方数据分开措辞。官方写“官方 recipe 给的数”，自算写“按 9.66ms / 43 层推算”。
3. 墙钟预算和纯计算耗时分开。225µs 是单卡单层的墙钟分摊，不是矩阵乘的纯计算时间。
4. global batch 和单卡吞吐分开。两个数不能直接相乘相除。
5. 单算子加速比和整网 TPOT 分开。单算子数字不能直接加到整网指标上。
6. 跨平台比 TPOT 可以，比吞吐要谨慎。A3 和 950DT 的精度方案不同。
7. 型号和版本分开。V4 和 V4.1 不是一套结构，Flash 和 Pro 的层数、hidden size、专家数量、压缩策略都不同。
8. 产品状态分开。已经可用、邀请测试、宣布以后提供、长期方向，不混写。
9. 来源冲突说明取舍。不挑最适合故事的一条写死。
10. 每个收益配一个代价。省了 GM 往返，可能换来 kernel 灵活性下降；省了带宽，可能换来精度回归；省了卡数，可能换来通信瓶颈。
11. 敏感数字进待核清单。专家数量、层数、hidden size、压缩倍率、top-k、卡数、序列长度、TPOT、吞吐，出现两次以上就要复核。
12. 不写没有来源的第三方数字。厂商自测、第三方实测、单算子微基准，三种口径不混用。
