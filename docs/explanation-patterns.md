# 讲解手法

面向 content/ 下的技术知识文章。讲解手法负责把材料送进读者脑子，不产生材料，也不替代证据。一篇文章选一到两个手法，第一个是主手法，第二个只在主手法够不到的地方补位。

开头先交代主题和核心概念，再用具体症状、场景或数字进入。数字不单独承担开场，也不要用一串数字代替解释。

## 先看读者卡在哪

选手法之前先回答一个问题。读者读这篇文章时，最可能在哪一步停下来。

- 没有直观图像，术语一多就跟丢。
- 角色太多，时序和冲突绕不清。
- 知道自己慢，不知道从哪下手。
- 信息量太大，分不清主次和适用边界。
- 看得到结果，不知道设计为什么这样。
- 结论和直觉冲突，不知道信哪部分。

答案决定主手法。不要先选一个手法，再去找例子。手法给读者用，不能拿去装饰文章。

## 按文章类型选

| 文章类型 | 读者通常卡在哪 | 主手法 | 副手法 |
|---|---|---|---|
| 概念解释、入门科普 | 没有直观图像，术语一多就跟丢 | 生活化类比 | 渐进推导 |
| 协议、并发、多角色系统 | 角色多，时序和冲突绕不清 | 拟人故事 | 问题前置 |
| 故障排查、性能优化 | 知道自己慢，不知道从哪下手 | 问题前置 | 渐进推导 |
| 架构、系统设计、survey | 信息量大，分不清主次和适用边界 | 分层讲解 | 问题前置 |
| 源码、算法、机制 deep-dive | 看得到结果，不知道设计为什么这样 | 渐进推导 | 分层讲解 |
| 产品、技术分析、评测 | 结论和直觉冲突，不知道信哪部分 | 问题前置 | 分层讲解 |

文章跨两类时，按读者最可能卡住的那一步选，不按题目分类选。

## 选择规则

- 一篇一个主手法。主手法负责开头和主线，出现次数最多。
- 最多一个副手法。副手法只补一个缺口，不平均分配篇幅。
- 手法在蓝图里定，不在正文里报菜名。不写“本文将用类比法”“让我们一步步推导”“先从 `新手` 视角看”。
- 材料不够支撑某个手法时换一个。没有具体症状，就不用问题前置；没有真实机制可映射，就不用拟人故事。
- 一段里只用一个解释框架。类比和拟人不要在同一节里抢读者注意力。
- 手法不能引入新材料。类比里的生活细节、拟人里的动作、问题里的数字，都要有来源或明确标成示例。

蓝图里留三行内部记录。

1. 读者卡点。
2. 主手法，负责哪一段。
3. 副手法，补哪个缺口。

三行都不进正文。写完一段回头看一眼，主手法还在不在干活。

## 1 生活化类比

### 核心逻辑

找到技术结构和生活场景共有的那套关系，用读者已经知道的东西搭一座桥。桥要能双向走，读者看完生活例子，能顺着映射回到技术对象。

### 写法

1. 先给生活场景，控制在四段以内。
2. 逐项写出对应关系，不写“就像”就完事。
3. 说明这个类比在哪里失效，防止读者把生活经验推过头。
4. 回到技术对象，继续讲机制。

### 必须做到

- 映射要具体到对象和动作。不要写“缓存就像仓库”，要写“缓存像书桌，主存像书架，取一本书要走到书架前”。
- 一个主类比只解释一个核心结构。不要中途换场景。
- 类比后面必须接技术解释。类比不承担证明，也不承担数字。
- 类比可以删掉，机制段不能删掉。删掉类比后如果机制段也不存在，说明类比替代了正文。

### 示例

讲 CPU 缓存时，可以先用书桌和书架。TCP 三次握手也可以先用两个人打电话确认双方都能听见，再说明这个类比不解释起始序号和半连接队列。

| 生活对象 | 技术对象 |
|---|---|
| 书桌 | L1、L2 缓存 |
| 书架 | 主存 |
| 从书架取书放到桌上 | 缓存未命中后加载缓存行 |
| 桌上放不下，先收走一本 | 缓存替换 |

然后写边界。这个类比不解释多核之间怎样同步缓存行，也不解释伪共享。读者知道桌子小、书架大，就能理解为什么命中率重要，但不会误以为缓存只是一块更快的内存。

### 失败模式

- 只写“就像”不写映射，读者各想各的。
- 生活例子比技术解释还长，读完只记得故事。
- 一个类比解释三个概念，每个都差一点。
- 用类比支撑数字或因果，把比喻当证据。
- 类比里出现材料没有的细节，越具体越假。

## 2 渐进推导

### 核心逻辑

不从最终方案开始，从最笨但能用的版本开始。每遇到一个约束，就改一版。读者跟着问题走，最后得到一套设计思路，结论只是副产品。

### 写法

1. 给出最简场景和初始方案。
2. 加一个约束，说明初始方案为什么不够。
3. 给出只解决这个约束的下一版。
4. 再加一个约束，重复。
5. 停在当前材料能支撑的方案上，说明它仍然不解决什么。

### 必须做到

- 每一步只加一个新约束。不要一口气加三个，读者会不知道是哪一条导致方案变化。
- 每一步都要指出上一版的具体失败。没有失败，就没有推导。
- 约束要有来源。来自论文、源码、配置、实验或用户亲历，不能为了让推导顺而编一个。
- 不伪造技术发展史。可以不写“当年工程师就是这样想的”，只写“如果只考虑这个约束，方案会怎样”。
- 推导结束要回到真实方案，说明真实方案多解决了什么，代价是什么。

### 示例

讲内存屏障，可以从一个核、没有缓存开始。

1. 单核、编译器不重排、CPU 不乱序，程序看到的顺序就是代码顺序。
2. 加入多核和缓存，两个核可能看到不同的值。
3. 加入缓存一致性协议，值能同步，但读写仍可能重排。
4. 加入内存屏障，限制哪些读写不能跨过屏障。
5. 说明屏障带来的代价，以及它不解决什么。

每一步只增加一个约束。读者看到问题怎么逼出方案，五个名词只是结果。

### 失败模式

- 伪造历史，把推导写成技术演义。
- 每一步都在重复同一个结论，只换说法。
- 上一版没有失败，下一版却突然出现。
- 一次加太多约束，读者跟不上。
- 推导到最后，真实方案和数据没有出现。

## 3 拟人故事

### 核心逻辑

给技术组件一个身份和目标，用角色冲突串起交互过程。读者先记住谁在抢什么，再回到机制。

### 写法

1. 明确标记这是假设。写“把调度器想成叫号机”，不写“调度器今天遇到了一件麻烦事”。
2. 给每个角色一个目标和一个限制。
3. 设计一个冲突，冲突必须对应真实机制。
4. 用故事走完一轮交互。
5. 回到技术术语，逐项说明故事里的动作对应什么。

### 必须做到

- 拟人段落必须有标记句。没有标记句，读者会把故事当成事实。
- 角色的行为要能对应真实机制。线程被抢占，对应的是调度器保存上下文、切换运行队列，不能写成“小张不高兴了”。
- 不编造事件、情绪、对话和数据。故事只负责组织已核实的机制。
- 故事结束后回到机制。不能停在“小张终于拿到了锁”这种结局上。
- 只用在多角色、多阶段、有时序的系统里。单组件概念不需要拟人。

### 示例

讲调度器，可以先把调度器想成叫号机，把线程想成排队办事的人。

| 故事里的东西 | 技术对象 |
|---|---|
| 排队的人 | 就绪线程 |
| 等候区 | 运行队列 |
| 叫号机 | 调度器 |
| 每次办事的时限 | 时间片 |
| 叫号机让当前的人先停下 | 抢占 |

故事可以写到“高优先级的人来了，叫号机让当前的人先停下，把位置留给新来的人”。然后回到机制，解释优先级、时间片、上下文切换和抢占点。最后写边界。叫号机不解释优先级反转，也不解释内核在哪些位置允许抢占。

### 失败模式

- 给组件编造情绪、对话和私生活。
- 故事很好看，但每个动作都对应不上真实机制。
- 故事里的数字没有来源，读者把情节当事实。
- 故事结束后不回到技术术语，文章变成寓言。
- 所有文章都用“线程小张”，角色变成模板。

## 4 问题前置

### 核心逻辑

读者先意识到自己有一个问题，才会认真看解决方案。痛点要具体，不能靠一句泛化提问制造共鸣。

### 写法

1. 给一个具体症状。报错、数字、时间、命令、用户亲历，至少有一个。
2. 说明这个症状带来的具体麻烦。谁多花了时间，谁多付了钱，哪条路径被堵住。
3. 引出技术问题。写“先查哪一层，为什么”，不写“今天讲透 X”。
4. 展开机制和方案。

### 必须做到

- 症状要具体。写“P99 从 80ms 涨到 1.2s，日志里出现大量连接等待”，不写 `你有没有遇到过接口变慢`。
- 痛点要有来源。来自用户经历、监控、issue、论文或官方文档。没有真实案例，就用有来源的失效模式，不编“很多团队都这样”。
- 痛点和方案要对得上。开头讲慢查询，后文不能全讲锁竞争。
- 不承诺“彻底讲透”“一文解决所有问题”。
- 问题前置只给症状，不做结构预告。不要写“本文将从三个方面展开”。

### 示例

线上接口的 P99 从 80ms 涨到 1.2s，日志里出现大量连接等待。连接池占用已经到上限，慢查询时间却没有明显变化。先查连接池，还是先查下游超时，这个顺序决定要熬多久。

这段是示例，数字不写成事实。真实文章里换成用户给的监控、报错或亲历动作。

### 失败模式

- 用 `你有没有遇到过` 开头，后面接一个万能痛点。
- 编造“很多团队都踩过这个坑”的普遍性。
- 痛点很吓人，但和后面的技术方案无关。
- 开头承诺太大，正文支撑不住。
- 把问题前置写成目录预告。

## 5 分层讲解

### 核心逻辑

同一篇文章里，不同读者需要不同深度。分层按内容深度排，不贴水平标签，让每层都能独立站住。

### 写法

1. 表层给一句话答案和适用条件。
2. 中层给核心机制和常规用法。
3. 深层给设计取舍、性能代价和常见坑。
4. 专家层给源码细节、边界条件和前沿进展。

### 必须做到

- 分层是内容顺序，不是标题标签。不写 `新手看这里`、`高手直接跳过`、`专家层`。
- 每层只回答一个问题。表层回答是什么，中层回答怎么工作，深层回答为什么这样选，专家层回答边界在哪里。
- 每层都能独立读懂。读者跳到深层，不需要先读完前三层。
- 不重复。同一结论不要在四层里各说一遍。
- 不在表层堆术语。表层用普通句子给结论，术语放到中层解释。
- 不用“更深一层”“还有一层”做路标。深度靠内容变化，不靠提示词。

### 示例

讲内存屏障，可以这样排。

- 表层。内存屏障限制编译器和 CPU 重排读写。
- 中层。它规定哪些读写不能跨过屏障，内核里对应哪些宏。
- 深层。它带来什么性能代价，哪些场景可以不用。
- 专家层。ARM64 的 `dmb ish` 和内核宏的对应关系，以及不同架构的差异。

读者只关心结论，读完第一段就能走。要写驱动，读到中层。要排查性能，跳到深层。要改内核，读专家层。

### 失败模式

- 用 `入门`、`进阶`、`专家` 当小标题，内容还是同一套。
- 表层就把所有术语倒出来，后面没有新东西。
- 四层重复同一个结论，只是措辞不同。
- 专家层变成名词展览，没有边界和取舍。
- 分层变成目录预告，正文没有对应的深度变化。

## 组合与禁用

| 组合 | 用法 | 注意 |
|---|---|---|
| 生活化类比 + 渐进推导 | 类比负责建立第一张图，推导负责把图改准 | 类比只出现一次，推导每步加约束 |
| 拟人故事 + 问题前置 | 先用具体症状定焦点，再用角色冲突讲时序 | 故事必须回到机制，痛点必须和方案对得上 |
| 问题前置 + 渐进推导 | 先给症状，再逐层排除 | 每一步的排查动作要有来源 |
| 分层讲解 + 问题前置 | 先用痛点定读者，再按深度排内容 | 表层回答要直接回应痛点 |
| 渐进推导 + 分层讲解 | 推导负责主线，分层负责细节 | 不要在每一层重新推导一遍 |

不要在同一节里同时用类比和拟人。两个解释框架会抢读者注意力。短文（1200 字以下）不要同时用问题前置和渐进推导，铺垫会占掉太多篇幅。任何手法都不能拿来替代证据、数字和机制。

## 交稿前自检

- 能不能用一句话说出读者卡在哪。
- 主手法是否在前三分之一出现，并且一直在干活。
- 副手法是否只补一个缺口，没有抢主线。
- 类比是否给出映射和失效边界，是否只有一个主类比。
- 拟人是否明示为假设，角色行为是否对应真实机制。
- 问题是否具体到症状、报错、数字或亲历动作。
- 推导是否每一步只加一个新约束，上一版是否真的失败。
- 分层是否只有深度顺序，没有 `新手`、`高手`、`入门`、`进阶`、`专家` 标签。
- 正文有没有报菜名，比如“本文将用类比法”“让我们一步步推导”。
- 删掉手法段落之后，技术解释是否仍然成立。如果不成立，说明手法替代了机制。
- 手法有没有引入材料里没有的事实、数字、情绪或对话。

长文的类比选择和边界检查，配合 `docs/article-template.md` 的类比库使用。
