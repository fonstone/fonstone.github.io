# 技术博客写作技能设计（tech-blog-writing）

日期：2026-09-06

## 背景

本工程是 StoneFon 的个人知识博客（Next.js + MDX），现有 35+ 篇技术知识文章（AI、OS、自动驾驶、管理）。当前写作方法沉淀为 docs/writing-guide.md（改编自 human-writing v1.1.0）+ scripts/check_prose.py 检测脚本。

human-writing 提供的是规则清单（材料关、真实性、细节、禁令、七遍改稿），但没有把方法变成带阶段门禁的可执行流程。参考 [HKUSTDial/Supervisor-Skills](https://github.com/HKUSTDial/Supervisor-Skills)（CC BY-NC-SA 4.0）的 skills 具体实现，其核心机制包括：

- paper-writer：六阶段流水线（Scope→Evidence→Blueprint→Draft→Red flags→Review→Deliver），证据层级 L0-L4，Evidence Map 工作文件，provenance thinking（写时溯源），占位标签禁令，红牌停止信号表，声称校准（claim strength 不超过 evidence strength）
- intro-drafter：六段内部骨架（背景+运行示例→局限→问题本质与目标→关键难点→方案概览→贡献），对齐检查，骨架只做内部思考不出现在输出
- paper-polish：忠实原意优先，声称强度校准，AI 腔清除
- pre-submission-reviewer：severity 分级（CRITICAL/MAJOR/MINOR）五维度审查，integrity gate（每条 finding 引原文、CRITICAL 必须有具体改法、不编造引文），能力降级披露

本设计把上述机制适配到技术博客写作，交付为单技能（带阶段门禁）+ 脚本扩展 + 文档更新。

## 技能设计

### 路由边界

- 本技能管 content/ 技术知识文章
- 公众号文章走 gzh-write，虚构/人物/故事走 human-writing，两者不混
- 触发词：写技术博客、技术长文、知识空间文章、survey、deep-dive

### 六阶段流水线

| 阶段 | 内容 | 门禁 |
|---|---|---|
| P1 范围 | 粒度（长文≥1200 字/短文）、文章领域（AI/OS/嵌入式/自动驾驶/管理）、模式（草稿/成稿） | 领域决定说话位置 |
| P2 材料关 | 证据层级 L0-L4 + 材料清单工作文件（长文落盘，短文脑内过） | 无 L0-L3 来源的声明不写成事实，先检索→改写→删除，绝不打占位标签 |
| P3 蓝图 | 说话位置五问 + 技术文内部段落骨架 + 对齐检查 | 骨架只做内部思考，输出结构仍从材料长出来 |
| P4 成稿 | 逐段 provenance thinking + 红牌停止信号 + 声称校准 + 真实/计划分离 | 写时拦截，不靠事后检查兜底 |
| P5 终审 | 自审 + severity 分级审查 + integrity gate + 脚本 | 每条 finding 必须引原文，CRITICAL 必须有具体改法 |
| P6 交付 | 干净成稿（零标记、零内部规划泄漏）+ 来源列表 + ≤3 行说明 | 能力降级（无检索/无独立核验）必须披露 |

### 能力检查（一次性，随任务降级）

- 有 websearch 就做独立检索，没有则闭卷写作并在交付说明中披露
- 有 task 子代理就派 fresh-context 代理独立核验关键数字与引用，没有则降级为同上下文自查并披露
- 证据规则本身永不降级，只有核验机制降级

### 证据层级（P2）

| 层级 | 来源 | 能支撑 | 不能支撑 |
|---|---|---|---|
| L1 全文/数据 | 论文全文、官方文档、源码、config.json、亲历调试日志 | 任何声明 | 无 |
| L2 摘要/页面 | 论文摘要、官方 release note、官方 blog | 研究方向、头条结论 | 具体数字、实现细节 |
| L3 元数据 | 检索返回的标题/作者/年份/版本 | "X 在 Y 年做了 Z" | 方法细节、性能数字 |
| L0 领域常识 | 从业者不引证也接受，且无数字无名无比较 | 背景框架句 | 任何带数字/名称/比较的声明 |
| L4 模型记忆 | 只是"记得" | 无 | 一切 |

### 材料清单工作文件（长文落盘为 材料清单.md，短文脑内过）

```markdown
| ID | 来源 | 层级 | 能支撑 | 不能支撑 | 计划用途 | 风险 |
```

- "不能支撑"列强制填写
- L3 行带 `仅元数据` 风险标记
- 来源是仓库文件时记路径
- L4 永不进清单

### 红牌停止信号表（P4 写时拦截）

| 想法 | 正确动作 |
|---|---|
| 我记得这个参数是 8 | 停。不确定就省略数字 |
| 我记得这篇论文用了三阶段 | 停。没读全文只写引证级 |
| 这个场景大概需要…… | 停。量级只写用户给的 |
| 背景应该提一下领域发展史 | 停。超出 L0 必须有来源，找不到就不写 |
| 加个失败案例更能说明问题 | 停。不编造案例，用用户亲历 |

### 声称校准（P4）

- 强词（证明/首次/最先进/显著提升）只在 L1 证据上
- 中词（表明/说明/与……一致）用于合理但有开放性的发现
- 弱词（可能反映/看起来/推测）用于猜测
- 真实结果与预期结果措辞分离，绝不混写（已开放/邀请测试/长期愿景分开记录）

### 内部段落骨架（P3，只做内部思考，不进入输出）

1. 具体场景/事实开头（尽快碰到事情）
2. 现有方案/工具的局限（至多三条，每条有来源）
3. 问题本质与目标（硬约束明确）
4. 关键难点（至多三条）
5. 方案/原理/数据（逐条对应难点）
6. 边界与结论（数据影响谁、哪些拿不准）

对齐检查：开头场景在方案段重现；每条局限都有来源，每条难点回应一条局限；难点与方案模块一一对应；每条结论能指出支撑的证据 ID。分类和小标题仍从材料长出来，不预设"三个维度"式命名。

### 终审（P5）

五个审查维度：
1. 事实可核验性（每个数字/版本/引用能否指出来源）
2. 材料支撑度（每段能指出支撑的证据 ID，L 级是否配得上声称强度）
3. 结构推进（每段新增了什么，删掉 1/3 后事实判断是否不变）
4. 硬禁令（冒号/破折号/翻案句/黑话/排比，脚本扫）
5. 语感节奏（主干、长短句、段落鼓点）

severity 分级：
- CRITICAL（阻断发布）：无来源的关键事实、编造数字、来源冲突挑好的写、声称强度远超证据
- MAJOR（读者会追问）：声称过强、关键证据缺失、段落无新增、结构断裂
- MINOR（打磨）：句长、措辞、过渡

integrity gate（静默执行）：每条 finding 必须引具体原文；CRITICAL 必须有具体改法；不编造引文。

输出 = 严重度统计 + 分维度表格 + 发布建议（可直接发布/需 1-2 天再改/需大改）。存在 CRITICAL 禁止"可直接发布"结论。

### 交付（P6）

- 干净成稿（零标记、零内部规划泄漏），写入 content/ 对应目录
- 有引用时附来源列表
- ≤3 行说明：能力降级披露、需用户确认项
- 内部规划（材料清单、骨架）不入成稿，可应要求提供

## check_prose.py 扩展

新增三类检查：

1. **占位标记**（硬失败）：中英文括号内以"待/补/引用/citation/TBD/TODO"开头、结尾为"核验/确认/补充/引用/补/待办/verify/confirm"类词的短标记，如 `[待核验]`、`[待确认]`、`[TBD]`、`[citation needed]`；正则实现，先做精确词表，再匹配 `[` 或 `（` 内以白名单词开头的待办短语
2. **过度声称词**（警告）：首次提出/首创/最先进/最领先/显著提升/大幅提升/革命性/突破性/彻底解决/遥遥领先
3. **真实vs计划混写**（警告）：同段落内"已实现/已完成/已开放"与"将提供/预计/即将"并存
