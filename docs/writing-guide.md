# StoneFon 知识空间写作指南

本文档管材料、证据、真实性、语言和审稿。结构、蓝图、逐节写法见 `docs/article-template.md`；讲解手法和类比库见 `docs/explanation-patterns.md`。

目标是把文章写成一个具体的人在说话。他查过资料、有判断，也承认哪里拿不准。读者读完能核验每个数字。

## 一、材料关

技术长文（1200 字以上）动笔前，逐条列出至少五件具体材料。论文或官方文档的原文、源码或 config.json 里的参数、实验或基准数字、产品版本号与许可证、亲历的调试过程，都可以。每件注明来自哪份来源。

材料不够，按顺序处理。

1. 查公开资料，换两三种关键词变体，重新计数。
2. 还找不到，一次问用户最多三个问题。
3. 用户不让问，缩小题目或缩短篇幅。
4. 缩不了，停。不拿重复解释灌字数。

抽象观点换四种说法仍然是同一条材料。每段都要能指出它靠哪件材料站住。答案只是由上一段可以想到，删。

## 二、证据层级

材料按来源分五级，决定它能撑住多强的声明。

| 层级 | 来源 | 能支撑 | 不能支撑 |
|---|---|---|---|
| L1 全文/数据 | 论文全文、官方文档、源码、config.json、亲历调试日志 | 任何声明 | 无 |
| L2 摘要/页面 | 论文摘要、官方 release note、官方 blog | 研究方向、头条结论 | 具体数字、实现细节 |
| L3 元数据 | 检索返回的标题/作者/年份/版本 | X 在 Y 年做了 Z | 方法细节、性能数字 |
| L0 领域常识 | 从业者不引证也接受，且无数字无名无比较 | 背景框架句 | 任何带数字/名称/比较的声明 |
| L4 模型记忆 | 只是记得 | 无 | 一切 |

对一句话是否常识犹豫，它就不是 L0，检索找来源。L4 永不进材料清单。长文把材料清单写成工作文件，每件一行。

| ID | 来源 | 层级 | 能支撑 | 不能支撑 | 计划用途 | 风险 |
|---|---|---|---|---|---|---|
| E1 | 论文全文第 3 节 | L1 | 方法步骤、精确数字 | 无 | 原理段 | 无 |
| E2 | 检索元数据 | L3 | X 在 Y 年做了 Z | 方法步骤、数字 | 背景段 | 仅元数据 |

不能支撑列强制填写。来源是文件时记路径。清单是内部工作文件，不进成稿。

同时建一份数字待核清单。层数、hidden size、专家数量、压缩倍率、top-k、卡数、序列长度、TPOT、吞吐，出现两次以上就要复核。发布前逐条对原表。

## 三、说话位置

写 AI 知识空间文章，以 AI 大模型工程师的身份说话。写 OS、嵌入式、自动驾驶文章，以对应领域的工程师身份说话。

内部回答五件事。

1. 谁在说，凭什么知道。
2. 什么事情让他现在想说。
3. 手里有哪些能托住文章的材料，比如动作、数字、时间、版本、原话、失败、代价。
4. 他对哪一点有明确判断，依据是什么。
5. 读者读完上一段最会追问什么。

作者可以承认哪块只是推测，哪块查过资料，哪块到现在仍拿不准。查资料不等于亲历，两者都写清楚。

材料核对不写成个人工作日志。少用“我拿……对了一遍”“我把……查了一遍”“我核过……”。把材料摆出来，用“把……放在一起核对”“对着……看一遍”让读者跟着核。第一人称留给判断和拿不准，比如“这一点我拿不准”“我倾向于保留高精度层”。

## 四、真实性

数字、版本号、许可证、价格、产品能力写作前重新确认。职位、政策、软件版本会变。一手材料优先。论文、正式文档、源码、config.json、官方模型卡。媒体与二手分析只用来补背景和交叉核对。

来源冲突时，说明怎样取舍，不挑最适合故事的一条写死。数据写完继续走一步，说明它让谁多花多少时间、少付多少钱、增加哪种选择或受什么限制。一个案例不能代表整个行业。

产品状态分开记录。已开放、邀请测试、宣布即将提供、长期愿景、行业猜测，不混写。标题只写到当前事实允许的位置。

用户提供截图，不补注册和运行过程。用户记不清原话，写大意或请确认。完全靠公开资料写成的文章，开头附近留一处真实的检索痕迹，比如“把能找到的报告和 config 放在一起核对，公开细节其实很少”。后面不用反复声明谨慎。引用别人的话第一次出现时说明是谁说的。

声称强度不超过证据强度。

| 强度 | 用词 | 适用证据 |
|---|---|---|
| 强 | 证明、首次、最先进、显著提升 | L1，且确实有对应数据 |
| 中 | 表明、说明、与……一致 | 合理但有开放性的发现 |
| 弱 | 可能反映、看起来、推测 | 猜测 |

真实结果与预期结果措辞分离。实测、已实现、已开放，与将提供、预计、即将，绝不混写。

### 数字口径

几种数字不能直接比较，写的时候分开。

- 三种口径分开标注。厂商离线自测、第三方实测、单算子微基准。跨口径比较处明写“不能直接对比”。
- 推算和官方数据分开措辞。官方写“官方 recipe 给的数”，自算写“按 9.66ms / 43 层推算”。
- 墙钟预算和纯计算耗时分开。225µs 是单卡单层的墙钟分摊，不是矩阵乘的纯计算时间。
- global batch 和单卡吞吐分开。两个数不能直接相乘相除。
- 单算子加速比和整网 TPOT 分开。单算子数字不能直接加到整网指标上。
- 跨平台比 TPOT 可以，比吞吐要谨慎。不同平台的精度方案和 kernel 支持不同。
- 型号和版本分开。同一系列的不同版本可能不是一套结构。

### 细节

一条 config 参数要说明它改变什么。一次编译报错要说明它如何暴露问题。一个性能数字要说明它相对谁、在什么条件下快多少。装饰性细节全部删除。无来源的精确时间、天气、神态、房间摆设。没有来源又不改变后文的细节，越具体越假。技术知识等读者问到再出现。一段背景能解释为什么只能这样选，或能推翻直觉，才放进来。只证明作者知道很多，删掉。

## 五、语言

### 中文怎么顺

先说谁做了什么，再补时间、原因和条件。一句话里三四个“的”，先找做事的人。删掉一半连词。中文小句靠语序和事理相接。长短句有高低差。十个字的句子挨着四十个字的句子。普通地方用普通句子结束，不要每段都用短判断收尾。

开头第一段不用孤立的数字或名词短语，第一句尽量有主语和动作，读者才知道谁在做什么。

该重复的词就重复，不要换同义词躲。动词直接写。把流程改顺了，不写“完成了对流程的优化”。动作、数字、原话已经把意思写出来就停住，不追一句解释。留白只省读者自己能得到的部分。

### 成稿绝对不能出现

| 类别 | 禁止 | 改成 |
|---|---|---|
| 标点 | 中文冒号、英文冒号、破折号 | 用逗号、句号，或引出人物原话 |
| 翻案 | 不是 A 而是 B、并非 A 而是 B、不在于 A 而在于 B、与其说 A 不如说 B、表面 A 实际 B、看似 A 实则 B、你以为 A 其实 B、A 不重要重要的是 B | 正面下判断，依据放旁边 |
| 排比 | 三项以上同构排比，同一句型连排三次 | 留两项，第三项换说法或删掉 |
| 名词化 | 进行优化、实现提升、完成了对……的 | 改顺了、从 X 降到 Y |
| 黑话 | 赋能、抓手、商业闭环、能力沉淀、拉通、底层逻辑、顶层设计、认知跃迁、价值释放、降本增效、全链路、组合拳、打开想象空间、结构性机会、关键命题、深层逻辑、技术底座、公共底座、技术主权、单点风险、主脊柱、材料锚点、认知增量、迭代闭环 | 写具体动作和对象 |
| 语境词 | 沉淀、颗粒度、对齐、协同、链路、生态位、心智、范式、方法论、核心变量、打法、想象空间、闭环、不丢 | 本义准确时保留，抬价时改写 |
| 路标 | 更微妙的是、还有一层、只说对了一半、值得注意的是、需要指出的是、从某种意义上说、说白了、说穿了、先说结论 | 直接写事实 |
| 借喻 | 仓库、抽屉、温度、死亡、坍塌、浪潮、钥匙、底座 | 写本义；解释性类比按 `docs/explanation-patterns.md` |
| 抒情 | 给抽象名词配具体动词，写时间、焦虑、情绪的形状 | 删掉，回到具体事实 |
| 结尾 | 升华到时代、文明、未来，重新摘要全文 | 回到具体事实，给尺子和提醒 |

解释性类比是例外，必须给出结构映射和失效边界，且不能替代证据。拟人必须写明是把组件想成角色，不能写成事实。分层讲解按内容深度排，不贴新手、高手、入门、进阶、专家标签。引用原话命中以上禁令时改成转述，不能靠引号保留。

### 删表演性中文

假深刻，单句截图好看放进正文没用的，删。假具体，无来源的精确细节，删。抽象名词，一句话能换进十篇文章，删。装饰性比喻换场，先还原成本义。解释性类比保留，检查映射和边界是否成立。

### 写时红牌

出现下面这些想法就停。它们是模型记忆冒充材料的信号。

| 想法 | 正确动作 |
|---|---|
| 我记得这个参数是 8 | 停。不确定就省略数字 |
| 我记得这篇论文用了三阶段 | 停。没读全文只写引证级 |
| 这个场景大概需要…… | 停。量级只写用户给的 |
| 背景应该提一下领域发展史 | 停。超出 L0 必须有来源，找不到就不写 |
| 加个失败案例更能说明问题 | 停。不编造案例，用用户亲历 |
| 补上原理细节更像技术文 | 停。没读到的机制不补，缺材料就明说 |
| 加一段实践更像教程 | 停。实践要来自真实材料，能跑、能验证，不编命令 |

## 六、审稿流程

初稿写完，按顺序过五遍。不要跳，也不要一边改语言一边改结构。

### 第一遍 结构

先看谁在说。作者凭什么知道这件事。哪几段换一个模型也能原样写出来，这类段落优先补材料来路或删掉。

再看六段是否齐，问题链有没有断点，痛点和解法是否一一对应。

- 开场有没有一个具体场景，带角色、数字或后果。
- 原理段有没有一句话结论、一个关键约束、一个可核验的量。
- 痛点段和解法段是否一一对应。
- 每个解法有没有上一代缺口、这一代动作、收益、新代价。
- 具体实践有没有和原理里的量对上。
- 标题是否带编号、概括内容，没有“痛点”“解法”“收口”。
- 结尾有没有尺子和落地提醒，没有重新摘要全文。

### 第二遍 证据

逐条核对事实、数字、引语和声称强度。

- 每个数字有没有来源、基线、适用条件。
- 自算数字有没有写推算过程。
- 强词有没有 L1 证据。
- 来源冲突有没有说明取舍。
- 产品状态有没有混写。
- 有没有把单算子加速比加到整网指标上。
- 有没有把离线吞吐当线上延迟。

### 第三遍 实践

把代码跑一遍，把配置对一遍，把步骤走一遍。

- 代码能不能跑，输入输出是否写清。
- 配置参数名是否真实，改变什么是否写清。
- 步骤有没有预期结果，失败时先查哪里。
- 验证方案是否同模型、同精度、同 batch、同序列长度分布。
- 实践算出来的数，能不能解释原理里的那个数。

### 第四遍 语言

跑 `python scripts/check_prose.py <稿件路径>`，硬禁令清零。再读一遍。

- 有没有冒号、破折号、翻案句、三项以上排比。
- 有没有黑话、借喻包装、洞察路标。
- 有没有名词化写法。
- 句子长短有没有高低差。
- 段落有没有统一的短句鼓点。
- 开头第一句有没有主语和动作。

### 第五遍 终读

从头到尾读一遍，只看三件事。

- 开头能不能让读者一句话说出文章在讲什么。
- 每一节开头能不能接住上一节留下的问题。
- 最后两段分别删掉再读，删掉更有力就让文章提前结束。

## 七、审稿清单

发现按严重度分级。阻断项必须有具体改法，不能只写“重写”。存在阻断项就不能交稿。

### 阻断发布

- 无来源的关键事实。
- 编造的数字、案例、对话或亲历。
- 来源冲突挑好的写。
- 声称强度远超证据。
- 具体实践的代码跑不通，或配置/命令是编的。
- `check_prose.py` 硬禁令未清零。

### 读者会追问

- 一句话论点和正文对不上。
- 问题链断裂，某一节没有回答上一节留下的问题。
- 痛点和解法对不上。
- 某个解法只有收益，没有新代价。
- 某一节没有新增机制、反例、代价或边界。
- 类比没有边界，或者删掉类比后机制段也不成立。
- 实践和原理各讲各的，代码算的不是前面那个数。

### 打磨

- 句子太长，主干来得太晚。
- 措辞空泛，动词被名词化。
- 过渡生硬，段落之间靠“首先、其次、最后”排队。
- 表格或图没有引导句和解释。

## 八、检测脚本

运行 `python scripts/check_prose.py 稿件路径`。脚本把冒号、破折号、翻案句、硬停词、模型路标、绝对禁用的黑话和占位标记判为失败，命中就改到清零。

占位标记指 `[待核验]`、`[TBD]`、`[citation needed]` 这类括号内待办。警告项比如句长变异系数、连词密度、段落节奏、借喻簇、过度声称词、状态混写、泛化痛点提问和水平分层标签，需要人工判断。

过度声称词，首次提出、最先进、显著提升，对照证据层级决定降级还是保留。真实状态词与计划状态词同段并存，比如已上线与将提供，检查是否把计划写成了事实。解释性类比是否成立，脚本判断不了，按 `docs/explanation-patterns.md` 人工检查。借喻簇警告可能打到解释性类比，先看映射和边界，再决定删不删。

## 九、交付

交付门禁见 `AGENTS.md`。顺序是，审稿完成，跑检测脚本，跑构建，检查页面和搜索索引，最后列来源。
