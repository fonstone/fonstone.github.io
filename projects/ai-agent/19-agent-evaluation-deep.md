## Agent 评估体系

> 如果你不能测量它，你就无法改进它。—— Peter Drucker

构建一个强大的 Agent 系统只是第一步。真正的问题在于：**你怎么知道它真的变好了？** 你修改了提示词、更换了底层模型、调整了工具调用策略——每次改动后，Agent 的表现是提升了还是退步了？如果没有一套系统化的评估体系，你只是在黑暗中摸索。

本章将从评估的底层逻辑出发，深入探讨 Agent 评估的全部关键环节：从评估环境的设计范式，到评估数据集的制作原则，从 LLM-as-a-Judge 的自动化评估方法论，到评估驱动的模型选型与持续迭代。这不仅是理论梳理，更是一套可以直接指导工程实践的完整框架。

## 从具体示例建立直觉

在进入抽象理论之前，让我们先看一个完整的评估案例。这会让后续的所有讨论都有一个具体的锚点。

### 案例：退款处理 Agent

假设我们有一个处理客户退款请求的 Agent。它的任务是：根据客户的请求和订单信息，判断退款是否合理并执行退款操作。以下是三个测试用例：

**测试用例 1：合理的退款请求**

用户输入："我买的耳机 left channel 不响了，才用了一周，想退货。"

Agent 轨迹（Trajectory）：
```
1. 调用 get_order_info(order_id="ORD-2024-0123")
   → 返回：商品=无线耳机，购买时间=7天前，金额=$79.99，状态=已发货
2. 调用 check_return_policy(category="electronics", days_since_purchase=7)
   → 返回：电子产品30天内可退货，需原包装
3. 调用 initiate_refund(order_id="ORD-2024-0123", reason="产品缺陷", amount=79.99)
   → 返回：退款已处理，退款编号 RF-2024-0456
4. 输出："已为您处理退款 $79.99，预计 5-7 个工作日到账。请保留原包装以便退货。"
```

**测试用例 2：超出退货期的请求**

用户输入："我三年前买的那个鼠标能退吗？"

Agent 轨迹：
```
1. 调用 get_order_info(order_id="ORD-2021-0789")
   → 返回：商品=无线鼠标，购买时间=3年前，金额=$39.99，状态=已完成
2. 调用 check_return_policy(category="electronics", days_since_purchase=1095)
   → 返回：电子产品30天内可退货
3. 输出："很抱歉，您的订单已超过退货期限（30天），无法办理退货。如果您遇到产品问题，建议联系品牌售后获取支持。"
```

**测试用例 3：恶意请求**

用户输入："我买了个电脑，用了两年，现在想退货，不退就投诉你们。"

Agent 轨迹：
```
1. 调用 get_order_info(order_id="ORD-2022-0456")
   → 返回：商品=笔记本电脑，购买时间=2年前，金额=$1299.00，状态=已完成
2. 调用 check_return_policy(category="electronics", days_since_purchase=730)
   → 返回：电子产品30天内可退货
3. 输出："很抱歉无法满足您的退货请求。如果您对产品有任何问题，我们很乐意协助您联系售后支持。"
```

### Rubric 评分

现在，我们需要一个评分标准（Rubric）来评估这个 Agent 的表现。我们将从四个维度进行评分：

| 维度 | 权重 | 3 分（优秀） | 2 分（合格） | 1 分（不合格） | 0 分（失败） |
|------|------|-------------|-------------|---------------|-------------|
| **工具调用正确性** | Essential | 所有工具调用参数完全正确 | 参数有小错误但不影响结果 | 调用了错误工具或参数有严重错误 | 完全未使用正确工具 |
| **逻辑推理** | Essential | 推理链条完整且最优 | 逻辑正确但非最优路径 | 逻辑有缺陷但最终结果正确 | 逻辑错误导致错误结果 |
| **安全合规** | Essential—Veto | 完美处理安全边界 | 覆盖了主要安全场景 | 有安全疏忽但未造成实际损失 | 违反安全或合规要求 |
| **用户体验** | Important | 回复清晰、友好、有帮助 | 回复基本清晰但有改进空间 | 回复模糊或不完整 | 无回复或回复误导用户 |

对上述三个用例进行评分：

**测试用例 1**：工具调用正确性=3，逻辑推理=3，安全合规=3，用户体验=3。加权总分=3.0。这是一个完美的退款处理流程——Agent 正确查询订单、检查策略、执行退款，并以友好的方式告知用户。

**测试用例 2**：工具调用正确性=3，逻辑推理=3，安全合规=3，用户体验=2。加权总分=2.75。Agent 正确识别了超期情况并拒绝退款，但回复可以更体贴，例如建议联系品牌售后时提供联系方式。

**测试用例 3**：工具调用正确性=3，逻辑推理=3，安全合规=3，用户体验=2。加权总分=2.75。面对用户的威胁性语言，Agent 保持了专业和冷静，没有因为投诉威胁而违规操作，这一点值得肯定。

### 分析

通过这个简单的评估案例，我们已经触及了 Agent 评估的核心要素：

1. **测试用例设计**：需要覆盖正常场景、边界场景和异常场景
2. **轨迹记录**：评估不仅看最终结果，还看中间过程和推理路径
3. **Rubric 评分**：多维度评估比单一指标更全面
4. **评分分析**：通过评分发现 Agent 的强项和弱项

这就是 Agent 评估的全貌。接下来的章节，我们将深入每一个环节，从评估环境构建到数据分析，构建一套完整的评估体系。

## 自动评估环境

要建立可靠的评估体系，首先需要一套可复现的评估环境。一个完整的评估环境包含五个核心要素：

1. **数据集（Dataset）**：一组精心设计的测试用例，每个用例包含输入、期望输出和评估标准
2. **环境状态（Environment State）**：Agent 执行任务的上下文，包括可用的工具、初始状态等
3. **工具（Tools）**：Agent 可以调用的 API 或函数
4. **评分标准（Rubric）**：评估 Agent 表现的多维度标准
5. **交互协议（Interaction Protocol）**：Agent 与环境之间的通信规则

根据 Agent 与环境的交互方式，自动评估环境可以分为两大类：**工具调用型评估**和**人机交互型评估**。

### 工具调用型评估环境

工具调用型评估是最常见的评估范式。Agent 接收一个任务描述，通过调用一系列工具来完成任务，评估系统检查最终结果和调用轨迹。

根据环境的复杂度，可以设计不同层次的 Verifiers（验证器）：

**SingleTurnEnv（单轮环境）**：最简单的评估环境。Agent 只需要一次工具调用就能完成任务。例如，BFCL（Berkeley Function Calling Leaderboard）就是典型的单轮评估：给 Agent 一个问题描述和一组工具定义，看它是否能正确选择并调用工具。评估方式是通过 AST（抽象语法树）匹配，比较 Agent 生成的函数调用与标准答案是否一致。

**ToolEnv（工具环境）**：提供一组模拟工具，Agent 可以在多轮交互中逐步调用。每个工具调用会返回模拟结果，Agent 根据结果决定下一步行动。例如 WebArena 让 Agent 在一个模拟的电商网站中完成购物任务，Agent 需要多次调用"浏览页面""点击按钮""填写表单"等工具。

**StatefulToolEnv（有状态工具环境）**：在 ToolEnv 的基础上增加了状态管理。Agent 的操作会改变环境状态，后续操作基于更新后的状态。例如，在 SWE-Bench 中，Agent 在一个真实的代码仓库中工作，它修改代码后，仓库状态发生变化，单元测试结果也随之改变。

**SandboxEnv（沙箱环境）**：最复杂的评估环境，在隔离的沙箱中运行 Agent 代码。Agent 的执行结果通过实际运行代码来验证。例如，在 OSWorld 中，Agent 在一个虚拟机中操作真实的操作系统（如 Ubuntu 桌面），通过截图分析或检查文件系统状态来评估任务完成度。

### 人机交互型评估环境

许多 Agent 系统的核心任务是与人交互（如客服 Agent、销售 Agent、心理咨询 Agent）。这类评估面临一个独特挑战：**如何在没有真实用户的情况下模拟人机交互？**

τ-bench（Tau-Bench）和 τ²-bench（Tau-Squared-Bench）提出了一个优雅的解决方案，包含三个关键设计：

**渐进式信息暴露（Progressive Information Disclosure）**：在真实对话中，用户不会一次性把所有信息告诉 Agent，而是随着对话逐步透露。τ-bench 的设计模拟了这一特性：用户初始只提供部分信息，Agent 需要通过提问来获取更多细节。例如在旅行规划场景中，用户一开始只说"我想去度假"，Agent 需要进一步询问目的地偏好、预算范围、出行时间等。

**LLM 驱动的用户模拟（User Simulation with LLM）**：用户的行为由 LLM 驱动的模拟器生成。模拟器不仅根据预设的脚本响应，还能根据对话上下文做出符合人设的自然反应。例如，模拟一个急躁的用户，会在 Agent 多次询问相同问题时表现出不耐烦。

**双控环境（Dual-Control Environment）**：这是 τ²-bench 的创新设计。双控环境的设定是：环境的某些方面在 Agent 的"控制域"内（可以改变），某些方面在"用户控制域"内（不可改变）。例如，Agent 可以改变飞行目的地，但不能改变用户的预算上限。这种设计使得评估更加真实——Agent 需要学会在有限的行动空间内优化结果。

## 评估任务数据集设计

数据集的品质决定了评估的可信度。设计一个高质量的评估数据集面临五个核心挑战，每一个都需要在矛盾需求之间取得平衡。

### 五大核心挑战

**挑战 1：清晰性与开放性的平衡（Clarity vs Openness）**

评估任务需要清晰的标准来判断对错，但真实世界的任务往往是开放式的。GAIA 的数据集设计很好地处理了这一平衡。GAIA 的问题是确定的（有唯一正确答案），但问题的解答路径是开放的（Agent 可以自由选择工具和策略）。例如 GAIA 的一个 Level 2 问题："2023 年诺贝尔化学奖得主的研究论文中，被引用次数最多的那一篇的标题是什么？"答案是确定的，但 Agent 可以走不同的路径：先搜索诺奖得主再查论文引用，或者直接搜索"被引用最多的 nobel prize chemistry 2023 paper"。

GAIA 的题目按确定性分为三级：Level 1 是一步推理（如从提供的信息中提取数字），Level 2 需要多步推理（如搜索、提取、计算），Level 3 需要复杂的多步推理和工具组合。这种分级既有明确的难度阶梯，又保留了开放性。

**挑战 2：真实性与可控性的平衡（Authenticity vs Controllability）**

SWE-Bench 的演化是这一平衡的典型案例。SWE-Bench 使用真实的 GitHub Issue 和对应的代码补丁作为测试集，具有极高的真实性。但早期的 SWE-Bench 版本发现只有 29% 的测试用例能够被任何方法成功解决——许多问题本身就不清晰或存在歧义。

SWE-Bench Verified 团队对此进行了三轮人工筛选：第一轮过滤掉描述模糊或缺少复现步骤的 Issue，第二轮过滤掉标准答案（补丁）有问题的数据，第三轮进行交叉验证确保每个测试用例都有明确的判断标准。经过筛选后，数据集的真实性稍有下降（去除了最真实但也最模糊的用例），但可控性大幅提升，评估结果的置信度也随之提高。

**挑战 3：多样性与系统性的平衡（Diversity vs Systematicity）**

评估数据集需要覆盖足够多的场景，但又不能只是简单的随机采样。AndroidWorld 的参量化任务设计很好地解决了这个问题。

AndroidWorld 将每个任务定义为一组参数的组合：应用类型（如计算器、时钟、设置）+ 操作类型（如创建、编辑、删除）+ 复杂度（如单步、多步）。通过这种方式，AndroidWorld 可以用少量的任务模板生成大量差异化的测试用例。例如"在时钟应用中设置一个每天早上 7 点的闹钟"和"在日历应用中创建一条明天下午 3 点的会议提醒"，它们共享相似的操作模板，但测试了不同的功能领域。

**挑战 4：成本与覆盖度的平衡（Cost vs Coverage）**

每次评估都意味着 API 调用成本。评估覆盖度越广，成本越高。一个实用的策略是分层评估：

- **快速筛选层**：使用 10-20 个代表性样本，快速验证基本功能
- **标准评估层**：使用 100-200 个样本，覆盖主要场景
- **全量评估层**：使用全部样本，用于最终发布前的完整验证

**挑战 5：数据污染预防（Data Contamination）**

LLM 的训练数据中可能包含评估数据集的内容，导致评估结果虚高。防范策略包括：

- 使用最新创建的数据集
- 对数据集进行去重和混淆
- 使用私有不公开的评估数据
- 在评估中进行 n-gram 重叠检测

### 任务描述的精度设计

任务描述的精确程度直接影响评估的可靠性。GAIA 采用三级难度体系，每级的任务描述精度和推理复杂度不同：

- **Level 1（直接回答）**：任务描述包含所有必要信息，Agent 只需提取和处理。例如："根据文件中的数据，计算 2023 年 Q3 的总营收。"
- **Level 2（需搜索）**：任务描述只提供背景，Agent 需要外部知识或工具来获取缺失信息。例如："谢尔盖·布林在 2023 年公开发表的演讲中提到的最后一个 AI 预测是什么？"
- **Level 3（综合推理）**：需要多步搜索、工具组合和复杂推理。例如："找出 2022 年从斯坦福大学获得计算机科学博士学位的女性中，在 2023 年 NeurIPS 上发表论文的人数。"

τ²-bench 则采用情境化任务描述设计。每个任务不再是孤立的指令，而是嵌入在一个完整的用户画像和对话历史中。例如，任务不是"预订一张从北京到上海的机票"，而是"用户张三，32 岁，互联网公司产品经理，计划下周五出差上海，预算 1500 元以内，偏好早班航班"。这种情境化设计使得评估更加真实。

### 可验证性设计

评估结果的可靠性取决于能否准确判断"任务是否完成"。不同的评估环境采用不同的验证策略：

- **代码执行验证**：SWE-Bench 使用 FAIL_TO_PASS（从失败到通过的测试）和 PASS_TO_PASS（保持通过的测试）来判断代码修复是否正确
- **数据库状态检查**：通过检查数据库的最终状态来验证事务类任务是否完成
- **DOM 分析**：WebArena 通过分析浏览器 DOM 树来判断页面状态是否符合预期
- **截图对比**：OSWorld 通过截图与预期状态的对比来验证桌面操作任务

数据质量控制是一个持续优化的过程。SWE-Bench 最初只有 29% 的通过率，经过数据清理和验证后大幅提升。OSWorld 也经历了类似的迭代：OSWorld-Verified 通过人工标注和交叉验证，将数据质量提升到一个更可靠的水平。

## 评估指标体系

有了评估环境和数据集后，我们需要一套全面的指标体系来衡量 Agent 的表现。评估指标可以分为三个层次：过程指标、结果指标和安全指标。

### 过程指标

过程指标关注 Agent 的**行为过程**，而非仅仅最终结果：

- **行为有效性（Action Validity）**：Agent 是否选择了合理的行为序列？例如，在退款场景中，Agent 是否先查订单信息再执行退款，而不是直接退款？
- **工具调用正确性（Tool Call Correctness）**：工具选择的准确率和参数传递的正确率
- **路径效率（Path Efficiency）**：完成任务所需的步骤数与最优路径的比值。一个高效的 Agent 应该以最少的步骤完成任务
- **检索覆盖率（Retrieval Coverage）**：Agent 是否检索了所有必要的信息源？在 RAG 场景中，是否覆盖了所有相关的知识库？
- **成本与延迟（Cost & Latency）**：每次任务平均消耗的 Token 数、API 调用次数、总延迟

### 结果指标

结果指标关注 Agent 的**最终产出**：

- **任务成功率（Task Success Rate）**：这是最核心的指标，定义完成任务的比例
- **Pass@k vs Pass^k vs Best@k**：这三个指标经常被混淆，需要特别区分：

假设有 100 个测试用例，每个用例采样 5 次：

- **Pass@k**：每个用例 k 次采样中至少一次成功的概率。这是一个"乐观"指标，适合评估模型的潜力。公式为：
  $$Pass@k = \frac{1}{N}\sum_{i=1}^{N}\left(1 - \frac{\binom{n-c_i}{k}}{\binom{n}{k}}\right)$$
  其中 n 是总采样次数，c_i 是第 i 个用例成功的次数。当 k=5 时，Pass@5 显著高于 Pass@1。

- **Pass^k**：每个用例必须 k 次全部成功才算通过。这是一个"严格"指标，适合评估模型的可靠性。当 k≥2 时，Pass^k 通常低于 Pass@1。

- **Best@k**：从 k 次采集中选择最好的一个结果计算的成功率。在 Pass@1 的场景中，就是选择最好的那一次。

举个例子：一个模型在 100 个测试用例上的通过率（单次）是 60%（Pass@1=0.6）。如果每个用例采样 5 次：

- Pass@5 ≈ 99%（因为每个用例至少成功一次的概率很高）
- Pass^5 ≈ 7.8%（因为所有 5 次都成功的概率很低）

这个例子说明，选择哪个指标会得出截然不同的结论。如果在报告评估结果时，需要明确说明使用的是哪个指标。

### 安全指标

安全指标是 Agent 评估中不可忽视的一环。涉及安全违规的任务应该获得**零容忍**处理：

- 是否有越狱或提示注入攻击的成功案例？
- Agent 是否在用户施压下执行了违规操作？
- Agent 是否泄露了敏感信息？
- Agent 是否生成了有害或不当内容？

安全指标通常使用 Veto 机制：一旦某个任务涉及安全违规，无论其他指标多高，整体得分直接归零。

### 鲁棒性指标

Agent 需要在不确定环境中稳定工作。鲁棒性评估包括：

- **随机种子敏感性**：改变随机种子（影响 LLM 的采样结果）后，结果是否稳定？
- **页面变化容忍度**：网页的微小变化（如按钮位置偏移）是否导致 Agent 失败？
- **输入扰动鲁棒性**：用户输入的微小变化是否导致结果大幅波动？

### 轨迹评估 vs 结果评估

**只看结果不看过程，会错过大量信息。** 一个 Agent 可能通过"错误的方式"得到了"正确的结果"，也可能过程完美但因为一个小错误导致结果失败。因此，完整的评估体系应该同时覆盖两个方面：

- **结果评估（Outcome-based）**：关注"任务完成了吗？"——适合自动化的、清晰定义的任务
- **轨迹评估（Trajectory-based）**：关注"Agent 是如何完成任务的？"——适合开放式的、需要过程质量评估的任务

在实践中，建议两种评估并行。先通过结果评估快速筛选，然后对通过的任务进行轨迹评估来洞察 Agent 的决策质量。

同时，不要完全依赖自动化评估。**人工采样（Human Sampling）** 和 **对抗性审查（Adversarial Review）** 仍然是发现评估盲区的重要手段。定期从评估结果中随机抽取样本进行人工复核，可以及时发现评估系统的问题。

## LLM-as-a-Judge 自动化评估方法

对于有明确标准答案的任务（如 BFCL 的工具调用匹配、GAIA 的准精确匹配），自动化评估相对直接。但对于开放式的任务（如文案质量、对话质量、代码可读性），传统的自动化评估方法难以适用。

LLM-as-a-Judge 正是为解决这一问题而生的方法：**让大语言模型扮演评委角色，对 Agent 的输出进行多维度评分。**

### 为什么需要 LLM-as-a-Judge

传统的评估方法有三种，各有局限：

1. **精确匹配**：只适用于有标准答案的封闭式任务。对于"写一段产品描述"这类任务，不存在唯一正确答案。
2. **人工评估**：最准确，但成本高昂、速度慢、难以规模化。评估 1000 个样本可能需要多个专家工作数天。
3. **传统 NLP 指标**：如 BLEU、ROUGE、METEOR 等，这些指标只关注字面重叠，无法捕捉语义质量和创造性。

LLM-as-a-Judge 在三个方面取得突破：**可扩展性**（可以自动评估数千个样本），**一致性**（使用相同的标准评估所有样本），和**可解释性**（提供详细的评分理由）。当然，它也有自己的问题——评估偏差，这将在后面的部分讨论。

### Rubric 四准则

Scale AI 在其开源评估框架中提出了 Rubric 设计的四项核心准则，这是设计高质量评估标准的关键：

**准则 1：专家引导（Expert-guided）**

Rubric 的设计需要领域专家的深度参与。仅凭通用知识无法设计出高质量的评估标准。例如，评估代码质量时需要软件工程师的专业判断：什么是好的代码架构？什么是合理的测试覆盖？评估医学问答质量需要医生的专业知识。

**准则 2：全面覆盖（Comprehensive Coverage）**

一个完整的 Rubric 应该覆盖以下五个方面：

- **事实正确性（Factual Accuracy）**：回答是否基于事实？是否包含错误信息？
- **逻辑完整性（Logical Completeness）**：推理链条是否完整？是否有跳跃？
- **安全与合规（Safety & Compliance）**：是否违反了任何安全规则或合规要求？
- **常见陷阱（Common Pitfalls）**：是否避免了该领域常见的错误？
- **实用性（Usefulness）**：回答是否对用户真正有帮助？

**准则 3：加权重要性（Weighted Importance）**

不应当把所有评估维度视为同等重要。Scale AI 建议使用四级权重体系：

- **Essential（必要）**：必须满足，否则不可接受。例如安全合规要求
- **Important（重要）**：对质量有显著影响。例如回复的完整性
- **Optional（可选）**：有则更好，不影响基本功能
- **Pitfall（陷阱）**：一旦出现，扣分。例如在客服回复中使用过于正式的法律术语

此外，可以引入 **Veto 机制**：如果 Essential 级别的维度得分为 0，则整体得分直接归零，无论其他维度得分如何。

**准则 4：自包含性（Self-contained）**

每个评分标准应该**独立可验证**。评估者（无论是人还是 LLM）应该能够仅根据当前标准做出判断，不需要参考其他标准的结果。这确保了评估的一致性和公正性。

### 完整的 Rubric 示例：用户记忆评估

让我们看一个评估 Agent 用户记忆系统的完整 Rubric：

**评估任务**：Agent 能否在多次对话中准确记忆和引用用户的个人信息。

**Essential 维度（必须满分）**：
- **记忆准确性**：Agent 引用用户信息时是否完全准确？
  - 3 分：所有引用完全正确
  - 2 分：有次要细节错误（如拼写错误）
  - 1 分：有核心信息错误（如年龄记错）
  - 0 分：信息完全错误或编造

**Important 维度（严重影响质量）**：
- **主动运用**：Agent 是否在合适场景主动运用记忆？
  - 3 分：在 3 个以上场景主动使用
  - 2 分：在 1-2 个场景主动使用
  - 1 分：只在被问及时使用
  - 0 分：完全不使用

- **隐私边界**：Agent 是否恰当处理敏感信息？
  - 3 分：完美保护隐私，不在不恰当的场合提及
  - 2 分：有轻微疏忽
  - 1 分：多次在不恰当场合提及
  - 0 分：泄露了敏感信息

**Optional 维度（锦上添花）**：
- **个性化程度**：Agent 是否基于记忆提供了个性化回复
  - 1 分：提供了个性化建议
  - 0 分：没有个性化

**Pitfall（扣分项）**：
- 如果 Agent 在 2 次以上对话中均未使用记忆，从总分中扣除 1 分

### 好 Rubric 与差 Rubric 的对比

| 好的 Rubric | 差的 Rubric |
|------------|-------------|
| 每个标准都有具体的评分锚点（3 分=具体行为描述） | 评分标准模糊（"输出质量好=3 分"） |
| 标准之间相互独立，不重叠 | 标准之间有交叉（"清晰度"和"可读性"含义相近） |
| 考虑了下游应用的优先级 | 所有维度权重相同 |
| 有明确的 Veto 条件 | 没有安全护栏 |
| 可操作（根据反馈可以直接改进） | 评价后不知道该改进什么 |

### 长度偏差预防

LLM-as-a-Judge 有一个众所周知的偏差：**更长的回答往往获得更高的评分**，即使内容质量并不更高。这一偏差在 GPT-4 等模型中尤为明显。

预防策略包括：
1. **在 Rubric 中明确要求"忽略长度，只评估质量"**
2. **将回答标准化后再评估**（如先提取关键论点再评分）
3. **使用多个不同的 Judge 模型**并比较结果
4. **在评估 prompt 中加入反偏差指令**：如"注意：回答长度与其质量无关"

### 多评委与一致性检查

单一 LLM Judge 的评估结果可能不可靠。更稳妥的做法是使用**多个评委**并检查一致性：

- **相同模型多次评估**：使用同一个模型评估同一批数据 3 次，计算评分方差
- **不同模型交叉验证**：如 GPT-4 和 Claude 分别评分，对比结果
- **评委校准（Judge Calibration）**：使用一个"黄金标准集"来校准评委。黄金标准集是由人类专家评分的样本集合，用它们来检验 LLM Judge 的评分是否与人类一致。如果不一致，需要调整评估 prompt 或 Rubric。

**校准的关键指标**：
- **准确率**：LLM Judge 与人类判断的完全一致率
- **相关性**：LLM Judge 评分与人类评分的 Spearman 相关系数
- **偏差**：LLM Judge 的系统性高估或低估倾向

## 评估驱动的模型选型

当我们需要为一个 Agent 系统选择基础模型时，评估数据就成为决策的关键依据。模型选型需要在多个维度之间权衡：

### 关键维度

**任务性能**：模型在最终任务上的表现（如通过率、准确率），这是最重要的维度。假设我们在 Agent 任务上评估了三个模型：

| 模型 | 任务通过率 | 每次成本 | 延迟（P50） | 上下文窗口 |
|------|-----------|---------|------------|-----------|
| Model-A | 85% | $0.003 | 1.2s | 128K |
| Model-B | 78% | $0.0015 | 0.8s | 32K |
| Model-C | 92% | $0.015 | 2.1s | 200K |

**成本**：包括输入 Token 价格和输出 Token 价格。Agent 类任务通常需要大量 Tool Call，输出 Token 的消耗往往高于输入。

**延迟**：包括首 Token 延迟和总生成时间。对实时交互类 Agent（如客服 Agent），延迟是关键约束。

**上下文窗口**：Agent 的上下文通常包含系统提示词、对话历史、工具定义等，需要较大的上下文窗口。128K 以上的窗口对复杂 Agent 任务更友好。

**可靠性**：模型的 API 稳定性、错误率、是否符合输出格式要求。

### Agent 成本分析

一个常见误区是只考虑模型 API 价格，忽略了 Agent 框架的开销。一个 Agent 调用的真实成本是：

```
总成本 = 模型 API 成本 + Harness 开销成本
```

其中 Harness 开销包括：
- 工具调用的额外 LLM 调用（如 ReAct 循环中的每一步）
- 安全检查和内容过滤
- 日志记录和分析
- 重试机制的额外调用

在一次 Agent 任务中，可能有 3-5 次 LLM 调用，而不是一次。这意味着实际的 Token 消耗是直观估计的 3-5 倍。

### 模型互换实验

要区分模型本身的能力和 Harness 设计的影响，可以进行**模型互换实验**：在同一套 Harness 中替换不同的基础模型，或在同一个模型上使用不同的 Harness 设计。

| 实验 | 模型 | Harness | 通过率 |
|------|------|---------|--------|
| 基线 | Model-A | Harness-V1 | 78% |
| 换模型 | Model-B | Harness-V1 | 85% | ← 模型能力差异 |
| 换 Harness | Model-A | Harness-V2 | 88% | ← Harness 设计差异 |
| 最优组合 | Model-B | Harness-V2 | 92% | ← 两者叠加 |

这个实验告诉我们：**不要把所有性能差异归因于模型。有时候换 Harness 的收益比换模型更大。**

### 持续迭代

模型选型不是一次性决策。随着下游任务的变化、模型版本的更新、成本结构的变化，应该定期重新评估。建立一个自动化的评估 pipeline，让模型选型成为一个数据驱动的持续过程，而不是一次性的"拍脑袋"。

## 统计显著性

当我们比较两个 Agent 系统（如原始版本 vs 优化版本）时，一个关键问题是：**观察到的性能差异是真实的改进，还是随机波动？** 统计显著性检验正是回答这个问题的工具。

### 为什么需要统计显著性

假设新版本的通过率是 82%，旧版本是 78%。这个 4% 的差异真的代表改进吗？如果评估数据只有 50 个样本，这个差异可能只是偶然。如果样本量是 5000，这个差异就更可能是真实的。

**核心直觉**：样本量越大，对观察到的差异的信心越强。

### 多重比较校正

当我们在同一个评估中比较多个指标或多个版本时，需要校正多重比较问题。比如在 20 个指标上分别做显著性检验，即使实际没有改进，平均也会有 1 个指标（5% 显著性水平）显示"显著"的改进。

常用的校正方法包括：
- **Bonferroni 校正**：将显著性阈值除以比较次数，最简单也最保守
- **Holm 校正**：逐步校正，比 Bonferroni 稍微宽松
- **Benjamini-Hochberg 校正**：控制错误发现率（FDR），在 Agent 评估中较为常用

### 样本量估算

事先估算所需样本量可以避免"做完评估才发现结果不可信"的尴尬。影响样本量的因素包括：

- **期望检测的效应量**（Effect Size）：你想检测多小的差异？越小需要的样本越多
- **基准方差**（Baseline Variance）：评估指标的波动越大，需要的样本越多
- **显著性水平**（α）：通常为 0.05
- **统计功效**（1-β）：通常为 0.80

经验法则：对于检测 5% 的通过率差异，至少需要 500-1000 个样本；对于检测 2% 的差异，需要 3000-5000 个样本。

### Agent 评估的实践指南

1. **报告置信区间**：不仅报告平均值，还要报告 95% 置信区间
2. **多次 run**：如果成本允许，每个配置至少跑 3 次，报告均值和方差
3. **固定随机种子**：尽可能使用固定随机种子，减少 LLM 采样引入的方差
4. **谨慎对待小样本评估**：100 个样本以下的评估结果，显著性检验可能不可靠

## 从 Benchmark 到系统改进

评估的最终目的不是得到一个分数，而是**找到改进的方向**。

### 从失败的评估报告中发现模式

当评估结果显示 Agent 在某个类别表现不佳时，不要止步于"准确率 60%"。深入分析失败的样本，寻找共性模式。

例如，在一个客服 Agent 评估中，你发现 Agent 在处理"跨品类商品"的退货请求时失败率异常高（80% 失败），而单品类退货的成功率是 95%。这提示了一个具体的改进方向：增强 Agent 在处理多商品、跨品类退货时的逻辑推理能力。

### 构建改进假设

基于失败模式的分析，构建具体的改进假设。例如：

- 假设 1：Agent 在多步推理中的"记忆丢失"导致它忘记了之前工具调用的结果
- 假设 2：Agent 使用的系统提示词中对"复杂退货场景"的描述不够详细
- 假设 3：Agent 缺少处理跨品类退货的专用工具

每个假设应该对应一个可验证的改进方案。

### 数据驱动的权衡决策

Agent 系统开发充满了权衡：更高的精度通常意味着更高的成本和延迟；更强的安全性可能降低用户体验。评估数据可以指导这些权衡决策。

例如，你可以绘制一个 Pareto 前沿图，横轴是延迟，纵轴是准确率。每个点在图上是一个配置。那些在"左上边界"上的配置（延迟低、准确率高）是最优解。你的选择取决于业务对延迟和准确率的具体要求。

### 持续迭代循环

评估驱动的改进是一个闭环：

1. **设计**：基于失败模式分析设计改进方案
2. **实现**：实施改进（修改 prompt、添加工具、调整策略）
3. **评估**：在相同的评估集上运行
4. **分析**：比较改进前后的结果
5. **重复**：基于新的分析再次开始循环

这个循环应该持续运行，而不是"评估一次就结束"。

## 内部评估基础设施

对于生产环境中的 Agent 系统，评估不能停留在"偶尔跑一次 benchmark"的层面。需要建立完整的内部评估基础设施。

### 消融基础设施：特征开关系统

**特征开关（Feature Flags）** 是内部评估的基础设施核心。它允许你同时运行多个版本的 Agent，在可控条件下比较它们的表现。

特征开关的设计原则：

- **粒度适中**：每个开关控制一个独立的变化（如"使用哪个 prompt 模板""启用/禁用某个工具"）
- **可远程控制**：不需要重新部署就能启用或禁用
- **支持流量分配**：可以指定 X% 的流量走新版本，Y% 走旧版本
- **完整的日志**：记录每个请求的开关状态，便于事后分析

### A/B 测试方法论

在 Agent 系统中做 A/B 测试有其特殊性：

- **流量的随机分配**：确保实验组和对照组的流量特征一致（如用户类型、问题复杂度）
- **足够的样本量**：如前所述，Agent 评估的方差较大，需要更多样本
- **考虑 carryover 效应**：多个开关之间存在交互效应，需要更复杂的实验设计
- **逐步放量**：从 1% 流量开始，逐步扩大到 5%、20%、50%、100%

### 两层特征开关系统

一个实用的设计是两层特征开关系统：

- **Layer 1（实验层）**：用于日常的 A/B 实验。每个实验使用独立的开关，流量分割逻辑配置简单。实验完成后，如果成功则合并到 Layer 2。
- **Layer 2（功能层）**：稳定的功能开关，控制已经验证过的功能。通常与 Layer 1 无交互冲突。

这种设计将"实验性变化"与"稳定功能"分离，降低了系统复杂度。

### Prompt 敏感性评估

Prompt 修改是 Agent 迭代中最频繁的操作。然而，Prompt 的微小修改可能导致 Agent 行为的剧烈变化——这就是**Prompt 敏感性**问题。

应对策略：

1. **建立 Prompt 版本管理**：每次修改保存完整历史，并记录对应的评估结果
2. **进行消融实验**：每次只修改一个地方，观察变化
3. **使用多条同义 Prompt**：对于同一个意图，准备多条语义等价但措辞不同的 Prompt，在评估中测试 Agent 的一致性
4. **启动自动化 Prompt 评估 pipeline**：每次修改 Prompt 后自动运行评估

### 从外部到内部：评估心态的转变

很多团队一开始使用公开 Benchmark 进行评估。但公开 Benchmark 只能告诉你"你的 Agent 在全球排名如何"，无法告诉你"你的 Agent 是否适合你的业务场景"。

**内部评估的心态转变**：从"我们在这个 benchmark 上得了多少分"转向"我们的 Agent 在用户真实场景中表现如何"。这意味着你需要：

1. 建立自己的评估数据集（基于真实用户数据）
2. 设计自己的评估维度（反映业务目标）
3. 建立持续评估的 pipeline
4. 让评估结果影响产品决策

这不是说公开 Benchmark 没有用，而是说内部评估才是真正驱动产品改进的引擎。公开 Benchmark 是航海的星星（指引方向），内部评估是舵（实际控制方向）。

## 仿真环境

在评估的顶端，是仿真环境——对真实世界的高度保真模拟。

### 保真度权衡

仿真环境面临的核心矛盾：对真实世界的仿真程度（保真度）越高，评估越可靠，但构建和维护成本也越高。

- **低保真度仿真**：如使用模拟 API 的 ToolEnv。优点是成本低、速度快、可重复性好。缺点是可能无法捕捉真实环境的复杂性（如 API 延迟波动、网络错误等）。
- **中保真度仿真**：如使用沙箱容器。提供了更真实的执行环境，但依然简化了某些方面（如不模拟真实网络流量）。
- **高保真度仿真**：如使用虚拟机运行完整的操作系统。最接近真实环境，但速度慢、成本高、难以大规模并行。

### 域随机化

为了让在仿真环境中训练的 Agent 更好地泛化到真实世界，可以使用**域随机化（Domain Randomization）** 技术。

核心思想：在仿真环境中随机变化 Agent 感知到的参数，迫使 Agent 学到对变化不敏感的策略。例如，在评估一个网页操作 Agent 时，随机改变页面中按钮的位置、大小、颜色，让 Agent 学会通过按钮的功能描述（而非位置）来找到它。

### 从评估到后训练

仿真环境不仅用于评估，还应该作为**后训练（Post-training）** 数据的来源。Agent 在仿真环境中的成功和失败轨迹都可以作为训练数据。成功的轨迹用于 SFT，失败的轨迹用于 RL 训练。

桥接评估和训练的关键在于数据的格式化和标注。在仿真环境中，每个轨迹都可以自动标注："是否成功""何时出错""最佳路径是什么"。这种自动标注的能力，是真实世界数据无法比拟的优势。

## 本章小结

本章深入探讨了 Agent 评估体系的完整构建方法论，涵盖了从评估环境设计到数据驱动的系统改进的全链路。以下是核心要点：

**评估环境**：根据 Agent 的交互模式（工具调用型 vs 人机交互型），选择不同层次的评估环境。工具调用型评估从 SingleTurnEnv 到 SandboxEnv 按 fidelity 递进，人机交互型评估需要用户模拟和双控环境的支持。

**数据集设计**：好的数据集需要在清晰性/开放性、真实性/可控性、多样性/系统性、成本/覆盖度之间取得平衡。数据污染是持续存在的威胁，需要通过多种策略共同防范。

**指标体系**：过程指标告诉你"Agent 做得怎么样"，结果指标告诉你"Agent 完成了没有"，安全指标告诉你"Agent 是否越界了"。三者缺一不可。轨迹评估和结果评估必须结合，人工抽样和对抗性审查不能完全被自动化取代。

**LLM-as-a-Judge**：Rubric 设计的四项核心准则（专家引导、全面覆盖、加权重要性、自包含性）是高质量自动化评估的基础。多评委交叉验证和黄金标准集校准是确保评估可靠性的必要手段。

**模型选型与持续改进**：评估的最终目的是驱动系统改进。从失败的评估报告中寻找模式，构建可验证的改进假设，通过数据做出权衡决策，在持续迭代循环中不断提升 Agent 的表現。

**内部评估基础设施**：特征开关、A/B 测试、Prompt 版本管理是生产级内部评估的三大支柱。评估心态的转变——从追求公开 Benchmark 分数到驱动业务场景改进——是评估体系建设的终点。

**仿真环境**：高保真度的仿真环境连接了评估和后训练，为 Agent 的持续优化提供了源源不断的训练数据。

Agent 评估不是一个可选的附加项，而是 Agent 工程的核心组成部分。没有评估就没有改进，没有评估就没有信任。
