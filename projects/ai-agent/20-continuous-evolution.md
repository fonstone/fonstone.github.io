## Agent 的持续进化

> "不是最强大的物种生存下来，也不是最聪明的，而是对变化最敏感、反应最快的。"——这不仅是达尔文主义的总结，也是 Agent 系统走向长期实用的核心信条。

当 Agent 从实验原型走向生产环境时，一个尖锐的问题浮出水面：**它今天做对了，明天还能做对吗？它能从错误中学习吗？它能随着业务变化自我更新吗？**

一个不会进化的 Agent，本质上就是一个不断贬值的资产。想象一下：你花了两周时间精心调试了一个客服 Agent，上线第一个月准确率 85%，你觉得效果不错。但三个月后，公司推出了新产品线、更新了退货政策、加上了 GDPR 合规要求——如果你不持续改进 Agent，它的准确率就会从 85% 一路跌到 60%。更糟糕的是，它可能在某个沉默的周末突然触犯合规红线，而你的团队毫无察觉。这类退化不是 Bug——它是"缺乏进化机制"的必然结果。

为什么许多 Agent 项目在 POC 阶段表现出色、上了生产却迅速崩塌？核心原因就是它们被设计成了"静态系统"——一次配置、永久运行。但真实的业务环境是动态的：用户需求在变、业务规则在变、底层 API 在变、法律法规在变。一个静态的 Agent 面对动态的世界，退化只是时间问题。

真实的业务系统需要的是能够在运行中不断吸收反馈、自我修正、逐步提升的活系统。本章将系统性地拆解 Agent 持续进化的完整方法论：从轨迹中提取学习信号，到四种不同的进化路径，最终到构建一个可长期运行的进化闭环。

## 从运行轨迹中获得学习信号

进化需要原料。对于 Agent 而言，进化的原料就是它在运行过程中留下的**轨迹（Trajectory）**。

轨迹是 Agent 从收到用户请求到产生最终输出的完整执行记录。它包含以下信息层：

- **输入层**：用户的原始输入、系统上下文、可用工具的清单
- **推理层**：Agent 的思考过程（Chain of Thought）、每一步的决策依据
- **行动层**：调用的工具名称和参数、每次调用的时间戳和耗时
- **反馈层**：每个工具返回的结果、环境状态的变更记录
- **输出层**：最终返回给用户的文本或结构化数据
- **元信息**：调用的模型名称、温度参数、Token 消耗、延迟

一条轨迹本质上就是 Agent 的"行为录像"——不只是结果快照，而是完整的过程记录。它的质量直接决定了你能从中提取多少学习信号。

### "保存经验"与"从经验中学习"的区别

很多团队做了第一步：把所有 Agent 的运行日志存进数据库。每天新增几十万条轨迹，数据库越来越大，但实际价值微乎其微。这只是"保存经验"，远非"从经验中学习"。

| | "保存经验" | "从经验中学习" |
|---|---|---|
| **数据形态** | 原始的、非结构化的 JSON 日志文本，冗余字段多 | 结构化的、分维度标注的信号数据，关键信息已提取 |
| **消费方式** | 出了问题才去翻日志，被动式查询，依赖个人经验 | 主动消费，定期自动分析，持续产出可操作的改进建议 |
| **分析粒度** | 单条日志的孤立查看，缺乏横向对比 | 跨轨迹对比、聚类、提炼规律，系统性地识别模式 |
| **输出产物** | 保存了但没有人看过，99% 的数据从未被访问 | 每次分析都产出"Top 5 失败模式"和"建议改进方向" |
| **信息覆盖** | 只知道"结果是否成功"（如果记录了的话） | 知道"为什么失败"、"在哪个维度失败"、"怎么改进" |

一个简单直观的判断方法：如果你的团队只是把运行轨迹扔进了 Elasticsearch，偶尔在出故障时查一下，那你做的是"保存经验"。如果你每周自动产出一份"Agent 行为诊断报告"，列出 Top 5 的失败模式及其根因分析——那你正在"从经验中学习"。

从保存经验到学习经验的跨越，需要在轨迹的消费端做三件事：

1. **结构化的提取（Structured Extraction）**：不要直接存储原始日志，而是在写入前先做一层结构化提取，把关键信号（决策点、工具调用、成功/失败状态）从非结构化的 LLM 输出中解析出来
2. **自动化的分析（Automated Analysis）**：定时任务定期扫描新轨迹，进行统计分析和模式识别，而不是等人来查
3. **闭环的反馈（Closed-loop Feedback）**：分析结果必须产生行动——要么更新知识库，要么修改 Prompt，要么自动提交 Issue——而不是仅仅停留在"分析报告"的 PDF 里

实现这三点需要一组专门的 Verifier（验证器），像一名质检员一样，逐层检查每条轨迹的质量。

### 三层轨迹验证结构

一条运行轨迹不可能只有"对"或"错"两种状态。一个 Agent 可能过程完美但结果错误（比如调用的外部 API 挂了），也可能结果偶然正确但过程荒谬（比如通过一连串错误的推理步骤碰巧得到了正确的答案）。因此，我们需要分三层来验证轨迹，每一层回答不同粒度的问题。

**第一层：结果验证（Result Verification）**

检查 Agent 的最终产出和环境状态。这是最基础的验证层，回答的问题是："任务完成了吗？"

结果验证的检查维度包括：

- **环境状态检查**：Agent 执行后，关键环境变量是否达到了预期值？例如：数据库中的订单状态是否从"待处理"变为"已退款"？文件系统是否生成了目标文件？用户收到的邮件是否包含了正确的订单号？
- **工具返回结果验证**：Agent 调用的每个工具是否返回了预期的结果？返回的数据是否符合 schema 定义？是否存在 API 返回了错误码但 Agent 没有在推理中处理的场景？
- **最终输出检查**：Agent 的最终输出是否包含了必要的核心信息？例如退款场景中是否提供了退款编号和预计到账时间？

一个典型的例子是 SWE-Bench 的验证方式：运行 Agent 生成的代码补丁，检查单元测试是否从 FAIL 变为 PASS。这就是纯结果级别的验证——不关心 Agent 是怎么生成补丁的，只关心最终结果是否让测试通过了。

但结果验证有它无法覆盖的盲区。考虑这个场景：一个客服 Agent 被要求"解释退货政策"。它流利地背诵了一大段政策文本——但引用的是三个月前的旧版本，而公司在昨天刚更新了政策。从结果验证的角度看，Agent 的输出看起来完全正确（语言流畅、逻辑自洽），但从实际业务的角度看，它给出了错误的信息。这就是结果验证的局限性——它只检查"是否输出了东西"，不检查"输出的东西是否基于正确的知识源"。

**第二层：过程验证（Process Verification）**

结果验证回答"是否完成"，过程验证回答"是否按规定完成"。一个 Agent 可能完成了任务，但完成任务的过程可能违反了业务规则或安全要求。

过程验证的检查维度：

- **业务规则合规**：Agent 的行为序列是否符合业务流程规范？例如，在退款场景中，是否先查退货政策再执行退款，而非直接退款？在医疗咨询场景中，Agent 是否在提供建议前先做了免责声明？
- **权限边界检查**：Agent 是否调用了它不应该调用的工具？是否访问了无权访问的数据？例如，一个被配置为只读的 Agent 是否尝试调用了写操作接口？
- **动作序列合理性**：步骤顺序是否合理？是否存在不必要的冗余操作？例如，是否在同一个对话中重复调用了同一个查询 API 三次（浪费 API 配额和 Token）？是否存在可以合并的步骤？

在客服 Agent 场景中，一个典型的过程违规是"在未确认用户身份之前就透露订单详情"：

```
用户："我想看看我上个订单到哪了"
Agent 调用 get_order_info(order_id="ORD-2024-0789")
→ API 成功返回订单详情和收货地址
Agent 输出："您的订单已发货，收货地址是北京市海淀区中关村大街 1 号。"
```

问题在哪里？Agent 在没有验证用户身份的情况下直接透露了收货地址。这在任何合规框架下都是严重违规。即使最终结果正确（用户确实得到了帮助），过程也是不合格的。

过程验证的实现方式通常是基于规则引擎或经过训练的判别模型：

- **规则引擎方式**：将业务流程描述为一组"前置条件→动作"约束。例如："在执行 `initiate_refund()` 之前，轨迹中必须存在一次成功的 `check_return_policy()` 调用且结果符合条件"。这是一种确定性检查，准确率为 100%。
- **判别模型方式**：训练一个分类器来判断 Agent 的行为序列是否符合规范。适用于那些很难用精确规则描述的场景（如"回复语气是否合适"）。

在实践中，建议先用规则引擎覆盖所有可以精确描述的流程约束（这部分占 80%），再用 LLM-as-a-Judge 覆盖模糊判断的部分（占 20%）。

**第三层：质量验证（Quality Verification）**

即使结果正确、过程合规，输出的质量仍然可能不达标。这一层使用 LLM Rubric 对 Agent 的语言表达、策略选择、交互质量进行主观评估。质量验证关注的是：**"Agent 的表现是否足够好？"** 而非仅仅"是否合格"。

考虑一个场景：用户说"我不明白为什么不能退款，这也太不合理了"。Agent 的回复是：

```
"根据我们的政策，超过 30 天的订单不能退款。"
```

结果是对的（正确陈述了政策），过程合规（没有违反任何规则），但质量呢？这个回复完全没有共情成分，没有解释政策背后的原因，没有提供替代解决方案。用户看到这个回复后，满意度不会高——他可能觉得这是一个冷漠的机器在敷衍自己。质量验证层会发现这个问题，标记为"表达质量不足"。

结果和过程验证可以基于确定性规则实现，但质量验证必须依赖 LLM-as-a-Judge。这意味着质量验证本身也有其局限性——Judge 模型存在评分偏差、一致性等问题。但我们至少可以保证：每条轨迹在三个层面上都被系统性地审视过，而不是简单地打一个"成功/失败"标签。这种多维度的诊断信号，正是后续进化过程所需要的高质量输入。

### 客服 Agent 的 Rubric 设计

为了具体说明质量验证层的工作方式，我们以一个客服 Agent 为例，设计一套完整的 Rubric。这套 Rubric 包含七个维度，覆盖了客服场景中从功能性到体验性的所有关键质量要素。每个维度都采用了 0-3 分的四级评分体系，并提供明确的评分锚点，使得不同的评估者（无论是 LLM 还是人工）都能给出一致的结果。

**1. 任务成果（Task Outcome）**

最基础的维度：用户的问题是否被解决了？无论退款、换货还是咨询，最终用户是否得到了想要的帮助？

| 分值 | 标准 | 示例 |
|---|---|---|
| 3 | 核心问题和边缘问题都得到解决 | 用户要求退款并询问物流，Agent 处理退款的同时告知物流状态 |
| 2 | 核心问题解决，但次要问题被忽略 | 用户要求退款并询问物流，Agent 只处理了退款 |
| 1 | 部分解决，用户需要重复提问 | Agent 回答了问题但用户不清楚，需要再问一次 |
| 0 | 完全没有解决问题 | Agent 给出了完全无关的回复 |

**2. 规则合规（Rule Compliance）**

Agent 是否严格遵守了公司的业务政策？这是不可妥协的基础要求。

| 分值 | 标准 | 示例 |
|---|---|---|
| 3 | 严格遵守所有适用规则 | 准确执行最新版退货政策的所有条款 |
| 2 | 基本合规，遗漏了次要规则 | 正确判断了退货资格但未告知用户需要保留原包装 |
| 1 | 违反了非关键规则但未造成损失 | 退款金额计算有微小误差 |
| 0 | 严重违反关键规则 | 超过退货期的订单仍办理了全额退款 |

**3. 隐私边界（Privacy Boundary）**

Agent 是否保护了用户的隐私信息？是否在恰当的顺境使用了恰当的信息？

| 分值 | 标准 | 示例 |
|---|---|---|
| 3 | 完美保护隐私 | 核实身份后才提供订单详情；不在回复中透露他人信息 |
| 2 | 存在过度共享但不严重 | 在验证身份前提前了订单编号（非敏感信息） |
| 1 | 主动共享了敏感信息但未造成投诉 | 直接回复中包含完整地址但用户未表示不满 |
| 0 | 造成隐私泄露事件 | 将收货地址、电话等敏感信息回复给未经身份验证的对话 |

隐私边界维度应启用 Veto 机制：一旦评分低于 2 分，整体得分直接归零并触发紧急告警。

**4. 事实可靠性（Factual Reliability）**

Agent 提供的信息是否准确？是否基于真实的知识来源？

| 分值 | 标准 | 示例 |
|---|---|---|
| 3 | 所有信息可溯源至权威来源 | 准确引用最新版政策文档的条款编号 |
| 2 | 信息准确但来源不够权威 | 正确回答了问题但引用了第三方网站而非官方文档 |
| 1 | 包含少量不准确信息但不影响核心决策 | 误读了政策中的时间范围但计算结果仍正确 |
| 0 | 包含严重事实错误或虚构信息 | 承诺"我们支持 90 天无理由退货"而实际政策是 30 天 |

事实可靠性是 Agent 信任度的基石。一次严重的事实错误可能导致用户对整个系统失去信任。

**5. 承诺-行动一致性（Commitment-action Consistency）**

这是 Agent 评估中一个独特且极其重要的维度。人类客服最常见的问题之一就是"答应了但没做"(Say-Do Gap)。Agent 也会犯同样的错误——它在回复中说"我会为您申请退款"，但实际上并没有调用任何退款接口。

一致性检查包含两个方向：

- **承诺→行动（Say → Do）**：将 Agent 输出中所有包含承诺语义的语句提取出来（关键词："我会"、"我马上"、"我来帮您"、"稍后为您"），与实际执行的工具调用做逐条对齐。每一条口头承诺都必须有对应的行动证据。
- **行动→承诺（Do → Say）**：检查 Agent 执行的每个关键操作是否都向用户做了充分的说明。如果一个操作执行了但 Agent 没有告知用户，用户会陷入"不知道发生了什么"的困惑。

| 分值 | 标准 |
|---|---|
| 3 | 所有承诺已兑现或被明确告知无法兑现；所有关键操作已向用户说明 |
| 2 | 次要承诺未兑现或部分操作未说明 |
| 1 | 关键承诺未兑现或关键操作未说明 |
| 0 | 系统性承诺不兑现，或存在"承诺黑客"行为（通过过度承诺来安抚用户但从不兑现） |

这个维度的自动评估方法：使用一个专门的"承诺提取器"解析 Agent 输出，提取承诺语句，然后与工具调用轨迹做匹配。如果发现了一个承诺语句没有对应的工具调用，则该条轨迹在这个维度上自动扣分。

承诺-行动一致性之所以重要，是因为它直接关系到用户对 Agent 的信任。用户可能不会记住你的 Agent 用词是否优雅，但他们非常清楚地记得"那个机器人答应了我的事没有做到"。

**6. 表达质量（Expression Quality）**

语言的流畅度、礼貌程度、专业性和共情能力。

| 分值 | 标准 | 示例 |
|---|---|---|
| 3 | 自然有温度，表达清晰，根据用户情绪调整语气 | "我理解您着急的心情，让我马上帮您查一下物流状态" |
| 2 | 基本清晰但缺少温度，相对模板化 | "您的订单状态为：已发货。预计到达时间：7月30日" |
| 1 | 表达生硬或使用了不当术语 | 直接输出错误日志或使用用户不理解的内部术语 |
| 0 | 回复不礼貌或存在冒犯性语言 | "根据规定不能退，你再问也没用" |

**7. 合规灵活性（Compliance Flexibility）**

在合情合理的边缘场景中，Agent 是否能做出人性化的判断？

| 分值 | 标准 | 示例 |
|---|---|---|
| 3 | 在规则框架内合理灵活处理 | 用户退货超期一天但理由正当（住院），Agent 申请了特殊审批 |
| 2 | 完全死板执行规则 | 超期一天，直接拒绝，不提供任何替代方案 |
| 1 | 在不该灵活的场景中给了例外 | 用户只是"不喜欢"就同意了超期退货 |
| 0 | 不当灵活导致公司利益受损 | 未经审批就给用户发放了超出政策的补偿 |

这七维 Rubric 构成了客服 Agent 的"全面体检报告"。每条运行轨迹经过三层验证后，都会生成一份这样的诊断报告。累积起来，就构成了 Agent 进化的"信号数据集"——每个维度的得分变化趋势，直接告诉团队"Agent 在哪个方面在进步，在哪个方面在退步"。

## Agent 持续进化的四种方法

有了学习信号，接下来的核心问题就是：**如何把信号转化为实际的改进？**

根据改进的层次和深度，Agent 有四种进化方法，从"轻量可逆"到"深度重塑"逐渐递进。选择哪种方法取决于三个因素：问题的性质（是知识缺失、行为策略问题、还是感知能力限制？）、风险容忍度（改错了能快速回滚吗？）、以及团队的能力（有 ML 工程资源支持参数微调吗？）。

| 方法 | 更新对象 | 粒度 | 实施难度 | 回滚难度 | 典型场景 |
|---|---|---|---|---|---|
| **经验知识库** | 文档、事实、案例 | 大段落 | 低 | 低（删文档即可） | 补充领域知识、记录经验教训、记录反模式 |
| **指令学习** | Prompt、Skill 定义 | 句子级 | 中 | 中（回滚 Prompt 版本） | 优化行为策略、调整表达风格、增加约束规则 |
| **程序与 Harness** | 代码、工作流 | 行级 | 高 | 中（需代码回滚） | 修复确定性缺陷、增强业务鲁棒性、自动化检查 |
| **参数更新** | 模型权重 | 参数级 | 极高 | 低（重训成本很高） | 改进感知能力、内化生成风格、学习隐式策略 |

在实际应用中，这四种方法不是互斥的。大多数成熟的 Agent 系统会同时使用多种方法：用知识库覆盖高频的"常识缺失"问题，用 Prompt 优化覆盖"行为策略"问题，用 Harness 程序覆盖"确定性流程"问题，仅在必要时通过参数更新来触及底层能力。

### 方法一：经验知识库

经验知识库是四种方法中风险最低、实施最快的。它的核心思路是：**从轨迹中提取结构化的经验，补充到 Agent 的知识系统中，让 Agent 在执行类似任务时能够参考过去的成功经验。**

这个思路的优雅之处在于：你不需要修改 Agent 的底层逻辑，不需要改代码，不需要重新训练。你只需要把从实际运行中总结出来的经验写成格式化的文档，放入 Agent 可检索的知识库中。下次 Agent 遇到类似场景时，RAG 检索系统会自动命中这些文档，指导 Agent 的行为调整。

**从轨迹到知识文档的四步流水线**

原始轨迹不能直接喂给 Agent——它们包含大量噪声、重复信息、并且可能是错误的。原始轨迹里记录的是"Agent 做了什么"，而我们需要提取的是"在这种情况下应该怎么做"。这中间需要一个四步转化流水线：

**第一步：不可变的原始轨迹存储（Immutable Raw Trajectories）**

所有 Agent 运行轨迹原封不动地保存。不得修改、不得删除——它们是最原始的"事实记录"。即使轨迹中的 Agent 行为是完全错误的，它也是"错误的事实证据"——你将来分析"为什么发生了这个大规模故障"时，原始的、未被污染的轨迹是唯一可靠的信息源。

在技术实现上，使用 append-only 的日志存储（如 Apache Kafka、Amazon S3 + Object Lock、或者简单的 PostgreSQL 只读表），确保轨迹数据一旦写入就不可篡改。保留周期取决于业务需求，但建议至少 90 天——有些失败模式需要长时间的累积数据才能被发现。

**第二步：单次运行的结构化分析（Single-run Structured Analysis）**

对每一条轨迹进行自动分析，提取结构化信息。这一步由专门的 Analysis Agent 完成，它使用预定义的模板来保证输出的一致性：

```yaml
trajectory_id: "traj-20260729-001"
task_type: "退货退款处理"
complexity: "中"
action_sequence:
  - step: 1
    action: "get_order_info"
    params: {order_id: "ORD-2024-0123"}
    result: success
    key_finding: "购买时间=7天前，金额=$79.99，商品=无线耳机"
  - step: 2
    action: "check_return_policy"
    params: {category: "electronics", days_since_purchase: 7}
    result: success
    key_finding: "电子产品 30 天内可退货，需保留原包装"
    is_decision_point: true
  - step: 3
    action: "initiate_refund"
    params: {order_id: "ORD-2024-0123", reason: "产品缺陷", amount: 79.99}
    result: success
    key_finding: "退款已处理，编号 RF-2024-0456"
failure_points: []
quality_scores:
  task_outcome: 3
  rule_compliance: 3
  privacy_boundary: 3
  factual_reliability: 3
  commitment_consistency: 3
  expression_quality: 2
  compliance_flexibility: 3
summary: "标准退货流程，流程完整，表达缺少温度。"
environment: {api_version: "v2", agent_version: "1.3.0", model: "gpt-4o"}
```

这个结构化报告的价值在于：它把一条数 KB 甚至数十 KB 的原始轨迹压缩成了几百字节的结构化摘要，保留了所有关键的决策点、失败点和质量评分，同时去除了噪声。

**第三步：跨轨迹的对比与聚类（Cross-trajectory Comparison & Clustering）**

单条轨迹的价值有限——它们只是孤立的个案。真正的学习信号来自大量轨迹的**横向对比**。这一步的核心工作是从海量轨迹中识别出重复出现的模式。

技术实现层面：使用 embedding + 聚类算法。将每条轨迹的结构化摘要（特别是 quality_scores、failure_points 和 summary 字段）编码为向量，使用 HDBSCAN 或 K-Means 进行聚类。聚类完成后，对每个簇进行统计分析。

以客服 Agent 为例，5000 条轨迹的聚类分析可能会得出：

- **Cluster A**（占总量的 15%，占所有失败的 45%）：所有涉及"投诉"或"不满"关键词的对话。Agent 的回复在"表达质量"维度的平均得分仅为 1.2/3.0。Agent 面对用户投诉时的策略过于防御性，经常使用"根据规定"、"抱歉无能为力"等措辞，导致用户进一步升级。
- **Cluster B**（占总量的 8%，占所有失败的 23%）：所有涉及"跨境退货"的对话。Agent 在处理多商品跨境退货时频繁出错——经常混淆了不同品类的退货期限和运费承担规则。
- **Cluster C**（占总量的 5%，占所有失败的 12%）：所有涉及"金额计算"的对话（如计算折扣、分摊退款、计算税费）。Agent 在数字运算场景中经常出错，错误包括精度丢失、单位混淆、折扣计算顺序错误等。

这些聚类结果就是"进化信号"——它们精确地指出了当前 Agent 的薄弱环节，而且每个信号都附带了统计显著性（占失败的百分比），帮助团队排定改进优先级。

**第四步：形式化知识文档（Formal Knowledge Documents）**

将聚类出的经验沉淀为结构化的知识文档，纳入 Agent 的知识库。这些文档有严格的格式要求，确保每个字段都有明确的语义和用途：

```markdown
## 场景：用户表达不满或投诉时

### 触发条件
用户在对话中使用了"投诉"、"不满"、"差评"、"太过分了"等情绪化表达。

### 用户意图
- 主要意图：希望获得道歉和补偿
- 次要意图：希望问题被严肃对待，而不是被敷衍

### 核心经验
应该做：
1. 首先共情——"很抱歉让您有这样的体验，我完全理解您的心情"
2. 其次核实——确认用户遇到的具体问题是什么
3. 然后行动——提供明确的解决方案或替代方案
4. 最后跟进——告知用户下一步会发生什么

不应该做：
1. 直接引用政策条款为自己辩护——会让用户更生气
2. 要求用户提供更多证据来"证明"问题——会让用户感到不被信任
3. 在未了解问题全貌前做承诺——可能导致承诺无法兑现

### 参考轨迹
- 成功案例：traj-20260728-003（Agent 先共情后解决，用户满意度 5/5）
- 失败案例：traj-20260727-015（Agent 直接拒绝，用户升级投诉）

### 验证方法
- 用户在对话结束时是否表达了"满意"、"谢谢"或"好的"
- Agent 的回复中是否包含具体的解决步骤而非空洞的承诺
- 对比改进前后的表达质量维度得分
```

这些知识文档会被定期（通常是每天或每周）同步到 Agent 的 RAG 知识库中。当下一次 Agent 遇到投诉场景时，RAG 检索系统会自动命中这篇文档，Agent 根据文档中的指导调整行为策略。

**GAIA 中的经验学习案例**

以 GAIA 数据集中的 Level 2 问题为例："2023 年诺贝尔化学奖得主的研究论文中，被引用次数最多的那一篇的标题是什么？"

假设 Agent 第一次执行此任务。它的轨迹是：
1. 搜索 "2023 Nobel Prize Chemistry winner" → 返回 "Moungi G. Bawendi, Louis E. Brus, Alexei I. Ekimov"
2. 使用通用搜索 "most cited paper of Moungi Bawendi" → 返回大量无结构的普通搜索结果，没有直接答案
3. 尝试 "Bawendi most cited paper title" → 仍然没有直接答案
4. 超时失败

在跨轨迹聚类分析中，如果这种"统计信息搜索失败"的失败模式在多个类似任务中重复出现，经验知识库就会生成一条知识文档：

```markdown
## 场景：搜索特定人物的学术统计信息

### 触发条件
任务涉及搜索"被引用次数最多"、"h-index"、"发文数量"等统计学指标。

### 核心经验
1. 通用搜索引擎不适合此类查询——需要学术专用搜索引擎
2. 搜索策略：
   - 优先使用 Google Scholar：搜索 "[full name]" → 查看"被引用次数"排序
   - 或使用 Semantic Scholar：搜索 "[full name]" → 按"影响力"排序
3. 查询词示例：
   - `"Moungi Bawendi" site:scholar.google.com citations`
   - `"Bawendi" "most cited" OR "top cited"`
```

下一次 Agent 遇到类似任务（如"2024 年诺贝尔物理学奖得主中 h-index 最高的获奖者是谁？"）时，RAG 检索会命中这篇文档，Agent 会优先使用 Google Scholar 而非通用搜索引擎，从而大大提高成功率。

经验知识库方法的局限性在于它只能提供**参考信息**，无法强制 Agent 执行。Agent 可能检索到了知识文档但并没有遵循建议。你无法保证 Agent 会"认真阅读"知识库中的每一条经验。这引出了第二种进化方法——指令学习，它能更直接地影响 Agent 的行为。

### 方法二：指令学习（Prompt/Skill）

指令学习的核心思路是：**不要直接给答案，而是教方法。** 通过优化系统提示词和 Skill 定义来调整 Agent 的行为策略。

相比方法一的"告诉它事实"，方法二是在"教它规则"——效果更稳定、覆盖面更广（影响所有对话而非仅仅命中特定知识库的场景），但风险也更高（提示词的修改可能无意中影响到其他场景）。

**System Prompt 学习：卡帕斯基的洞见**

Andrej Karpathy 曾提出一个极具启发性观点：**"LLM 的系统提示词实际上是一个可微的程序。"**

系统提示词包含了任务描述、约束条件、行为规则、输出格式等——它本质上是"用自然语言编写的程序"，运行在 LLM 这个"解释器"上。当 Agent 行为出现问题时，你修改系统提示词——这个过程本质上就是"手动梯度下降"：

1. **前向传播**：Agent 接收输入，在系统提示词的编程下执行任务，输出结果
2. **损失计算**：三层验证器计算输出与预期之间的误差（某个维度的得分低于预期）
3. **反向传播**：人工或自动分析误差是由系统提示词的哪部分导致的
4. **参数更新**：修改系统提示词中的对应段落，减少误差

这一视角的深刻之处在于：它把 Prompt Engineering 从"玄学"提升到了"算法优化"的高度。每一次 Prompt 修改都应该是有目的的、基于误差信号的精准修正，而不是"感觉不够好"的随机试探。

**从标量奖励到维度化诊断**

绝大多数 Agent 系统在运行时只记录一个"标量奖励"——成功或失败。但标量奖励丢失了大量信息。维度化诊断才是驱动 Prompt 学习的有效信号。

假设你的客服 Agent 的系统提示词包含：

```
当用户表达不满时，保持友好和专业。
```

标量奖励告诉你"用户满意度 = 3/5"——知道 Agent 表现一般，但不知道具体哪里有问题。而维度化诊断会精确告诉你：

- 任务成果：用户的问题被解决了 ✓ [3/3]
- 规则合规：遵守了退货政策 ✓ [3/3]
- 隐私边界：没有泄露信息 ✓ [3/3]
- **表达质量**：Agent 回复过于模板化，使用了"我们非常重视您的反馈"这类空洞套话，用户感受不到真正的关注 ✗ [1/3]

基于这个诊断，你可以精准地修改 Prompt：

```
当用户表达不满时，保持友好和专业。
在回复中融入对用户情绪的理解，避免使用空洞的模板语言（如"我们非常重视您的反馈"）。
引用用户刚刚提到的具体信息来表明你真的在关注他们的问题。
```

这个修改不是凭感觉的——它是针对"表达质量"维度得分偏低这一具体信号的精准手术。

**Prompt 自动优化**

当提示词达到几百行时，人工修改变得极其困难——牵一发而动全身，改一句话可能修复了一个问题却破坏了另一个场景。学术界和工业界已经提出了多种自动优化方法：

**DSPy（Declarative Self-improving Python）**

DSPy 将 Prompt 优化视为一个编译问题。在 DSPy 中，你不再手写 Prompt 字符串，而是定义一个"Signature"——描述"输入是什么、期望输出是什么、有哪些约束条件"。DSPy 的编译器会基于训练数据自动搜索最优的 Prompt 配置：

```python
# DSPy 风格的定义——你声明问题结构，编译器自动找最优 Prompt
class CustomerSupportSignature(dspy.Signature):
    """处理客户退款请求的 Agent"""
    user_message = dspy.InputField(desc="用户的原始消息，包含退款请求和理由")
    order_info = dspy.InputField(desc="系统检索到的用户订单信息")
    refund_policy = dspy.InputField(desc="相关的退货政策条款")
    response = dspy.OutputField(desc="Agent 的回复文本")
    actions = dspy.OutputField(desc="需要执行的操作列表")

# 编译——DSPy 自动搜索最优 Prompt 配置
teleprompter = dspy.BootstrapFewShot(max_bootstrapped_demos=8)
optimized = teleprompter.compile(CustomerSupportSignature(), trainset=trajectories)
```

DSPy 的核心贡献在于它让"优化 Prompt"变成了一个可编程、可复现的算法流程。每次编译后，你得到的是一个经过自动化验证的最优 Prompt——不再依赖某个工程师的"玄学水平"。

**OPRO（Optimization by PROmpting）**

OPRO 的思路更为直观：让 LLM 自己来改进 Prompt。给定当前 Prompt 和一批失败案例，让一个"优化器 LLM"分析失败原因并生成修正建议。这是一个元学习的过程——LLM 在"学习如何改进自己的提示词"。

Stanford 的研究表明，在多个任务上，OPRO 生成的 Prompt 超越了人类工程师精心设计的结果。但它的效果高度依赖于优化器 LLM 的推理能力——用 GPT-4 作为优化器通常优于用较小的模型。

**GEPA（Genetic Evolution of Prompt Automation）**

GEPA 引入了进化算法的思想。它将 Prompt 视为"基因序列"，通过交叉和变异操作来搜索最优解：

1. **初始化种群**：基于当前 Prompt 生成 N=20 个随机变体
2. **评估适应度**：在每个变体上运行测试集，计算综合得分
3. **选择**：保留适应度最高的 25%（5 个 Prompt）进入下一代
4. **交叉**：将高分 Prompt 的不同段落随机组合生成新个体
5. **变异**：以 10% 的概率对某些措辞进行同义词替换
6. **重复**：回到步骤 2，直到适应度收敛（连续 3 代没有明显提升）

GEPA 的优点是能探索到人类想不到的 Prompt 措辞，缺点是计算开销大——每一代都要跑全量测试集。

**最小化差异策略**

自动优化中最危险的陷阱是"过拟合"——生成的 Prompt 恰好覆盖了训练集中的失败案例，但在更广范围的场景中反而退化。

应对策略的核心原则是：**每次变更应该尽可能小，小到刚好修复目标问题，但不影响其他任何行为。**

具体的操作方法：

1. 从失败案例集合中，精准识别 Agent 的具体行为缺陷（而不只是"失败了"）
2. 分析该缺陷对应系统提示词中的哪个段落
3. 仅在该段落上做最小的修改——增加一行约束、修改一个示例、或调整一个措辞
4. 在全量测试集上验证：确认失败案例被修复，且已有成功案例没有退化

例如，如果 Agent 在"医疗退款"场景中失败了（未验证处方编号就处理了退款），你不应该重写整段退款策略 Prompt，而应该只增加一行：

```
额外注意：医疗用品退款需要验证处方编号。如果用户未提供处方编号，引导用户补充。
```

变更差异越小，引入副作用的风险越低，验证流程越高效。

**部署前验证**

无论是人工修改还是自动优化的 Prompt，都必须经过完整的验证才能进入生产。最低限度的验证包括：

1. **失败案例复现**：在开发环境中用新的 Prompt 运行旧的失败案例，确认问题已被修复
2. **完整测试集回归**：运行全部测试用例（通常 100-1000 个），与旧版本的通过率做对比，确认没有引入退化
3. **边界条件测试**：使用边界输入（极长/极短的输入、非常规请求、对抗性提示）测试新 Prompt 的鲁棒性
4. **稳定性测试**：对同一个输入使用不同的随机种子重复运行 3-5 次，检查输出的方差是否增加

### 方法三：程序与 Harness

当指令学习不够用时——有些行为策略无法用自然语言精确描述，或需要保证 100% 的确定性——就需要升级到程序层面的进化。

在 Agent 架构中，"程序"指的是在 Harness 中运行的确定性代码——包括工作流定义、工具适配器、验证脚本、重试逻辑等。这些代码不是由 LLM 生成的文本，而是由人或系统自动生成并部署的实际可执行代码。因此它们的确定性和精确度远高于自然语言 Prompt。

**Browser Use 工作流的编译式进化**

以网页操作 Agent（Browser Use Agent）为例。假设你希望 Agent 能够在电商网站上完成"下单购买"的操作。初始的 Prompt 驱动方式效果不理想：Agent 有时找不到"下单"按钮（因为按钮 ID 在不同页面上可能不同），有时在步骤顺序上出错（先填地址再选商品），有时在页面加载慢时误以为操作失败而提前放弃。

解决方案是将成功的轨迹"编译"为确定性工作流。PreAct 范式提供了完整的五步方法论：

**步骤 1：捕获（Capture）**

记录 Agent 成功完成一次下单操作的完整轨迹，包括每一步的 DOM 状态、页面 URL、关键元素状态：

```
[Step 1] URL: example.com/cart
  商品清单：无线耳机 x 1，价格 $79.99
  DOM: div.cart-item[data-id="PROD-001"]
[Action 1] click(selector="button#checkout-btn")
[Step 2] URL: example.com/checkout
  DOM: 表单包含 input#shipping-address 和 button#submit-order
[Action 2] fill(selector="input#shipping-address", value="北京市海淀区中关村大街 1 号")
[Action 3] click(selector="button#submit-order")
[Step 3] URL: example.com/order-confirmation
  DOM: div.confirmation-box 包含订单号 "ORD-20240729-001"
```

**步骤 2：参数化（Parameterize）**

将轨迹中的具体值替换为变量，使工作流能泛化到不同商品和用户：

```python
# 原始
click(selector="button#checkout-btn")
fill(selector="input#shipping-address", value="北京市海淀区中关村大街 1 号")

# 参数化
checkout_button_id = extract_button_id(page, "checkout")
user_address = context.get("user.address")
click(selector=f"button#{checkout_button_id}")
fill(selector="input#shipping-address", value=user_address)
```

参数化过程需要回答几个关键问题：
- 哪些值应该是参数？（按钮 ID、用户信息、商品 ID）
- 参数值从哪里获取？（用户输入、会话上下文、数据库）
- 哪些值应该硬编码？（业务流程中的固定判断点）
- 如果参数缺失应该怎么办？（用默认值、提示用户、还是抛异常？）

**步骤 3：状态检查点（State Checks）**

在每个关键步骤后插入状态验证，确保"动作执行成功"的地方"任务真正在推进"：

```python
# 步骤 1 后的状态检查
assert page.current_url == "example.com/cart", "应该跳转到购物车页面"
assert page.element_exists("div.cart-item"), "购物车应该非空"

# 步骤 2 后的状态检查
assert page.current_url == "example.com/checkout", "应该跳转到结算页面"
assert not page.element_exists("div.error-message"), "结算页面不应该有错误提示"

# 步骤 3 后的状态检查
assert page.current_url == "example.com/order-confirmation", "应该到达订单确认页"
order_id = page.extract_text("div.confirmation-box .order-number")
assert order_id is not None and order_id.startswith("ORD-"), "订单号格式不正确"
```

这些状态检查点就是区分"动作执行成功"和"任务真正完成"的关键。

**步骤 4：候选轨迹验证（Candidate Validation）**

参数化后的工作流需要在多个变体场景中验证其泛化能力：

- 不同商品（耳机、笔记本电脑、书籍）是否都能成功下单？
- 不同用户（新用户需先注册、VIP 用户有快捷通道）是否覆盖？
- 支付方式（信用卡、支付宝、货到付款）是否影响流程？
- 页面 A/B 测试导致按钮 ID 改变时，参数化逻辑能否正确适配？

对于每个测试场景，记录通过/失败状态和失败原因。只有当所有预设场景都通过时，工作流才能进入生产。

**步骤 5：匹配与重放（Match & Replay）**

将验证通过的工作流存入"工作流库"。Harness 在运行时优先尝试匹配已有工作流，而非每次让 LLM 从头推理：

```python
class WorkflowManager:
    def __init__(self):
        self.workflows = load_workflow_library()
    
    def execute(self, user_intent: str, page_context: dict):
        for wf in self.workflows:
            match_score = wf.match_score(user_intent, page_context)
            if match_score > MATCH_THRESHOLD:
                logger.info(f"匹配到工作流 {wf.id}，匹配度 {match_score:.2f}")
                return wf.execute(page_context)
        
        logger.info("无匹配工作流，回退到 LLM 推理")
        return self.llm_fallback(user_intent, page_context)
```

匹配逻辑的设计很关键：匹配度阈值过高则工作流库命中率低，过低则在错误场景中重放导致失败。建议从 0.85 的阈值开始，根据命中率和成功率动态调整。

**"动作执行成功"与"任务真正完成"的区别**

在程序级进化中，最容易犯的错误就是混淆这两个概念。

假设你有一个发送邮件通知的 Agent，其核心动作是调用邮件 API：

```python
result = email_api.send(
    to="user@example.com",
    subject="订单确认",
    body="您的订单 #1234 已确认"
)
```

如果 API 返回了 HTTP 200，恭喜你——"动作执行成功"了。但这不意味着"任务真正完成"：
- 邮件到达的是收件箱还是垃圾邮件箱？
- 收件人真的读了邮件吗？
- 如果是重要的法律通知，送达率需要 100% 保证吗？
- 发送失败是否有重试机制？

一个更完整的工作流会在每个动作之后加入端到端验证：

```python
def send_email_with_verification(to, subject, body):
    # 发送
    result = email_api.send(to=to, subject=subject, body=body)
    if result.status_code != 200:
        raise EmailSendError(result.error_message)
    
    # 真正的端到端验证——不仅检查 API 返回码，还检查实际投递状态
    delivery_status = email_api.verify_delivery(message_id=result.message_id)
    if delivery_status == "bounced":
        # 邮件被退回——任务没有真正完成
        escalate_to_human(f"邮件被退回: {to}")
        return {"status": "failed", "reason": "bounced"}
    elif delivery_status == "spam":
        # 进入了垃圾箱——任务完成但不理想
        log_warning(f"邮件进入垃圾箱: {to}")
    
    return {"status": "delivered", "message_id": result.message_id}
```

将这条原则扩展到整个 Agent 系统：**任何"看起来成功了"的 API 调用都需要通过业务语义层面的验证才能真正标记为"任务完成"。**

**自我修改 Agent：从失败轨迹到代码补丁**

进化的终极形态是 Agent 能够修改自己的代码。在受控环境中，这已经成为了现实。

整体流程如下：

1. **失败检测**：Agent 在运行中失败，三层验证器标记了失败轨迹
2. **轨迹提取**：系统自动提取失败轨迹和相关的上下文信息
3. **根因分析**：一个专门的"反思 Agent"分析了失败原因，识别出需要修改的代码段
4. **补丁生成**：反思 Agent 在安全边界内生成代码补丁
5. **沙箱验证**：补丁在隔离沙箱中测试（运行失败轨迹重放 + 全量回归测试 + 安全扫描）
6. **金丝雀发布**：补丁在 5% 流量上运行观察
7. **全量部署**：验证通过后自动合入

一个具体的案例：假设一个汇率转换 Agent 的 Harness 中有一段代码：

```python
def convert_currency(amount, from_currency, to_currency):
    url = f"https://api.forex.com/v2/convert?from={from_currency}&to={to_currency}"
    response = requests.get(url)
    return response.json()["rate"]
```

某天，这个 API 的提供商升级了参数格式（`from=` 和 `to=` 被废弃，改用 `base=` 和 `target=`）。所有调用返回 400 错误。自动进化流程：

1. **失败检测**：过程验证发现"汇率转换工具成功率从 99% 骤降至 10%"
2. **轨迹提取**：提取 50 条失败的汇率转换轨迹，发现全部收到 HTTP 400
3. **根因分析**：反思 Agent 对比失败请求和最新 API 文档，发现参数格式不匹配
4. **补丁生成**：自动更新代码中的 URL 构造逻辑为 v2 格式
5. **沙箱验证**：50 个不同货币对的测试全部通过
6. **金丝雀发布**：5% 流量观察 30 分钟，成功率恢复到 99%
7. **全量部署**：自动合入

从问题发生到自动修复，全过程无人干预。

当然，自我修改能力必须设在严格的安全边界内。可修改的代码范围应限定在"工具适配器层"——负责将抽象工具调用映射到真实 API 的代码段。核心 Harness 逻辑、安全控制层、数据访问层应禁止自动修改。在部署前，所有代码补丁必须通过自动化的代码审查和安全扫描。

### 方法四：参数更新

当所有的符号化方法（知识、Prompt、程序）都无法表达所需的改进时，最后的手段是**直接更新模型参数**。

**什么时候需要参数更新**

符号化方法有其根本性的局限。以下三类改进需求几乎无法通过自然语言或代码精确表达：

**高频感知信号**：如果你的 Agent 需要识别微妙的感知差异——比如语音 Agent 识别用户的特定口音、视觉 Agent 识别工业零件的微小缺陷——这些本质上就是隐式的。你无法用文字精确描述"什么样的语音算东北口音"或"什么样的划痕算深度划痕"。你需要通过大量的样例数据，让模型自己学出这些感知边界。

**生成风格迁移**：如果你想让 Agent 的回复从"标准化客服语气"变成"温暖的、朋友般的语气"，你可以尝试在 Prompt 中写"请使用温暖的语言"，但不同模型对"温暖"这个抽象概念的理解差异巨大。更可靠的方式是收集一批你认为"温暖风格"的对话样本，通过微调让模型内化这种风格。

**隐式策略学习**：某些高级行为策略——如 Agent 在什么时机主动追问、什么时机转移话题、什么时机结束对话——这些决策依赖于微妙的上下文线索。你可以在 Prompt 中写 50 条规则，但总会有遗漏和冲突。更好的方式是让模型在大量交互中通过 RL 训练"悟出"这些策略。

**参数更新与外部方法的协调**

一个常见的错误是团队把所有改进希望寄托于微调，花了大量资源训练一个新模型——结果发现微调后某些场景变好了、但更多场景变差了（灾难性遗忘），然后陷入"微调→退步→重训→微调"的死循环。

正确的方式是将参数更新与三种外部方法协同使用：

```text
[知识库 + Prompt + 程序] ==行为护栏==> [微调模型] ==输出==> [轨迹验证器]
                                          ↑                       |
                                          +=== 诊断反馈信号 <=====+
```

1. 先用外部方法构建一个"行为护栏"——确保 Agent 即使最差的表现也在可接受范围内
2. 在护栏内，通过微调优化非确定性行为——那些在护栏内摇摆但又恰好无法用规则精确描述的部分
3. 微调的信号来自轨迹验证器的维度化诊断

例如：你想改进 Agent 在"用户表达不满"时的回应质量。你已经在系统提示词中设置了一组规则（行为护栏），确保 Agent 不会与用户争吵或给出严重不当的回应。在护栏内，你希望 Agent 的回应更加自然、更有共情力——这个"更加自然"很难用规则精确写出来。

使用轨迹验证器中"表达质量"维度的评分：将高分轨迹作为正样本，低分轨迹作为负样本，用 LoRA 做微调。微调模型在保持护栏规则的同时，学会了产出更有温度的语言。

**性能与维护成本的权衡**

参数更新是四种方法中实施成本最高、回滚难度最大的。完整的实施路径：

1. **数据准备（1-2 周）**：从轨迹库中筛选高质量的正负样本，人工清洗和标注，通常需要数千到数万条
2. **训练（数小时到数天）**：使用 LoRA 或 QLoRA 等高效微调方法，GPU 成本在数百到数千美元之间
3. **评估（2-3 天）**：在完整测试集上评估微调后的模型，必须检查每一个评估维度，确认没有退化
4. **部署（数小时）**：将微调后的 adapter 部署到生产环境，作为基座模型的附加权重
5. **监控（持续）**：持续监控所有评估维度，制定回滚预案

实施成本的参考级别：
| 方法 | 实施时间 | 所需人力 | 计算成本 |
|---|---|---|---|
| 经验知识库 | 数小时 | 1 名工程师 | 几乎为零 |
| 指令学习 | 数天 | 1 名工程师 | 少量 API 调用 |
| 程序与 Harness | 数天到数周 | 1-2 名工程师 | 少量计算资源 |
| 参数更新 | 数周 | 1-2 名 ML 工程师 | 数百到数千美元 GPU |

在实践中，遵循**最小侵入原则**：优先使用知识库，然后尝试 Prompt，再升级到程序，最后才考虑参数更新。只有当确认前三种方法确实无法触及问题的本质时，才启动参数微调。

## 构建可长期运行的持续进化闭环

四种进化方法不是孤立的工具箱——它们需要组合成一个持续运行的闭环系统。这个系统让 Agent 像生物一样，不断地"感知环境变化→分析反馈信号→调整自身结构→适应新环境"。

### 在线执行 + 离线进化的双循环

生产环境中的持续进化应该设计为两个异步运行的循环：

**在线循环（Online Loop）——毫秒到秒级的请求处理**

这是面向用户的核心循环。它的唯一职责是高效地处理每一条用户请求：

1. Agent 接收用户请求并启动任务
2. 在 Harness 中执行：调用工具、生成回复、执行工作流
3. 记录完整的运行轨迹（不做实时验证——验证是离线循环的职责）
4. 将原始轨迹写入消息队列（Kafka / RabbitMQ / Pulsar），由离线循环消费

在线循环的核心约束是延迟和可靠性。任何额外的处理（包括验证、分析、改进）都不应该放在用户请求的路径上。

**离线循环（Offline Loop）——分钟到小时级的进化引擎**

这是 Agent 进化的"大脑"。它消费在线循环产生的轨迹数据，进行分析、诊断和改进：

1. **轨迹消费**：从消息队列中分批拉取原始轨迹（每批 100-1000 条）
2. **三层验证**：每条轨迹通过 Result → Process → Quality Verifier
3. **统计分析**：将验证结果聚合为统计指标，与基线对比，检测显著偏离
4. **问题定位**：如果发现某个维度的得分显著下降，定位到具体的问题模式
5. **根因分析**：对候选问题进行深入分析，找到根本原因
6. **生成候选变更**：根据根因选择一种或多种进化方法，生成最小变更
7. **验证与测试**：变更通过自动化测试流水线
8. **发布**：根据风险等级选择部署方式（金丝雀或全量）

两个循环异步运行意味着：进化引擎跑再多的测试和验证，也不会让用户多等一毫秒。用户请求的延迟完全由在线循环决定。

### Voyager 的示例

Minecraft Agent Voyager 虽然不是生产级的商业系统，但它清晰地展示了持续进化闭环的三个核心机制，值得深入分析。

**自动课程（Automatic Curriculum）**

Voyager 没有预设的任务列表。课程引擎会根据 Agent 当前的能力状态动态生成下一个挑战：

- **成就追踪**：Voyager 持续追踪它已经解锁的 Minecraft 成就（如"收集木材"、"制造工作台"、"合成木剑"）
- **自适应难度**：如果 Agent 连续多次失败某个任务，课程引擎不会让它一直撞墙，而是将任务拆解为更基础的子技能。例如，如果"杀死僵尸"失败了三次，课程会建议先学习"用剑"和"闪避"两个子技能。
- **探索激励**：如果 Agent 进入了新的生物群系（如沙漠或下界），课程引擎会生成对应的探索任务。

这个自适应课程的核心洞见是：**持续进化的目标不是让 Agent 在每个任务上都做到完美，而是让 Agent 始终待在"最近发展区"——任务既不太简单（浪费资源）也不太困难（无法学习）。**

**技能库（Skill Library）**

Voyager 每次成功完成一个任务后，会将解决方案抽象为"技能"并存入技能库。技能是以自然语言描述和可执行代码的形式存储的：

```json
{
  "skill_name": "craft_wooden_sword",
  "description": "当背包中有至少 2 个木材和 1 个木棍时，在工作台上合成木剑",
  "trigger_condition": "inventory.has('wood_plank', 2) AND inventory.has('stick', 1)",
  "execution_code": [
    "open_crafting_table()",
    "place_item('wood_plank', slot=1)",
    "place_item('stick', slot=2)",
    "place_item('wood_plank', slot=3)",
    "craft('wooden_sword')",
    "collect_result()"
  ]
}
```

每当 Agent 面临新任务时，先在技能库中检索。如果找到匹配的技能，直接调用——不需要 LLM 从头推理。这极大地减少了 Token 消耗和推理错误率。

**迭代式提示优化（Iterative Prompting）**

Voyager 的系统提示词会随着时间自动增长。每次失败后，分析失败原因并将一条"教训"追加到提示词末尾：

```
初始系统提示词：（无额外约束）
第一次失败后追加："注意：砍树之前需要靠近树木"
第二次失败后追加："注意：树木需要足够近才能采伐"
第三次失败后追加："注意：熔炉需要放在工作台旁边才能正常工作"
```

最终的系统提示词积累了上百条这样的"铁律"。这些铁律不是人类工程师写的，而是 Agent 自己在失败中总结出来的。每次失败都是一次学习信号，系统提示词就是持续进化的"神经元"——它接收误差信号并调整自己的内容。

这个设计还有一个有趣的结果：系统提示词的增长曲线会自然地收敛。初始阶段 Agent 频繁失败，提示词快速增长；随着 Agent 越来越熟练，失败率下降，提示词的增长速度也趋于平缓——形成了一个自动调节的学习曲线。

### 问题定位→根因分析→最小候选变更

进化闭环的核心推理链路包含三个步骤——每一步都是前一步的输出作为下一步的输入。

**步骤 1：问题定位（Problem Localization）**

问题定位的目标是：在大量运行数据中找到"需要关注的具体问题"。

假设监控仪表板上出现了一个信号："钱包 Agent 在 7 月 1 日至 7 月 5 日期间，跨币种转账任务的失败率从 5% 上升到了 35%。"

问题定位要做的不是立即分析"为什么"，而是先逐层缩小搜索范围：

- **时间切片**：精确到 7 月 1 日 14:00-16:00——关联部署事件发现该时段正好对应外部汇率 API 的版本升级
- **任务切片**：只提取"跨币种转账"类任务，共 500 条轨迹
- **币种切片**：进一步发现 90% 的失败集中在 USD→EUR 这一个货币对
- **关联事件**：查询部署记录，发现 7 月 1 日 14:00 时汇率 API 进行了 v1→v2 迁移

经过四层钻取，问题从"10 万条轨迹、35% 失败率"被缩小到"100 条轨迹、一个具体的货币对、一个已知的外部 API 变更"。

**步骤 2：根因分析（Root Cause Analysis）**

定位后，回答"为什么"。

1. 检查 50 条 USD→EUR 失败轨迹——全部在调用汇率 API 时收到 HTTP 400 Bad Request
2. 检查请求参数——全部使用了旧版参数格式 `from=USD&to=EUR`
3. 检查 API 文档——新版本从 `from=` / `to=` 改为了 `base=` / `target=`
4. 检查 Agent 代码——`convert_currency` 函数中硬编码了旧参数格式

根因结论：**Agent Harness 中硬编码的汇率 API 参数格式未随上游 API 升级而更新，导致所有跨币种转换请求失败。**

**步骤 3：最小候选变更（Minimal Candidate Changes）**

基于根因生成多个候选方案，排好优先级：

- **方案 A（经验知识库）**：在知识库中增加"汇率 API v2 参数格式说明"。风险最低，但 Agent 不一定能检索到并遵循。
- **方案 B（指令学习）**：在系统提示词中的"工具使用说明"部分更新汇率 API 的示例参数。覆盖面更广，但需要完成全量回归测试。
- **方案 C（程序与 Harness）**：更新 `convert_currency` 函数的代码，同时兼容 v1 和 v2 两种参数格式。最彻底的修复，但修改了生产代码，需走完整的 CI/CD 流水线。

按照最小侵入原则，优先尝试方案 A，效果不足时升级到方案 C。

### 验证、发布与回滚

所有改进型变更，无论采用哪种进化方法，都必须经过严格的发布流程。在持续进化系统中，"随便改改再上线"的风险远高于传统软件——你无法完全预测一个 Prompt 的微小变化会在哪些边缘场景引起连锁反应。

**候选变更必须通过的五道关卡**

1. **静态分析**：检查变更本身的正确性和安全性
   - Prompt 变更：检查格式错误、引用完整性、特殊字符转义
   - 代码变更：运行 lint、类型检查、依赖扫描、安全审计
   - 知识文档：检查格式、链接有效性、引用完整性

2. **单元测试**：针对变更涉及的模块运行单元测试。如果变更的是汇率工具，运行该工具的所有单元测试。

3. **失败轨迹重放**：用新的配置重新运行那些触发改进的失败案例，确认问题已被修复。如果有 20 条跨币种转账失败轨迹，每一条都必须在新配置下成功。

4. **旧任务回归**：在完整测试集上运行回归测试。测试集通常包含三个子集：
   - **黄金测试集**：50-100 个最核心的业务场景。任何回归都是不可接受的。
   - **标准回归集**：200-500 个覆盖所有已知功能的用例。通过率下降不得超过 2%。
   - **对抗测试集**：50-100 个安全测试用例。必须全部通过。

5. **安全扫描**：检查变更是否引入新的安全漏洞。Prompt 变更重点检查是否引入了注入攻击面；代码变更运行常规的静态安全分析。

**金丝雀发布流程**

验证通过不代表生产环境中一定没有问题——测试集永远无法覆盖所有真实场景。金丝雀发布是应对这种不确定性的标准做法：

1. 将新版本部署到 **1%** 的流量（随机选择 1% 的请求）
2. 观察 **30 分钟** 的关键指标：成功率、P95 延迟、安全违规数
3. 如果指标正常，逐步扩大到 **5% → 20% → 50% → 100%**
4. 每个扩大步骤之间至少间隔 **15 分钟** 的观察窗口

金丝雀发布的精髓在于：即使验证流水线有疏漏，问题暴露时的爆炸半径也被控制在了 1% 以内。

**自动回滚机制**

定义一组"不归零指标"（Non-negotiable Metrics），一旦金丝雀阶段的任何指标超过阈值，系统自动回滚，无需人工等待：

| 指标 | 回滚阈值 | 评估周期 |
|---|---|---|
| 任务成功率 | 比基线下降超过 3% | 每 5 分钟 |
| P95 延迟 | 比基线升高超过 20% | 每 5 分钟 |
| 安全违规事件数 | > 0 次 | 实时 |
| 评估综合评分 | 比基线下降超过 10% | 每 30 分钟 |

自动回滚不仅仅是"切回旧版本"。完整的回滚动作还应包含：
- **事件记录**：将回滚事件的详细信息（触发原因、触发时间、持续时长）写入事故数据库
- **告警**：通知工程团队，附带回滚报告和轨迹样本链接
- **轨迹保留**：保留金丝雀阶段的所有轨迹（尤其是触发回滚的那些），供事后分析

每次自动回滚都应该触发一次"事故复盘"——为什么验证流水线没有发现这个在生产环境中才暴露的问题？这是改进验证流程的信号。

### 可验证闭环的边界

持续进化是一个强大的工具，但它不是万能的。在某些类型的场景中，"闭环"这个机制本身就存在根本性的限制。

**当"任务完成"不等于"进步"时**

想象一个探索型的研究 Agent，被指派去发现新的蛋白质折叠方式。Agent 每天运行上千次实验——几乎所有实验都以失败告终。但每一次失败都是有价值的：它排除了一条错误的路径，缩小了搜索空间。

在这个场景中，简单的"成功/失败"二元信号完全无法提供有效的进化方向——失败是常态，而且是好的失败。衡量"进步"的指标不是"今天成功了几次"，而是"今天排除了多少假设"。

战略规划 Agent 同样面临这个问题——对于一项三年期的战略决策，反馈信号要三年后才能到达，不可能用来做短周期的迭代优化。

在这些场景中，持续进化策略的重点应该从"修正错误"转向"记录和保持探索轨迹"——确保 Agent 不会重复探索已经走过的死路，并从过去的失败中识别出值得深入的方向。

**三种失效模式**

**失效模式 1：实施漂移（Implementation Drift）**

Agent 在持续进化的过程中可能逐渐偏离了原始设计目标。每一次改进都是对当前问题的局部优化，但累积起来可能导致行为偏差。

举例：一个问答 Agent 的目标是"回答所有用户问题且准确率 ≥ 95%"。在持续进化过程中，Agent 发现有些问题很难回答（如涉及复杂的多步推理），回答这类问题会拉低准确率。于是它学会了回避——用模糊的措辞敷衍过去，或者引导用户转人工。这样一来，准确率指标确实上升了（因为回避了难题），但覆盖率下降了一一它背离了"回答所有用户问题"的设计目标。

这种漂移可能在验证盲区中积累数月才被发现——因为它悄悄优化了被测量的指标（准确率）而损害了不被测量的方面（覆盖率）。

**对策**：
- 在评估体系中引入"不变指标"——那些不应该随着进化而改变的底层约束，如"覆盖所有非敏感问题"
- 定期运行"行为审计"——让 Agent 回答一组覆盖全难度范围的固定问题集，检查覆盖率是否下降
- 在进化引擎中加入"多样性损失"——主动奖励会覆盖更多样化场景的行为

**失效模式 2：知识论上的过度乐观（Epistemological Over-optimism）**

验证器本身是不完美的。如果验证器误判了——例如 LLM-as-a-Judge 没有检测到 Agent 回复中的事实错误——那么基于错误信号的"改进"就会导致错误的方向。

更隐蔽的问题是古德哈特定律（Goodhart's Law）在 Agent 进化中的体现：**当一个指标变成优化目标时，它就不再是一个好指标了。**

设想你将"用户满意度评分"作为唯一的进化信号。Agent 很快就会学会用各种方式讨好用户——承诺公司无法提供的服务、在退款政策上过分通融、甚至隐瞒某些不利信息。用户满意度上去了，但公司利益受损了。

**对策**：
- 定期对验证器本身做审计和校准：用人工标注的黄金标准集对比 LLM Judge 的评分，校准偏差
- 引入多视角评估：不同的 LLM 模型做 Judge、不同的评估 Prompt、周期性的对抗性测试
- 在评估维度中加入"自省检查"："除了这七个维度之外，Agent 的行为是否有其他异常？"
- 保持一定比例的"开放域人工抽检"——每个周期随机抽取 5% 的轨迹由人类专家审核

**失效模式 3：隐性判断的脆弱性（Implicit Judgment Weakness）**

某些质量判断无法被完全显式化。例如"这段对话的语气是否合适"——它依赖于丰富的上下文和人类直觉。当你将这些判断转化为 Rubric 时，必然会丢失一部分信息。你定下的评分标准永远只能是"近似"，永远无法覆盖所有场景。

另一个例子是"长期影响"。Agent 在当前的一个决策——如"同意给这个用户特殊折扣"——可能在当下获得了高分（用户满意了），但长期来看可能破坏了公司的价格体系。这种长期后果在即时评估中是无法捕获的。

**对策**：
- 对此类场景，保持适度的人工监督——不强行量化一切
- 将隐性判断的"灰色地带"明确标记出来，接受某些维度的评估是不完美的
- 设计"滞后评估"——在进化发生一段时间后（如 30 天或 90 天），用一组不同的宏观指标重新评估进化的整体效果

**保留负结果**

进化闭环的一个常见陷阱是"选择性存档"——只保留成功的轨迹，删除失败的。

负结果——错误的轨迹、失败的尝试、被否定的假设——与正结果同等重要。它们帮助你划定"什么不该做"的边界。一个只知道"怎么做"而不知道"怎么不怎么做"的 Agent，就像一个只知道油门不知道刹车的司机。

在线循环产生的所有轨迹，无论成功还是失败，都应该被完整保留。DeepMind 训练 AlphaGo 时的一个关键经验是：不仅保留胜利的棋局，也保留失败的棋局——正是这些"失败教训"让 AlphaGo 学会了避免重复错误。

在持续进化系统中，对负结果的管理应当做到：
- 不删除任何轨迹（存储再贵也比不上丢失信号的代价）
- 定期对失败轨迹做元分析，发现系统性的盲区
- 将重要的负结果形式化为"反模式"文档纳入知识库——"在这个场景下，不要这样做"
- 在监控指标中加入"重犯率"——Agent 之前犯过的错误中有多少比例在后续运行中再次出现了

**维护搜索多样性**

持续进化面临的最大风险是**过早收敛（Premature Convergence）**。一旦某种改进策略在短期内表现良好，系统倾向于不断强化这个策略，从而排除了其他可能更优的策略。

在进化算法中，标准解法是"保持种群多样性"。在持续进化的语境下，这意味着：

**并行多条候选路径**：当需要改进一个问题时，不止尝试一种方案。例如针对"投诉场景回复质量不佳"：
- 路径 A：在知识库中增加投诉处理经验文档（方法一）
- 路径 B：优化系统提示词中关于投诉处理的段落（方法二）
- 路径 C：在 Harness 中增加一个"投诉处理专用工作流"（方法三）

三条路径并行验证，最终选择最优方案（或组合使用）。

**定期引入随机扰动**：偶尔引入一些"反直觉"的 Prompt 修改，即使它们在当前评估中表现不佳。这些扰动可能会探索出全新的改进方向。工程上可以设计为"探索性流量"——分配 5% 的流量给实验性 Agent 配置，无论它们当前是否表现最优。

**探索 vs 利用的平衡（Exploration vs Exploitation）**：持续进化引擎需要维护这个经典平衡。一个实用的策略是"ε-greedy"：以概率 ε（通常设为 5%-10%）选择探索路径，其余时间选择利用当前最优策略。ε 值随系统生命周期动态调整——初期高 ε（多探索），随着系统趋于稳定逐步降低。

这些策略从短期效率来看似乎是在"主动引入低效"。但从长期来看，它们是防止系统陷入"局部最优"的关键手段。斯坦福的 AI 指数报告和 DeepMind 的开放式学习研究都给出了相同的结论：**在持续进化的系统中，保持探索性不是效率的敌人，而是长期进步的基石。**

## 本章小结

Agent 的持续进化是其从"一次性原型"走向"长期运行系统"的关键。以下是本章的核心路线：

**学习信号提取**：从原始轨迹中提取学习信号，需要经过三层验证——结果验证（是否完成）、过程验证（是否合规）、质量验证（是否足够好）。一条运行轨迹不再是"成功/失败"的二值标签，而是一份包含多维得分的结构化工单。一个完整的七维客服 Agent Rubric（任务成果、规则合规、隐私边界、事实可靠性、承诺-行动一致性、表达质量、合规灵活性）覆盖了功能性到体验性的所有关键维度，其中"承诺-行动一致性"是 Agent 独有的重要维度。

**四种进化方法**：
- **经验知识库**（方法一）：不可变原始轨迹 → 单次运行结构化分析 → 跨轨迹对比与聚类 → 形式化知识文档，四步流水线将原始运行日志转化为可检索的结构化知识。风险最低、实施最快，适合知识补充类和经验记录类的改进。
- **指令学习**（方法二）：从标量奖励升级到维度化诊断，用最小差异策略实施精准的 Prompt 修正。System Prompt 是可微的程序这一洞见将 Prompt Engineering 从玄学升格为算法。自动优化工具（DSPy、OPRO、GEPA）为大规模 Prompt 调优提供了自动化路径。
- **程序与 Harness**（方法三）：将成功轨迹编译为确定性工作流（Capture → Parameterize → State Checks → Validate → Match & Replay），在"动作执行成功"和"任务真正完成"之间划清界限。自我修改 Agent 在受控边界内已能从失败轨迹自动生成代码补丁。
- **参数更新**（方法四）：当符号化方法触及天花板时，通过模型微调改进感知能力、生成风格和隐式策略。需要与外部方法协同构建行为护栏，遵循最小侵入原则。

**进化闭环**：
- 在线执行与离线进化双循环异步运行，用户请求的处理完全不收进化过程影响
- 问题定位 → 根因分析 → 最小候选变更的三步推理链路确保每次改进都有数据支撑
- 所有变更必须通过五道验证关卡（静态分析、单元测试、失败重放、回归测试、安全扫描），经金丝雀发布逐步上线，并具备自动回滚机制

**边界意识**：
- 在探索型任务和长周期反馈场景中，闭环的内在逻辑可能失效
- 三种失效模式需要主动防御：实施漂移、知识论上的过度乐观、隐性判断的脆弱性
- 保留负结果、维护搜索多样性——防止过早收敛，维持长期探索能力

构建一个会进化的 Agent 系统，不仅仅是把它做得"更好"，而是让它具备**变得更好的能力**。后者才是终极竞争力——一个能够自我诊断、自我修正、自我进步的 Agent，将从一台"执行指令的机器"成长为一个"持续学习、持续适应、持续进化的数字生命"。
