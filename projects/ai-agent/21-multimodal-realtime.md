## 第二十一章 多模态与实时交互

在前面的章节中，我们聚焦于纯文本的智能体——它们读取文字、思考文字、输出文字。但从 DeepSeek R1 开始，我们就不断听到一个关键词：<strong>多模态</strong>。这不仅仅是"给 LLM 加个摄像头"那么简单，而是涉及到整个交互范式的根本转变。当智能体从对话框走进现实世界，它需要<strong>看</strong>、<strong>听</strong>、<strong>说</strong>，甚至需要<strong>操作物理设备</strong>。每增加一个模态，系统的延迟、成本和架构复杂度都会指数级上升。

本章将围绕三个核心场景展开：语音交互（最自然的人机接口）、Computer Use（GUI 自动化）、以及机器人操作（物理世界交互）。我们会看到，实时性是多模态智能体面临的最大挑战，而业界正在从流水线架构向端到端全双工架构演进。

## 21.1 语音——最自然的人机接口

在计算机交互的历史中，键盘和鼠标统治了数十年，触摸屏改变了移动互联网，而语音被认为是"下一件大事"。为什么？一个数据就足够说明问题：<strong>语音的带宽是打字输入的 4 倍</strong>。普通人每分钟能说 150-180 个英文单词，而打字只有 40-60 个。对于中文，这个差距更大——语音输入比拼音打字快 3-5 倍。

但"语音输入法"和"语音 Agent"是两种完全不同的产品。语音输入法解决的只是"转写"问题——把声音变成文字，后面还是文本交互。而语音 Agent 不仅要听懂你在说什么，还要理解语气、情绪、意图，然后用语音回应你——它做的是"对话"。

最早的 Agent 语音能力来自 Whisper：一段音频输入，一段文字输出。如下图所示的流程中，模型将语音直接编码为文本 token，完成从语音到语义的映射。

![Whisper 语音编码流程](/images/courses/ai-agent/fig9-1.svg)

Whisper 类模型的成功给我们的启发是：语音输入可以像文本一样作为 token 序列来处理。这个思想直接催生了后续的端到端语音模型——既然语音可以 token 化，那为什么不直接让 LLM 理解这些 token 呢？

## 21.2 语音架构的三种范式

OpenAI 将自己的语音对话模型发展历程分为三个阶段，这恰好概括了语音 Agent 架构的三种范式：

| 范式 | 代表 | 延迟 | 特点 |
|------|------|------|------|
| **级联流水线** (Cascaded) | 传统方案 | 1-2.5s | VAD→ASR→LLM→TTS 串行 |
| **端到端全模态** (Omni) | GPT-4o Audio, Qwen3-Omni | 300-800ms | 单一模型处理听→想→说 |
| **全双工交互** (Interactive) | Moshi, GPT-Live | ~200ms | 同时听说，微轮次对话 |

这三种范式的核心区别在于它们如何打破传统的"轮次对话"（turn-based）假设。轮次对话本质上是把语音交互降级成了文本聊天的形式——你说一句，我回一句。而真正的人类对话是连续的、重叠的、可打断的。

## 21.3 范式一：级联流水线

级联流水线是最早也是最直观的语音架构：VAD（语音活动检测）→ ASR（语音识别）→ LLM（推理）→ TTS（语音合成）。四个模块串行工作，一个的输出是下一个的输入。

### 21.3.1 四段串行的问题

这个架构的问题非常典型。首先是<strong>VAD 的局限性</strong>：VAD 需要检测到用户停止说话后 500-800ms 的静音段，才能确认一句话结束。如果在嘈杂环境中，这个静音检测窗口需要拉得更大，以避免误判。结果是用户说完话后要等将近 1 秒，系统才开始处理。

其次是<strong>延迟瀑布效应</strong>。我们来算一下每一段的典型延迟：

- VAD 静音检测：500-800ms
- ASR 识别（200ms 音频约需 100-300ms 处理时间）
- LLM 推理（取决于模型大小，300ms-1s）
- TTS 合成（200-500ms）
- **总计：1.1s 到 2.6s**

这还只是计算延迟，没有算网络传输和排队时间。下图展示了完整的延迟瀑布。

![延迟瀑布分析](/images/courses/ai-agent/fig9-4.svg)

还有<strong>排队延迟</strong>（queueing delay）。当系统利用率从 50% 提升到 90% 时，排队延迟不是线性增长，而是指数级增长。利用率 50% 时排队延迟可以忽略，利用率 90% 时排队延迟变成处理时间的 9 倍。这意味着高并发场景下，级联流水线的延迟会瞬间崩盘。

### 21.3.2 全链路流式优化

针对这些问题，业界发展出了一系列优化技术：

- <strong>流式 ASR</strong>：不再等整句说完，而是边听边识别，每 100-200ms 输出一次中间结果
- <strong>LLM chunked output</strong>：大模型可以流式输出 token，每生成几个 token 就送给 TTS
- <strong>增量 TTS</strong>：不等待完整的文本，而是每收到一段就合成一段语音

<strong>预生成（speculative generation）</strong>是更激进的做法：在用户还没说完的时候，系统就根据已有的部分输入推测用户的意图并开始生成回复。如果猜对了，延迟几乎为零；如果猜错了，需要中断并重新生成。

### 21.3.3 流式语音感知

级联流水线最大的瓶颈在于 VAD+ASR 的割裂——VAD 只做"有没有人说话"的检测，而 ASR 只做"说了什么文字"的转写。两个模块完全不知道对方在做什么。

流式语音感知（streaming voice perception）的理念是：<strong>把 VAD 和 ASR 合并</strong>，用一个模型同时完成"谁说、说没说话、说了什么、什么语气、什么情绪"的感知。

Qwen2-Audio 和 Ultravox 走的就是这个路线。它们将音频输入直接映射为 LLM 能够理解的 token 序列。Qwen2-Audio 的做法是将音频编码后拼接在文本 token 序列前面，让 LLM 看到一个"音频感知前缀"。

更重要的是，这样的架构可以引入<strong>特殊 token</strong>来表示语音事件：

| 特殊 Token | 含义 |
|-----------|------|
| `<speak_start>` / `<speak_end>` | 说话开始/结束 |
| `<interrupt>` | 对方打断 |
| `<emotion>` | 情绪标记 |
| `<laugh>` | 笑声 |
| `<sigh>` | 叹气 |

这些 token 让 LLM 不仅知道"说了什么"，还知道"怎么说的"。这为语义端点检测（semantic endpoint detection）铺平了道路——不是靠静音来判断一句话是否结束，而是靠语义和语气来判断。

## 21.4 范式二：端到端全模态（Omni）

端到端全模态模型（Omni model）的核心思想是：用一个模型完成"听→想→说"的全流程。音频输入直接进入 LLM，LLM 直接输出音频 token，不需要中间的文本转写步骤。

### 21.4.1 技术权衡

相比级联流水线，Omni 模型的优势明显：

- **更低延迟**：省去了 ASR-TTS 的串行开销
- **保留非语言信息**：语速、音调、情绪、重音——这些在 ASR 转文本过程中丢失的信息，在 Omni 模型中被完整保留
- **端到端优化**：模型可以学习到音频输入与音频输出之间的直接映射，而不是经过文本这个中间 bottleneck

但代价也很明显：

- **可解释性差**：你没法知道模型"在想什么"，因为它的中间表征不是人类可读的文字
- **训练复杂度高**：需要大规模的语音-文本多模态数据
- **调试困难**：当输出不对时，很难定位问题出在"听"还是"想"还是"说"

### 21.4.2 自级联：何时先转写再推理

一个有趣的发现是：在某些场景下，让模型先转写再推理（所谓的自级联，self-cascade）反而更好。

这取决于一个关键的设计原则：<strong>bottleneck 的质量取决于中间表征承载了多少信息</strong>。

简单来说：如果音频中的任务相关信息都能被文本无损承载（比如语音助手："设定一个明天早上 8 点的闹钟"），那先转写再推理就足够了，不需要端到端。但如果任务依赖语气、情绪、环境音（比如客服场景:"我真的很失望！（叹气）"），那文本中间表征就会丢失关键信息，端到端就更合适。

### 21.4.3 代表模型

<strong>OpenAI Realtime API</strong>：2024 年推出，基于 GPT-4o，支持 WebRTC 协议。开发者可以用它构建语音对话应用，延迟在 500-800ms 之间。它本质上是一个云端的端到端语音模型，客户端发送音频到 API，API 返回音频。

<strong>Qwen3-Omni</strong>（通义千问）：阿里巴巴千问团队 2025 年发布的端到端全模态模型。它采用了"Thinker-Talker"架构思维链设计——Thinker 负责语义理解，Talker 负责语音生成。这个分离的设计让每个模块可以独立优化。

<strong>Step-Audio 2</strong>（阶跃星辰）：2025 年发布的语音模型，在副语言理解（paralinguistic understanding）上取得了突破性进展。它在 MoCha-En 数据集上的副语言理解准确率达到 83.09%，而 GPT-4o Audio 的基线只有 43.45%。这意味着它能更准确地识别语气、情绪、笑声等非语言信号。

## 21.5 范式三：全双工交互模型

全双工（Full-Duplex）是语音交互的终极形态——用户和系统<strong>同时</strong>在说话和听，就像两个人在面对面聊天。你可以在说话的中途听到对方说"嗯""对""真的吗"，这种反馈是自然对话的核心特征。

### 21.5.1 Moshi

Moshi 是法国 Kyutai 实验室 2024 年发布的开源全双工语音模型，是第一个公开的、可运行的全双工语音 Agent。它的核心创新是引入了<strong>双音频流</strong>：一个流处理用户的输入，一个流生成系统的输出，中间通过"内心独白"（inner monologue）文本进行协调。

Moshi 的工作流程是：

1. 用户说话时，音频流 1 实时编码
2. "内心独白"层持续输出文本线程——这相当于模型的思考过程
3. 音频流 2 基于内心独白和用户输入，实时生成语音

延迟约 200ms，达到了人类对话的感知阈值。用户几乎感觉不到延迟，可以自然地打断和回应。

### 21.5.2 Thinking Machines Lab 的交互模型

Thinking Machines Lab（TML）2025 年发布的交互模型将全双工能力提升到了新的高度。他们提出的<strong>微轮次</strong>（micro-turns）概念将对话切分为约 200ms 的颗粒度，每个微轮次都是一次"听→理解→反应"的小循环。

TML Interaction-Small 是一个 276B MoE 模型，在实时性上达到了接近人类的水平。它能够处理复杂的对话场景，包括：

- **实时翻译**：用户说英文，系统实时翻译成中文并输出语音
- **情感协调**：检测到用户情绪低落时，自动调整语气和回复策略
- **打断与重叠**：正确处理用户打断，不丢失上下文

### 21.5.3 GPT-Live 的实践

GPT-Live 是 GPT-4o Audio 的持续对话模式。它的特点是：

- 持续的音频流处理，而非分轮次
- 支持任意的"次轮次"交互（sub-turn interaction）
- 可以一边说一边修改自己的输出内容
- 真正的实时翻译能力

### 21.5.4 快慢解耦

全双工架构面临一个根本矛盾：<strong>实时响应需要"快"（潜意识级的反应），而深度思考需要"慢"（高级推理）</strong>。解决这个矛盾的关键是<strong>快慢解耦</strong>：

- **交互模型**（快）：负责实时语音处理、副语言理解、流畅对话衔接。它对延迟极度敏感，但对推理深度要求不高
- **后端推理模型**（慢）：负责复杂的语义理解、知识检索、逻辑推理。它可以花 10 秒甚至更长时间思考，然后把结果传递给交互模型

这两个模型通过一个<strong>意图路由</strong>：当交互模型判断用户的问题需要深度推理时，会交给后端推理模型；否则自己直接回应。这种架构在 GPT-Live 和 TML 系统中都有体现。

![全双工快慢解耦架构](/images/courses/ai-agent/fig9-7.svg)

## 21.6 思考架构的取舍

全双工模式下，实时响应和深度思考的矛盾更加尖锐。如何让模型既能在 200ms 内回应"嗯嗯"，又能花 30 秒推导一个数学题？目前有三种主流方案。

### 21.6.1 Plan A：快速回应 + 慢速答案

这是大多数系统的默认做法：用户问完问题后，系统先用"好的，让我想想..."之类的填充词回应，然后开始思考，最后给出完整答案。

**问题**：
- 对于简单问题（"今天星期几"）也要过一遍"慢速"流程，造成不必要的延迟
- 快速回应和慢速答案之间可能不一致，用户能感觉到"这是两个系统拼起来的"

### 21.6.2 Plan B：快速交互 + 慢速顾问

把系统拆成两个组件：一个负责"闲聊"级别的交互（实时、轻量），另一个在后台持续思考并给出建议。当交互模型遇到复杂问题时，会用状态栏之类的 UI 信号告诉用户"正在思考中"。

**问题**：
- 仍然无法实现"一边思考一边说"——人类在说话时大脑也在思考，这种"边说边想"的体验很难模拟
- 两套模型的输出风格可能不一致

### 21.6.3 Plan C：端到端思维+表达

Step-Audio R1 提出的方案是最前沿的尝试。它的核心问题被称为<strong>Textual Surrogate Reasoning</strong>（文本代理推理）问题：当语音模型需要思维链时，应该用什么形式的推理？

直接用文本思维链？问题在于文本和语音的 token 分布完全不同。用语音思维链？训练和推理的成本极高。

Step-Audio R1 的解决方案是<strong>MGRD（Modality-Grounded Reasoning Distillation，模态接地推理蒸馏）</strong>：让文本推理模型教会语音推理模型如何思考。蒸馏过程中，语音模型学会在语音 token 空间中建立推理链，而不是先把语音转成文本再推理。

![Step-Audio R1 推理蒸馏架构](/images/courses/ai-agent/fig9-8.svg)

更深层的架构是<strong>MPS（Mind-Paced Speaking，心语同步）</strong>双脑架构，将推理过程拆为两部分：

- **构思大脑（Formulation Brain）**：负责语义规划、逻辑推理、内容生成。它"想说什么"
- **表达大脑（Articulation Brain）**：负责语音合成、韵律控制、副语言表达。它"怎么说"

两个大脑以流水线方式并行工作：构思大脑输出一个语义片段，表达大脑立刻将其合成为语音。这种流水线并行使第一个音节的延迟缩短到了约 350ms。

## 21.7 Computer Use——GUI 自动化 Agent

如果说语音 Agent 是在改变"交互方式"，那么 Computer Use（计算机使用）Agent 是在改变"交互对象"——从对话框变成整个操作系统界面。

### 21.7.1 动作空间设计

Computer Use Agent 的核心设计问题是<strong>动作空间</strong>：Agent 应该能对 GUI 做什么？

最基本的动作集包括：

| 动作 | 参数 | 说明 |
|------|------|------|
| click | x, y, button | 在屏幕坐标点击 |
| type | text | 输入文字 |
| scroll | dx, dy | 滚动 |
| screenshot | — | 获取当前屏幕截图 |
| keypress | key | 键盘快捷键 |

看起来简单，但细节非常复杂。比如 click 动作需要决定点击的精确坐标，而坐标可能会因为窗口大小、系统缩放设置、分辨率的不同而完全不同。

### 21.7.2 视觉定位的挑战

多模态 Computer Use Agent 面临的视觉定位（visual grounding）问题比传统 RPA 难得多：

- **动态 UI**：网页元素的位置、样式、可见性都会动态变化
- **非确定性布局**：同样的应用在不同屏幕尺寸、不同操作系统下的布局完全不同
- **无障碍信息缺失**：很多 UI 元素没有 aria-label、alt text 等辅助信息

人类可以通过"那个蓝色的按钮""第三行的输入框"来定位元素，但对模型来说，这需要在截图和动作之间建立精确的空间映射。

### 21.7.3 感知挑战

90% 的 Computer Use Agent 都只处理静态截图。这意味着它们完全"看不见"两样东西：

- **动画**：加载动画、过渡效果、弹出提示——这些动态信息对理解系统状态至关重要
- **声音**：系统错误提示音、消息通知音——这些听觉信号可能意味着 Agent 的操作出了问题

真正能"看动画、听声音"的多模态 Computer Use Agent 仍处于研究阶段。

### 21.7.4 移动端生态的壁垒

移动端 Computer Use 的挑战比桌面端大得多。苹果和安卓的底层架构完全不同，且都缺少标准化的无障碍接口泄露。iOS 的 VoiceOver 和 Android 的 TalkBack 虽然是无障碍工具，但它们产出的信息是面向视障用户的，不是面向 Agent 的。

### 21.7.5 实时性：未解的核心挑战

Computer Use 的实时性比语音更难。问题在于：

1. GUI 的响应时间不确定性极高——一个操作可能 100ms 就有反馈，也可能 10 秒后才加载完成
2. Agent 需要等待某操作完成后才能执行下一操作，但这个"完成判断"本身就是难题
3. 截图频率太低会漏掉关键状态变化，太高（每秒 30 帧）又导致计算成本爆炸

目前的主流方案是"事件驱动的增量观察"——利用操作系统的无障碍事件流（Accessibility Events）来替代截图轮询，只在 UI 发生变化时才触发模型推理。

## 21.8 机器人操作

当 Agent 从屏幕走进物理世界，挑战的复杂度再次跃升。机器人操作被认为是多模态 Agent 的"终极考场"。

### 21.8.1 算法而非硬件的瓶颈

很多人认为机器人卡在硬件上（电机不够精准、传感器不够灵敏），但事实是<strong>软件和算法才是真正的瓶颈</strong>。以灵巧手（dexterous hand）为例，市面上已经有 20+ 自由度的灵巧手硬件，精度足够完成大多数精细操作任务。但问题在于：

- 如何让模型理解"用手指捏起一枚鸡蛋"涉及的多关节协同运动？
- 如何在不同的机械臂、不同的灵巧手之间迁移技能？

这些是算法问题，不是硬件问题。

### 21.8.2 两层的架构

机器人操控智能体的标准架构是两层的：

- **规划层（Planning）**：接收高层次指令（"把桌子上的杯子拿给我"），分解为一系列子目标（→定位杯子→规划抓取路径→移动到指定位置→释放）
- **控制层（Control）**：执行具体的关节角度、力矩控制信号，完成每个子目标

从这个角度看，规划层与 Computer Use 的"任务分解"本质相同，控制层则是机器人特有的低层问题。

### 21.8.3 长程规划：从 VLM 到具身推理模型

早期机器人规划依赖手工编写的任务脚本，现在则用 VLM（视觉-语言模型）来替代。VLM 可以理解场景、分析任务、分解步骤。但 VLM 在长程规划上的能力有限——它善于理解"瞬时"场景（一张桌子的照片），但不善于跟踪"一段时间内的变化"。

最新的方向是<strong>专属具身推理模型</strong>（embodied reasoning model），它们将时序感知、物理规律理解、错误恢复能力内置到模型中。

### 21.8.4 VLA：从演示数据到跨本体泛化

VLA（Vision-Language-Action）模型是机器人领域最重要的新范式之一。它将视觉输入、语言指令和动作输出统一在一个模型中。

VLA 的核心 pipeline：

1. **数据采集**：通过遥操作（teleoperation）采集人类操控机器人的演示数据
2. **预训练**：在互联网数据上预训练视觉和语言能力
3. **微调**：在机器人演示数据上微调，学习"给定当前视觉输入和语言指令，输出下一个动作"
4. **跨本体泛化**：在训练过程中引入多种机器人平台的数据，让模型学会"不同物理结构的机器人如何执行相似的任务"

RT-2（Robotic Transformer 2，Google 2023）是 VLA 的代表工作。它证明了一个关键结论：**从互联网预训练中获得的视觉-语言知识可以有效地迁移到机器人动作预测中**。

### 21.8.5 Sim2Real：模拟到现实迁移

Sim2Real 转移是机器人学习的核心难题：在模拟器中训练的策略，部署到真实机器人上后，往往会因为<strong>模拟与现实之间的各种差距</strong>而表现不佳。

这些差距包括：

- **视觉差异**：模拟器中的光照、纹理、反射永远无法完全复现真实世界
- **物理差异**：摩擦力、惯性、柔性形变等物理属性在模拟器中只能近似建模
- **感知差异**：真实传感器的噪声分布与模拟器完全不同

解决 Sim2Real 的常见策略包括域随机化（domain randomization，在训练时随机化视觉和物理参数）和系统辨识（system identification，精确建模真实系统的物理参数）。

真实机器人采集数据的成本极高。一次遥操作数据采集可能需要一名熟练操作员花数小时，而采集到的数据只能用于训练特定机器人上的特定任务。这使得高效的数据利用和跨本体泛化成为该领域的核心研究方向。

## 21.9 本章小结

多模态与实时交互正在重塑 AI Agent 的能力边界。从语音 Agent 的三代架构演进中，我们看到一个清晰的趋势：**从串行、轮次、单模态，走向并行、连续、多模态**。

三个关键要点值得记住：

第一，<strong>实时性是所有多模态系统的核心约束</strong>。无论是语音的 200ms 全双工，还是 Computer Use 的毫秒级 UI 响应，或是机器人控制的数 kHz 控制频率，"延迟"是衡量系统优劣的最关键指标。

第二，<strong>架构的选择取决于信息 bottleneck 的定义</strong>。如果任务相关的信息都可以通过文本传递，级联流水线就足够；如果需要保留非语言信息（情绪、语气、环境音），端到端 Omni 模型更合适；如果需要真正的自然交互体验，全双工架构是必经之路。

第三，<strong>快慢解耦是多模态 Agent 的通用设计模式</strong>。无论是语音 Agent 的"交互模型+推理模型"，还是机器人 Agent 的"规划层+控制层"，将"快速响应"和"深度思考"拆解为两个独立系统，是平衡实时性和智能水平的有效手段。

多模态 Agent 的时代才刚刚开始。随着 Whisper、GPT-4o Audio、Step-Audio 2 等模型能力的不断提升，以及 Computer Use、VLA 等范式的逐渐成熟，我们有理由相信：未来的智能体将不再局限于对话框，而是能看、能听、能说、能操作现实世界。
