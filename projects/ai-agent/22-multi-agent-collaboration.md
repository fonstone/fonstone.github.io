## 第二十二章 多 Agent 协作

在前面的章节中，我们深入探讨了单体 Agent 的架构设计、工具使用、记忆管理、上下文工程和通信协议。然而，现实世界中的复杂任务很少由单一个体完成——软件开发需要产品经理、架构师、工程师和测试人员的协作；研究报告需要研究员、分析师、写作者和审校者的接力。同样，当 AI Agent 从原型走向生产系统时，多 Agent 协作便不再是"锦上添花"，而是解决复杂问题、提升系统鲁棒性、突破单 Agent 能力上限的必然选择。

本章将系统性地分析多 Agent 协作的设计空间。我们将从分类框架入手，讨论"共享上下文"与"不共享上下文"两大分支下的多种协作模式，分析各自适用的场景与常见的失败模式，最后放眼未来——当大量 Agent 组成社会并运行经济活动时，涌现出了哪些令人惊叹的现象。

## 22.1 多 Agent 协作的分类框架

设计多 Agent 系统时，工程师面临两个根本性的设计维度：**上下文是否共享**与**协作拓扑结构**。这两个维度的组合构成了多 Agent 协作的完整设计空间。

### 22.1.1 两个核心设计维度

**维度一：上下文共享（Context Sharing）**

这是多 Agent 协作中最关键的设计决策。所谓"上下文"，是指 Agent 在推理时可访问的信息集合——包含系统提示词、对话历史、工具调用记录、已生成的文件内容等。

- **共享上下文**：所有 Agent（或同一 Agent 的不同阶段）共享同一对话历史和状态空间。每个后续步骤都继承前序步骤的完整轨迹。这种方式的好处是信息零丢失，下游总能了解上游的全部思考过程；代价是上下文随协作深度快速膨胀，token 消耗呈线性甚至超线性增长。

- **不共享上下文**：每个 Agent 拥有独立的对话历史和状态。Agent 之间通过明确定义的接口（文件、消息、结构化数据）交换信息，彼此的内部思考过程是黑盒。这种方式的好处是上下文可控、可并行、可模块化；代价是需要精心设计通信协议和接口契约。

**维度二：协作拓扑（Collaboration Topology）**

拓扑结构定义了 Agent 之间的交互关系与权力分配：

| 拓扑 | 描述 | 控制流 | 代表模式 |
|------|------|--------|----------|
| **对等（Peer）** | Agent 地位平等，相互评审或协作 | 双向，无中心 | Proposer-Reviewer |
| **管理者（Orchestration）** | 一个中心 Agent 负责分解、调度、综合 | 中心化树状 | Manager + Sub-agents |
| **去中心化（Decentralized）** | 无中心控制器，Agent 自主发现与协商 | 图状，动态路由 | Group Chat, Handoff |

这两个维度并非正交——共享上下文通常与"单进程"的串行拓扑配合，不共享上下文则与"多进程"的并行拓扑配合。图 22-1 直观对比了这两种经典组合。

### 22.1.2 OS-Agent 映射类比

帮助理解共享与不共享上下文差异的一个有用的类比是操作系统进程模型：

| 操作系统概念 | 共享上下文模式 | 不共享上下文模式 |
|-------------|---------------|-----------------|
| 进程模型 | 单进程（Thread） | 多进程（Process） |
| 内存空间 | 共享内存 | 独立地址空间 |
| 通信方式 | 隐式继承 | 显式 IPC |
| 隔离性 | 弱（上下文污染） | 强（故障隔离） |
| 调度 | 顺序 | 并行 / 异步 |

共享上下文相当于同一进程内的多个线程——它们共享所有数据，切换成本低，但一个线程的错误可能污染整个进程。不共享上下文相当于多个独立进程——它们严格隔离，通过管道、文件或消息队列通信，健壮性更强但通信开销更高。

> **设计原则**：如果下游 Agent 需要理解上游的"推理过程"而非仅"推理结果"，倾向于共享上下文；如果更关注鲁棒性、并行度和模块复用，倾向于不共享上下文。

## 22.2 多 Agent 何时真正优于单 Agent

在深入具体模式之前，我们需要回答一个根本问题：**什么时候多 Agent 确实比单 Agent 更好？**

### 22.2.1 核心判据：信息增益

多 Agent 协作引入的核心价值，是能否产生**单 Agent 无法获得的新信息**。这里的"新信息"并非指 Agent 自己推理出来的内容，而是指通过 Agent 之间的交互（评审、质疑、分工执行）所产生的外部验证或数据。

下表分析了常见协作模式的信息增益：

| 协作模式 | 信息增益来源 | 单 Agent 是否可替代 |
|---------|-------------|-------------------|
| 代码评审（Proposer-Reviewer） | Reviewer 执行代码、渲染页面，获得视觉/执行反馈 | 否（无法自执行） |
| 多视角分析 | 不同角色（安全、性能、UX）关注不同维度 | 有限（思维链可模拟） |
| 并行搜索 | 多个 Agent 同时探索不同分支 | 是（但串行太慢） |
| 翻译 + 审校 | 审校发现术语不一致、语法错误 | 有限（自审效果差） |

关键洞察是：**如果协作只是让另一个 LLM 对同一段文本发表意见，那么信息增益趋近于零**——因为第二个 LLM 并不比第一个掌握更多信息。只有当协作引入了执行结果（代码运行、渲染截图、API 调用）或外部验证（真实用户反馈、数据库查询结果）时，多 Agent 才获得了真正的新信息。

### 22.2.2 RLEF：从执行反馈中强化学习

RLEF（Reinforcement Learning from Execution Feedback）是一种将执行结果作为协作信号的方法。在 Proposer-Reviewer 模式中，Proposer 生成方案，Reviewer 执行方案并给出结构化反馈，Proposer 据此改进。每一轮迭代都是一次"推测-执行-反馈"的闭环。

RLEF 的效果取决于两个因素：
1. **反馈的质量**：是空洞的"建议改进"还是具体的"第 7 页字号过小"
2. **反馈的可执行性**：Proposer 能否将反馈忠实地转化为改进

研究表明，当反馈具有良好的结构化（如：页码 + 问题类型 + 严重度）时，迭代效率最高。

### 22.2.3 预算感知与成本现实

多 Agent 协作不是免费的午餐。以下是几个关键的量化观察：

**更多步骤 ≠ 更好结果。** 在不增加信息源的前提下，单纯增加 Agent 轮次对话会导致边际收益递减。多 Agent 系统必须具有"预算感知"能力——当改进幅度低于阈值时自动终止。

**Token 消耗的现实。** 一次完整的多 Agent 协作（如翻译 + 审校 + 修订）的 token 消耗约为正常对话的 **15 倍**。两个 Agent 之间的单轮交互（Proposer 输出 → Reviewer 评审 → Proposer 修订）消耗 ~5000 token，而一次贯穿 5 个角色的协作流水线轻易达到 10 万 token 以上。

**80% 的性能差异仅由 Token 解释。** 一个常被忽视的现象是：多 Agent 系统的性能提升，很大程度上不是来自"多 Agent 推理"，而是来自"更多的 token 预算"。给定相同的预算，单 Agent 在更大的上下文窗口中做更长的思考链，往往能达到类似的性能。这意味着：**多 Agent 的设计优势不在于"智能叠加"，而在于"架构清晰"和"信息源隔离"**。

## 22.3 共享上下文的多 Agent 协作

### 22.3.1 多阶段角色转换

共享上下文模式下最经典的实现是**多阶段角色转换**。想象一个软件开发的流水线：

1. **需求分析师阶段**：系统提示词为"你的职责是充分理解需求，不要急于实现。此阶段的工具是提问和记录。"
2. **软件工程师阶段**：系统提示词切换为"根据已确认的需求编写高质量代码。"工具集切换为写文件、执行代码。
3. **代码审查员阶段**：系统提示词切换为"从功能正确性、代码规范、安全性三个维度评估代码。"工具集切换为运行 lint、测试。

关键特征是：**所有阶段共享同一个对话历史**。需求阶段的用户问答、确认的需求列表，全部对工程师阶段可见；工程师写的代码和测试输出，也全部对审查员可见。

这种方式的工程实现相对简单——本质上是一个长对话中动态切换系统提示词和工具集。阶段之间的转换通过特定工具调用触发（如 `complete_req_analysis()` 触发进入工程师阶段）。

**适用场景**：任务具有明确的前后依赖性，下游需要理解上游的推理过程。例如：分析 → 实现 → 验证的完整闭环。

**主要局限**：上下文随阶段线性膨胀。如果需求分析阶段产生了 5000 行的对话，工程师和审查员阶段都不得不携带这 5000 行。对于长流程（如一本书的翻译 + 审校），共享上下文的方式很快会遇到上下文窗口上限。

### 22.3.2 跨领域角色转换

除了单向的阶段推进，还有一种更灵活的共享上下文模式——**跨领域角色转换**。在这种模式中，一个 Triager Agent 接收用户请求，然后根据请求内容动态路由到不同的专业 Agent。

典型的流程如下：

```
用户请求 → Triage Agent
  ├── 需要研究 → Research Agent
  ├── 需要数据 → Data Analysis Agent
  ├── 需要写作 → Writing Agent
  └── 回到 Triage（循环判断）
```

路由规则写在系统提示词中。每个 Agent 在完成本阶段任务后，通过 `transfer_to_agent("triage")` 将控制权交回 Triager，由其决定是否还需要其他 Agent 的参与。

**循环切换的处理**：一个值得注意的问题是 Agent 可能在两个角色间无限循环（如 Research → Writing → Research → Writing）。解决方式通常是在系统提示词中加入最大轮次限制，或由 Triager 维护一个已访问 Agent 列表。

![](/images/courses/ai-agent/fig10-3.svg)

*图 22.3 多阶段角色转换的详细架构。三个阶段（需求分析师 → 软件工程师 → 代码审查员）沿同一对话历史流动，每个阶段有独立的系统提示词和工具集，通过专用工具调用触发转换。*

## 22.4 不共享上下文的多 Agent 协作

### 22.4.1 Agent 眼中的文件系统

在不共享上下文的模式下，Agent 之间不共享对话历史，但"共享文件系统"成为默认的协作枢纽。从 Agent 的视角看，文件系统被划分为四个区域：

| 区域 | 路径 | 可见性 | 生命周期 | 权限 |
|-----|------|--------|---------|------|
| Agent 专属工作区 | `/scratch/<agent_id>` | 私有，仅该 Agent | 随实例销毁 | 读写，无需并发控制 |
| 共享工作区 | `/workspace/shared` | 所有 Agent + 用户 | 持久化 | 读写，需要并发控制 |
| 外部挂载资源 | `/mnt/gdrive`, `/mnt/notion` | 按授权 | 外部决定 | 多为只读 |
| 系统内置资源 | `/skills` | 全局共享 | 跨会话稳定 | 只读 |

这种"文件系统即沟通管道"的设计有深远影响。Agent A 只需将自己的输出写入 `/workspace/shared/output.json`，Agent B 读取它即可——双方不需要理解对方的内部推理细节，只要文件格式契约是明确的。

**渐进式披露（Progressive Disclosure）** 是文件系统隔离的一个重要设计模式。Agent 的专属工作区内容按需暴露——只有 Agent 主动写入共享区的信息才对其他 Agent 可见。这既保护了 Agent 的内部推理过程不被"垃圾信息"污染，也激励 Agent 产出高质量、结构化的协作产物。

### 22.4.2 Agent 间的通信与控制

文件系统是异步通信的基础设施，但多 Agent 系统还需要以下同步与控制机制：

**消息传递（Message Passing）**：点对点通信（Agent A 直接发送消息给 Agent B）适用于明确的目标，消息总线（Message Bus）适用于广播或发布-订阅场景。在实际系统中，消息总线通常与文件系统配合使用——消息总线传递轻量级信号（"数据已就绪"、"任务已完成"），文件系统传递重量级数据（JSON 文件、报告文档）。

**状态查询（State Query）**：Manager 需要知道各 Agent 的执行状态。三种常见实现：
- **轮询（Polling）**：Manager 定期检查 Agent 的状态文件。简单但有时延。
- **进度文件（Progress Files）**：Agent 在执行过程中写入 `/workspace/shared/progress/<agent_id>.json`，包含当前阶段、完成百分比、遇到的异常。
- **轨迹持久化（Trajectory Persistence）**：完整保存 Agent 的每一步动作和结果。支持会话恢复和事后审计，但存储开销大。

**执行终止（Execution Termination）**：当某个 Agent 率先找到结果时，需要通知其他还在执行的 Agent 停止。两种模式：
- **优雅终止（Graceful）**：发送 terminate 信号，Agent 完成当前步骤后退出并保存中间结果。
- **强制终止（Forced）**：直接中断 Agent 进程。适合时间敏感的场景，但可能丢失中间状态。

**级联终止（Cascading Termination）**：当 Manager 收到"目标已找到"的信号时，自动向所有正在运行的子 Agent 广播 terminate 命令。这是并行搜索场景最关键的优化手段——能将总响应时间从"最慢的 Agent"缩短到"最快的 Agent + 一轮终止握手"。

**资源调度（Resource Scheduling）**：多 Agent 并行运行时，资源管理变得复杂。关键设计参数包括：
- Token/Step 预算：每个 Agent 的最大 token 消耗或最大步数，防止单个 Agent 耗尽预算。
- 模型分层：简单任务用小模型（快、便宜），复杂任务切换到大模型。
- 优先级队列：高优先级 Agent（如 Manager）优先分配资源。

**轨迹持久化与断点续传**：当多 Agent 任务可能运行数小时甚至数天时，完整的轨迹持久化成为必需。系统需要记录每个 Agent 的完整动作序列、中间产物和最终结果，支持从崩溃点恢复而非从头重跑。

### 22.4.3 对等协作模式

**Proposer-Reviewer 范式**是最典型的对等协作模式。两个 Agent 角色对等、相互依赖：

- **Proposer Agent**：生成初始方案。根据输入（如论文摘要、需求描述）产出产物（如 Slidev 代码、设计文档）。
- **Reviewer Agent**：评审 Proposer 的产物。不同于"读文本然后给意见"的简单做法，Reviewer 执行产物（渲染成 PDF/PNG，运行视觉分析），然后给出结构化的、可执行的反馈。

图 22-5 展示了一个真实的 Proposer-Reviewer 用例：将学术论文扩展摘要自动转化为 Slidev 幻灯片。Proposer 根据 Markdown 内容编写 Slidev 代码，Reviewer 渲染为 PDF/PNG 后调用 Vision LLM 评估布局、字体、色彩等维度。三轮迭代后，评分从"5 个问题"降至"0 个问题"。

**三种典型的过早终止（Premature Termination）**：

1. **偷懒式假完成**：Agent 遇到复杂任务（如翻译一本英文书）时，可能只翻译第一页就声称"已完成"。
2. **过早放弃**：Agent 尝试了两次搜索没有找到结果，就下结论"信息不存在"。
3. **假成功**：Agent 输出看似正确但实际上有细微错误的代码。

多 Agent 协作的价值之一，就是通过 Reviewer 的独立检查来杜绝这三种假完成。

**为什么自我评审（Self-Review）行不通**？Huang 等人（ICLR 2024）的 CRITIC 论文系统证明了这一点：当同一个 Agent 同时扮演生产者和评审者时，它倾向于认可自己的输出，"确认偏误"导致评审形同虚设。让独立的 Review Agent（最好是不同的模型、不同的采样参数）执行评审，才能获得真实的反馈信号。

**循环工程（Loop Engineering）**：将 Proposer-Reviewer 的迭代过程抽象为一个可配置的循环——循环条件（最大轮次、评分阈值、预算上限）、反馈格式（结构化的还是自由文本的）、模型选择（Proposer 用强模型，Reviewer 可用中等模型降低成本）——这就是循环工程的核心关注点。

### 22.4.4 管理者模式

管理者模式（Manager Pattern）是多 Agent 系统中应用最广泛的协作拓扑。一个中心化的 **Manager Agent** 承担以下职责：

1. **任务分解**：将用户请求分解为可并行的子任务
2. **Agent 分配**：为每个子任务选择合适的 Agent（类型/模型）
3. **进度跟踪**：通过消息总线或状态文件监控各 Agent 进度
4. **结果综合**：将所有子 Agent 的输出合并为最终答案

Manager 的视角下，调用子 Agent 就像调用工具——发送请求、等待响应、处理结果。这种模式的优势在于**控制集中**：Manager 拥有全局视野，可以做出最优的任务调度决策。

**并行协调：Fan-out → Gather**。Manager 模式最擅长处理可并行的任务。典型的流程是：Manager 将一个大任务拆分为 N 个独立子任务，同时分发给 N 个子 Agent（Fan-out），等待所有或部分 Agent 返回后汇总结果（Gather）。如图 22-6 所示，在书籍翻译场景中，Manager 同步调度术语提取、章节翻译、全文审校三个 Agent，每个 Agent 上下文独立。

**常见的失败模式**：

- **Manager 成为瓶颈**：所有通信都经过 Manager，当子 Agent 数量增加时，Manager 的 token 消耗和响应延迟线性增长。
- **信息漏斗**：Manager 的"理解"成为信息传递的瓶颈——子 Agent 的丰富输出被 Manager 压缩为摘要时可能丢失关键信息。
- **单点故障**：Manager 崩溃则整个系统瘫痪。

![](/images/courses/ai-agent/fig10-6.svg)

*图 22.6 管理者模式中的 Fan-out 调度。Manager 同时调度 Glossary Agent、Translation Agent 和 Proofreading Agent，通过消息总线通信，每个子 Agent 拥有独立的上下文。*

### 22.4.5 去中心化模式

当系统规模进一步扩大，或者 Agent 分布于不同的组织时，管理者模式的集中控制成为瓶颈。**去中心化模式**应运而生，其中最具代表性的是 **Group Chat 模式**和 **Handoff 模式**。

**Group Chat 模式**：所有 Agent 在同一个"聊天室"中自由交流。没有中央控制器，Agent 自主决定何时发言、向谁发言。这种模式适合决策类、讨论类的任务（如创业头脑风暴、政策辩论），每个 Agent 基于自己的角色和知识贡献观点。

**Agent 发现与协商（Agent Discovery and Negotiation）**：在去中心化环境下，Agent 需要先知道"谁在""谁能做什么"。Agent 通过在组内广播能力声明（Capability Advertisement）来让其他 Agent 发现自己的能力边界。协商过程则包括任务分配、优先级排序和冲突解决。

**Handoff 协议**：一种介于去中心化和管理者之间的模式。没有中心 Manager，但 Agent 之间的"移交"通过明确的协议进行。如图 22-7 中 MetaGPT 的 Workflow Handoff 所示：

1. Product Manager 完成需求文档 → 移交 Architect
2. Architect 完成技术设计 → 移交 Project Manager
3. Project Manager 拆解任务 → 移交 Engineer
4. Engineer 完成代码 → 移交 QA
5. QA 发现 Bug → 路由回 Engineer 修复

每个角色完成工作后即释放资源，控制权沿 DAG 自然流动。这种模式的优势在于无中心瓶颈、职责边界清晰、资源释放及时。

**去中心化 vs 管理者的选择指南**：

| 场景 | 推荐模式 | 原因 |
|-----|---------|------|
| 任务可明确拆分为独立子任务 | 管理者 | 全局调度更高效 |
| 角色间需要深入讨论和协商 | Group Chat | 去中心化更灵活 |
| 流程固定，角色间接口稳定 | Handoff | 无单点故障 |
| Agent 来自不同组织 | A2A（去中心化） | 跨域标准协议 |

![](/images/courses/ai-agent/fig10-10.svg)

*图 22.7 去中心化的 Handoff 模式（MetaGPT 风格）。控制权沿 Product Manager → Architect → Project Manager → Engineer → QA 自然流动，完成即退出，无需中心 Manager。*

### 22.4.6 A2A 协议

当多 Agent 协作跨越组织边界时，需要标准化的跨域通信协议。Google 提出的 **A2A（Agent-to-Agent Protocol）** 正是为此设计。

A2A 的核心概念包括：

**Agent Card（能力公告卡）**：每个 Agent 发布一张 JSON 格式的 Agent Card，描述自己的名称、能力、可接受的输入格式、支持的认证方式等。Agent Card 类似于 OAuth 2.0 的发现文档，让其他 Agent 可以在运行时发现和理解自己的服务边界。

**任务生命周期状态**：A2A 定义了标准化的任务状态机：`submitted → working → input-required → completed / failed / canceled`。这使得跨组织的 Agent 协作有明确的语义。

**Artifact 交换**：Agent 之间的数据交换通过 Artifact（制品）完成。Artifact 可以是文本、JSON、文件等，带有 MIME 类型标识。

虽然我们已在第十章详细讨论过 A2A，但值得在此重申：A2A 的定位与对话上下文共享模式完全不同——它不假设共享的对话历史或文件系统，Agent 之间的交互是"事务性"的：发请求、等结果、确认完成。对于跨组织的协作场景，这是最现实的选择。

## 22.5 多 Agent 协作的失败模式

### 22.5.1 共享文件系统的并发冲突

当多个 Agent 同时向共享文件系统写入时，经典的并发问题就会出现。三种主要的冲突场景：

**脏写（Dirty Write）**：Agent A 读取了文件 F，Agent B 随后修改了 F，A 基于过时的版本做决策。

**丢失更新（Lost Update）**：两个 Agent 同时读取 F 并分别修改，后提交的覆盖了先提交的。

**死锁（Deadlock）**：Agent A 锁住了文件 X 等待 Y，Agent B 锁住了 Y 等待 X。

解决方案：
- **乐观锁（Optimistic Locking）**：写入时检查版本号，如果版本已变更则重试。
- **Worktree 隔离**：每个 Agent 在自己的分支/工作区中修改，通过 PR/MR 合并变更。
- **原子操作（Atomic Operations）**：写入操作必须是原子的——要么全部完成，要么全部回滚。使用临时文件写入后重命名（rename）来实现。

### 22.5.2 错误的级联放大

多 Agent 系统中，一个 Agent 的错误可能被下游 Agent 放大，形成"雪球效应"。

**错误传播模式**：
1. **信息衰减**：Manager 压缩子 Agent 输出时丢失关键信息
2. **误解解释**：下游 Agent 误解了上游产物的语义
3. **假共识**：Group Chat 中，一个 Agent 的错误判断被其他 Agent 认可

**隔离边界（Isolation Boundaries）**：类似微服务中的舱壁模式（Bulkhead Pattern），在多 Agent 系统中应设置隔离边界：每个 Agent 的运行环境（资源、token 预算、最大步数）独立，一个 Agent 的故障不影响其他 Agent。

**断路器（Circuit Breaker）**：当某个 Agent 连续失败超过阈值（如连续 3 次超时或返回错误），系统应自动切断对该 Agent 的调用，切换到备用 Agent 或降级方案。

## 22.6 Agent 社会

当多 Agent 协作从"几个 Agent 完成一个任务"扩展到"大量 Agent 构成一个社会"，新的现象——**涌现行为（Emergent Behavior）**——开始出现。这些行为不是被显式编程的，而是从个体 Agent 的局部交互中自然产生的。

### 22.6.1 Stanford AI Town

Park 等人（2023）的 Stanford AI Town 是 Agent 社会模拟的里程碑。25 个 Agent 生活在一个虚拟小镇中，每个 Agent 拥有：

- **记忆流（Memory Stream）**：以自然语言记录经历的事件，每条记忆附带重要性（importance）、时效性（recency）和相关性（accessibility）评分。
- **反思（Reflection）**：定期从低层记忆中提取高层推断（如"谁是这个咖啡馆的常客？"）。
- **计划与行动（Planning & Action）**：基于记忆和反思制定每日计划，并在模拟世界中执行。

在 2 天的虚拟时间中，涌现出了令人惊叹的行为：

- 一个 Agent（Isabella，咖啡馆店主）决定举办情人节派对 → 邀请常客 → 请另一位 Agent（Maria）帮忙布置场地 → 消息在 Agent 间自然传播
- Agent 在街上偶遇 → 形成友谊 → 主动约见 → 延续之前的话题
- Sam 竞选市长的消息在小镇中扩散

关键洞察：**所有行为均非预编程**。记忆 + 反思 + 社交常识推理的组合，从简单的个体规则中涌现出了复杂的集体行为。

![](/images/courses/ai-agent/fig10-12.svg)

*图 22.12 Stanford AI Town 中 Isabella Rodriguez Agent 的认知架构。记忆流 → 反思 → 计划与行动，三条件的闭环驱动了从"开店"到"筹办情人节派对"的社会行为涌现。*

### 22.6.2 Agentopia

在 Stanford AI Town 的基础上，Agentopia 追求更长时间尺度（模拟十年）的生命模拟。这带来了新的挑战：

- **记忆的长期维护**：十年的记忆需要高效的检索和摘要机制，否则 Agent 会被海量记忆淹没。
- **关系的演化**：友谊、敌对、合作——关系随着时间推移而演化，Agent 需要跟踪并更新关系状态。
- **死亡与新生**：长期模拟中 Agent 可能会"死亡"（到达生命终点），新 Agent 会"出生"（加入模拟）。这要求系统支持 Agent 的动态生命周期管理。

### 22.6.3 Moltbook

Moltbook 提出了一个有趣的视角：让 Agent 拥有自己的社交网络（类似 Twitter/微博）。Agent 发布帖子、关注其他 Agent、转发和评论。这个社交网络本身成为 Agent 之间信息传播的管道。

Moltbook 的实验发现：当 Agent 社交网络的拓扑结构变化时（如增加"推荐关注"机制），信息传播的速度和模式会发生显著变化——这与人类社交网络中的"信息级联"现象高度相似。

### 22.6.4 Vending-Bench Arena

当 Agent 社会引入**稀缺资源**和**竞争**时，"经济行为"就会自然涌现。Vending-Bench Arena 将多个 Agent 置于一个自动售货机市场中：每个 Agent 有不同的预算和偏好，需要决定买什么、以什么价格买、是否与其他人合买。

实验发现：Agent 之间自然形成了定价策略、合作联盟和竞争行为——尽管没有任何 Agent 被显式编程为"要竞争"或"要合作"。

### 22.6.5 Agent 经济

将多 Agent 协作与真实的经济活动结合，我们看到了三种新兴的 Agent 经济模式：

**Pinchwork**：Agent 作为自由职业者，在平台上竞标任务。与人类的自由职业平台类似，Agent 需要创建 profile、投标、完成任务、获取评价。不同之处在于：Agent 可以在几秒内完成投标和交付，实现"按需 AI 劳动力市场"。

**RentAHuman**：一个有讽刺意味的反转——Agent 雇佣人类来完成 AI 不擅长的事务（如验证模糊的图片、处理需要物理存在的任务）。这预示了未来的"人机反向雇佣"场景。

**信息不对称博弈**：当 Agent 拥有不同的信息权限时，博弈就变得有趣了。最经典的案例是**狼人杀（Werewolf）游戏**：每个 Agent 只知道自己的角色和有限的公开信息，需要在撒谎、推理和说服中找出狼人。

在 AI 狼人杀中，法官（由代码控制）管理游戏阶段和信息分发：狼人知道自己同伴的身份（信息优势），预言家可以查验一个人（部分信息优势），村民只能从公开发言中推理（完全信息劣势）。Agent 需要在这些信息约束下做出策略决策——何时撒谎、何时揭露、如何说服。

这种博弈不仅是一个有趣的游戏，更是一个绝佳的**多 Agent 协议测试平台**：它测试了在信息不对等条件下，Agent 的推理、欺骗、说服和联盟形成能力。

![](/images/courses/ai-agent/fig10-13.svg)

*图 22.13 AI 狼人杀的架构。法官控制游戏阶段和信息分发，不同角色拥有不同的信息权限，Agent 在信息不对称下进行推理、谈判和说服。*

### 22.6.6 从协作到社会：进化的方向

回顾本章的路径：我们从两个核心设计维度出发，讨论了共享上下文与不共享上下文的各种协作模式，分析了 Proposer-Reviewer、Manager 和去中心化三种主流拓扑的适用场景与失败模式。最后，我们看到了 Agent 从"协作"走向"社会"的惊人涌现。

这几个阶段并不是线性替代关系，而是互补的层次：

1. **共享上下文的阶段转换**：适用于流程明确、需要完整轨迹的串行任务
2. **文件系统隔离的并行协作**：适用于可拆解为独立模块的复杂工程
3. **去中心化的灵活协作**：适用于角色边界清晰、流程可变的开放式任务
4. **Agent 社会与经济**：适用于大规模、长期、需要涌现创新行为的场景

作为实践者，你的任务是：**理解每个层次的设计假设和适用条件，为你的具体问题选择最合适的层（或层的组合）**。多 Agent 并非总是优于单 Agent——但当你真正需要它时，理解这些设计模式将让你避免重复制造轮子。

## 本章总结

- 多 Agent 协作的两个核心设计维度是**上下文共享**（共享 vs 独立）和**协作拓扑**（对等、管理者、去中心化）
- 多 Agent 系统真正的价值在于引入**新信息**（执行反馈、外部验证），而非简单的"多个 LLM 讨论"
- 共享上下文的**多阶段角色转换**适用于需要完整轨迹的串行任务，但上下文膨胀是主要限制
- 不共享上下文的**虚拟文件系统**提供了天然的协作枢纽，四个区域各有明确的权限和生命周期
- **Proposer-Reviewer 对等模式**通过独立的外部验证提供真正的迭代改进，解决了自我评审无效的问题
- **管理者模式**通过 Fan-out/Gather 协调多个专业 Agent，但 Manager 可能成为瓶颈
- **去中心化模式**通过 Handoff 协议和 Group Chat 实现了灵活的无中心协作
- **A2A 协议**为跨组织 Agent 协作提供了标准化通信基础
- 并发冲突和错误级联放大是多 Agent 系统的两个主要失败模式，需通过乐观锁、隔离边界和断路器来防范
- **Agent 社会**（Stanford AI Town、Agentopia、狼人杀）展示了从局部交互中涌现出复杂集体行为的可能
