### 7.1.2 构建步骤详解

**第一步：编写 OIL 配置文件**

`conf.oil` 是整个工程的配置入口，定义了 OS 实例、CPU 配置、Task、ISR、Counter、Alarm、Event 等所有 OS 对象：

```oil
CPU test_application {
  OS EE {
    CPU_DATA = TRICORE { ID = 0x0; CPU_CLOCK = 200.0; COMPILER = GCC; };
    CPU_DATA = TRICORE { ID = 0x1; MULTI_STACK = TRUE; };
    MCU_DATA = TC39X { DERIVATIVE = "tc397xe"; };  /* 兼容 TC38X */
    KERNEL_TYPE = OSEK { CLASS = ECC1; };
    STATUS = EXTENDED;
    ERRORHOOK = TRUE;
  };

  APPDATA my_app {
    APP_SRC = "master.c";
    APP_SRC = "slave1.c";
    APP_SRC = "slave2.c";
  };

  TASK TaskMaster   { CPU_ID = 0x0; PRIORITY = 1; };
  TASK TaskSlave1   { CPU_ID = 0x1; PRIORITY = 1; AUTOSTART = TRUE;
                      STACK = PRIVATE { SIZE = 256; }; SCHEDULE = FULL;
                      EVENT = RemoteEvent; };
  /* ... */
};
```

**第二步：RT-Druid 代码生成**

调用 `generate_code.sh`（或 Eclipse RT-Druid 插件）处理 `conf.oil`：

```bash
${RTDRUID_ECLIPSE_HOME}/evidence/generate_code.sh \
  ${RTDRUID_ECLIPSE_HOME} conf.oil .
```

RT-Druid 解析 OIL 文件，生成以下产物：

| 生成文件 | 内容 | 目标目录 |
|---|---|---|
| `ee_oscfg.h` | Task/Resource/Event/Counter/Alarm 宏定义、类型声明 | `erika/inc/` |
| `ee_oscfg.c` | TDB/TCB/CDB/CCB/KDB/KCB 静态初始化、ISR 向量表、TDB 指针数组 | `erika/src/` |
| `ee_oscfg.mk` | 编译选项宏（`OSEE_HAS_*`）、源文件列表 | `erika/mk/` |
| `*_libcfg.mk` | 架构/板级库配置 | `erika/mk/` |
| `*_linkcfg.mk` | 链接脚本路径、内存段配置 | `erika/mk/` |
| `ee_arch_compiler_*.mk` | 编译器工具链变量（GCC/Tasking） | `erika/mk/` |

`mk/ee_pull.mk` 中的规则将 `pull/` 目录中的中间文件拷贝到最终的 `erika/` 树中：

```makefile
# ee_pull.mk 中的核心拷贝规则
pull/ee_oscfg_h.txt --> erika/inc/ee_oscfg.h
pull/ee_oscfg_c.txt --> erika/src/ee_oscfg.c
pull/ee_oscfg_mk.txt --> erika/mk/ee_oscfg.mk
```

同时，`ee_pull.mk` 将 `pkg/arch/tricore/` 和 `contrib/` 中的源文件复制到 `erika/` 目录，形成完整的编译树。

**第三步：编译 OS 内核库**

```bash
make os    # 在 erika/ 目录下执行
```

`mk/ee.mk` 是编译系统入口：
1. 包含 `ee_oscfg.mk`（RT-Druid 生成的编译配置）
2. 包含 `ee_arch_compiler_gcc.mk`（GCC 工具链变量）
3. 编译 `EE_SRCS`（内核源码）+ `OS_EE_CFG_SRCS`（生成的 ee_oscfg.c）→ 生成 `libee.a`

关键编译选项（GCC/HighTec）：

```makefile
EE_CC = tricore-gcc
OPT_CC += -c -Wall -Wextra -Wstrict-prototypes -mcpu=tc397xe
# Debug: -g -O1 | Release: -g -Os
OPT_LINK += -T $(OSEE_LINKER_SCRIPT) -nostartfiles -Wl,--gc-sections
```

**第四步：编译应用代码**

```bash
make appl    # 在 out/ 目录下执行
```

编译 `master.c`、`slave1.c`、`slave2.c` 等应用源文件，链接 `libee.a` 和启动代码，生成最终的 `erika3app.elf` / `.hex`。

**第五步：烧录与调试**

```bash
# 生成 HEX 文件
tricore-objcopy -O ihex erika3app.elf erika3app.hex

# 通过 Lauterbach TRACE32 或 Infineon MemTool 烧录
# 或通过 AURIX Development Studio (ADS) 的调试配置
```

### 7.1.3 GCC vs. TASKING 编译器

| 特性 | GCC (HighTec) | TASKING (CTC) |
|---|---|---|
| OIL 配置 | `COMPILER = GCC` | `COMPILER = TASKING` |
| 编译器前缀 | `tricore-gcc` | `ctc` |
| 链接脚本 | GNU LD 格式 | TASKING LSL 格式 |
| 内存映射 | `ee_os_mem_map_gnu_hightec.h` | `ee_os_mem_map_tasking_ctc.h` |
| Section 宏 | `__attribute__((section(...)))` | `#pragma section` |
| 示例前缀 | `tricore_2G_mc` | `tricore_2G_t_mc` |
| 启动代码 | `ee_tc_cstart.c`（GNU 汇编） | `ee_tc_cstart.c`（TASKING 汇编） |
| BMHD 支持 | `__symver` + 链接脚本符号 | TASKING LSL 段定义 |

TASKING 编译器在汽车行业更常见（通过 Infineon AURIX Development Studio 分发），但 GCC/HighTec 是开源生态的首选。ERIKA v3 的 `conf.oil` 中只需修改 `COMPILER = GCC` 为 `COMPILER = TASKING` 即可切换——RT-Druid 会生成对应的编译配置。

### 7.2.3 多核示例代码导读

**`master.c` — Core0 主函数**：

```c
#include "shared.h"

OsEE_reg myErrorCounter;

void ErrorHook(StatusType Error) {
  (void)Error;
  ++myErrorCounter;
}

TASK(TaskMaster) {
  SetEvent(TaskSlave1, RemoteEvent);  /* 跨核 SetEvent：Core0 → Core1 */
  TerminateTask();
}

TASK(TaskCpu0Remote) {
  TerminateTask();            /* 被 Core2 上的 Alarm 远程激活 */
}

int main(void) {
  StatusType      status;
  AppModeType     mode;
  CoreIdType const core_id = GetCoreID();

  if (core_id == OS_CORE_ID_MASTER) {
    StartCore(OS_CORE_ID_1, &status);  /* 唤醒 Core1 */
    StartCore(OS_CORE_ID_2, &status);  /* 唤醒 Core2 */
    mode = OSDEFAULTAPPMODE;
  } else {
    mode = DONOTCARE;                   /* Slave Core 不指定 AppMode */
  }

  StartOS(mode);       /* 所有 Core 进入 OS */
  return 0;           /* 不应到达此处 */
}
```

**`slave1.c` — Core1 任务**：

```c
#include "shared.h"

TASK(TaskSlave1) {
  while (1) {
    WaitEvent(RemoteEvent);         /* 等待 Core0 的 SetEvent */
    ActivateTask(TaskSlave2);        /* 激活 Core2 上的 TaskSlave2 */
    ClearEvent(RemoteEvent);
  }
  TerminateTask();
}
```

**`slave2.c` — Core2 任务**：

```c
#include "shared.h"

TASK(TaskSlave2) {
  SetRelAlarm(AlarmSlave2RemoteCPU0, 50, 0);  /* 设置 Alarm 50 ticks 后激活 Core0 上的 Task */
  TerminateTask();
}
```

这个示例完整演示了三核协作：
1. **Core0**：`TaskMaster` 通过 `SetEvent` 唤醒 Core1 上的 `TaskSlave1`
2. **Core1**：`TaskSlave1` 等待事件，收到后激活 Core2 上的 `TaskSlave2`
3. **Core2**：`TaskSlave2` 设置一个 Alarm，50 ticks 后激活 Core0 上的 `TaskCpu0Remote`

跨核 `ActivateTask` 和 `SetEvent` 通过核间中断（ICI）实现，读者可以对照 `ee_tc_hal_mc.c` 中 `osEE_hal_signal_core()` 的实现理解整个路径。

## 7.3 TC38x 移植的"黑客"之处

项目 README 明确标注 "hacks to run on TC38x"，关键适配点：

| 适配点 | 说明 |
|---|---|
| `MCU_DATA = TC39X` | 使用 TC39X 配置代理 TC38X，两者同为 AURIX 2G 平台 |
| `DERIVATIVE = "tc397xe"` | 调试器识别用，TC387 的 iLLD 驱动在此配置下兼容 |
| `OSEE_TC_2G` 宏 | 区分 AURIX 2G（TC38x/TC39x）与 1G（TC27x 等），影响启动代码和内存布局 |
| `OSEE_TC_LINK_BMHD` | 2G 设备的 Boot Mode Header 链接选项 |
| Core5 跳过 | `/* Numeric ID 5 is took by HSM core, how lame :(. */` |
| DSPR 大小调整 | GCC 链接脚本中 TC39X A-Step 的 `__DSPR0_SIZE=96k` 等修正 |

这些"黑客"适配的实质是：TC38x 与 TC39x 共享 AURIX 2G 平台的绝大多数寄存器布局、中断架构和内存映射，因此 TC39X 的 ERIKA 移植可以直接运行在 TC38x 上，仅需要少量的链接脚本和启动参数调整。

## 7.4 从 ERIKA v3 到商用 AUTOSAR OS：学习桥梁

### 7.4.1 概念映射

经过前六章的学习，读者已经掌握了 AUTOSAR OS 的核心概念。以下是 ERIKA v3 与商用 AUTOSAR OS 的概念映射表：

| ERIKA v3 概念 | 商用 AUTOSAR OS 对应 | 差异 |
|---|---|---|
| `OsEE_TDB` / `OsEE_TCB` | OsTaskType / Task OCB | 结构名不同，语义相同 |
| `OsEE_CDB` / `OsEE_CCB` | OsCoreDescription / Core Control | ERIKA 支持多核 CDB/CCB |
| `osEE_sn_alloc()` / `osEE_scheduler_rq_insert()` | 内部就绪队列管理 | ERIKA 用 SN 链表，商用 OS 可能用优先级位图 |
| `osEE_begin_primitive()` / `osEE_end_primitive()` | `SuspendOSInterrupts()` / `ResumeOSInterrupts()` | ERIKA 内部原语，对应用户 API |
| `OIL 配置` → `ee_oscfg.c/h` | Arxml → BSW 代码生成（Vector DaVinci / EB tresos） | 工具链不同，生成逻辑一致 |
| `ee_tc_intvec.c` 向量表 | AUTOSAR Os_IsrCfg / 中断配置 | ERIKA 用汇编宏生成，商用 OS 用代码生成器 |
| `ee_tc_cstart.c` 启动代码 | EcuM / BswM 初始化序列 | ERIKA 更底层，商用 OS 通过 MCAL 抽象 |
| `GetResource()` / `ReleaseResource()` | 完全一致 | 协议相同 |
| OS Application | **不实现** | Vector/EB 完整实现 SC3/SC4 |
| Memory Protection | **不实现** | Vector/EB 支持 MPU/DMPU 配置 |

### 7.4.2 ERIKA v3 的学习价值

**为什么 ERIKA v3 是学习 AUTOSAR OS 的最佳开源载体？**

1. **API 级兼容**：`ActivateTask`、`SetEvent`、`GetResource`、`StartCore`、`GetSpinlock` —— 这些 API 在 ERIKA v3 和商用 AUTOSAR OS 中的签名和行为完全一致。在 ERIKA 上学到的 OS 服务调用知识可以直接迁移。

2. **数据结构透明**：商用 AUTOSAR OS 的 TDB/TCB/CCB 是编译后的二进制黑盒，而 ERIKA v3 的 `ee_kernel_types.h` 是完全开源的。读者可以跟踪 `ActivateTask` 从 API 入口到就绪队列插入的每一个指针操作。

3. **多核 Real**：许多商业演示环境只有单核，而 ERIKA v3 的 TC38x 移植提供了真正的多核调试环境——`StartCore()`、核间中断、Spinlock、全局调度器都是真实运行的代码，不是模拟。

4. **中断全栈可见**：从 `bisr`/`svlcx` 汇编入口到 `osEE_tc_isr2_wrapper` 到 `osEE_activate_isr2`，中断处理的全栈路径完全可读。商用 OS 通常不提供这一层源码。

5. **TC38x 即是量产芯片**：这不是模拟器或 FPGA 上的教学 RTOS——它在英飞凌 AURIX 2G 多核微控制器上真实运行，与量产 ECUs 使用相同的硬件架构。

### 7.4.3 商用 AUTOSAR OS 的额外能力

了解 ERIKA v3 的不足，也就理解了商用 AUTOSAR OS 的增值点：

| 能力 | ERIKA v3 | Vector MICROSAR OS | EB tresos OS | ETAS RTA-OS |
|---|---|---|---|---|
| OS Application 隔离 | 不支持 | 支持（SC3/SC4） | 支持（SC3/SC4） | 支持（SC3/SC4） |
| Memory Protection | 不支持 | MPU/DMPU 配置 | MPU 配置 | MPU 配置 |
| Memory Mapping | 无 Os_MemMap.h | 完整 AUTOSAR MemMap | 完整 MemMap | 完整 MemMap |
