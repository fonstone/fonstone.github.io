### 了解 ARM 通用寄存器

AArch32（ARM 32 位模式）有 16 个通用寄存器，编号 r0–r15：

| 寄存器 | 别名 | 用途 |
| --- | --- | --- |
| r0–r3 | — | 函数参数 / 返回值 |
| r4–r11 | — | 被调用者保存的变量 |
| r12 | ip | 临时寄存器（intra-procedure call） |
| r13 | sp | 栈指针（Stack Pointer） |
| r14 | lr | 链接寄存器（Link Register，存返回地址） |
| r15 | pc | 程序计数器（Program Counter） |

此外还有 `cpsr`（Current Program Status Register），记录当前运行模式、中断使能状态和条件标志位。

**这些寄存器就是 CPU 在某一时刻"正在做什么"的完整描述。**

# 任务与上下文

## 什么是任务

想象浏览器里同时打开了多个标签页——每个标签页独立运行，有自己的加载进度、滚动位置和输入框内容。关掉一个标签、再切回来，它的状态还在。

RTOS 里的 **任务（Task）** 就是这样一个概念：

- 一段独立的代码（一个 `fn` 函数，通常是无限循环）
- 一块私有的栈空间（存放局部变量、函数调用链）
- 当前的执行位置和寄存器状态

多个任务"同时运行"的假象，来自 CPU 在它们之间快速切换——每次切换间隔只有几毫秒，人眼感知不到。

## 什么是上下文

**上下文（Context）** 就是某个任务被暂停时 CPU 的完整快照：

- r0–r12：13 个通用寄存器的当前值
- sp（r13）：栈顶指针，指向该任务私有栈里当前使用到的位置
- lr（r14）：返回地址，记录"下一步该回到哪里继续"
- pc（r15）：程序计数器，记录"现在执行到哪一条指令"
- cpsr：状态寄存器，记录运行模式和中断标志

就像暂停一款 RPG 游戏存档：角色坐标、血量、背包、地图位置……所有状态缺一不可，少一个字段下次读档就会出错。

**CPU 只有一套寄存器**，但可以有很多任务。切换任务前必须把当前任务的寄存器状态保存下来，否则另一个任务的运行会把它们覆盖，原来那个任务就再也恢复不了了。

## TCB 的作用

每个任务都需要一个**任务控制块（Task Control Block，TCB）**——相当于这个任务的"档案袋"。

TCB 最核心的字段是**栈指针的保存位置**。当任务被暂停时，它的 r0–r12、lr、cpsr 都会被 push 到该任务的私有栈上，然后把当时的 sp 值记录在 TCB 里。下次恢复时，从 TCB 取出 sp，就能找到这些保存的寄存器，pop 出来继续执行。

除此之外，TCB 通常还存：

- 任务入口函数的地址（首次启动时用）
- 任务私有栈的内存缓冲区（TCB 负责持有这块内存，防止被释放）
- 任务状态（运行中 / 就绪 / 阻塞，第 07 章使用）

> **注意：** 本章先不实现调度器，TCB 只需要包含"能做一次 context switch"所需的最少字段。

# Context Switch 的三步流程

一次完整的上下文切换包括三步：

## 第一步：保存当前任务（任务 A）的上下文

把 r0–r12、lr、cpsr 压栈（push 到任务 A 的私有栈），然后把此时的 sp 值写入任务 A 的 TCB。此后任务 A 的栈顶保存了它被暂停瞬间的完整寄存器状态。

## 第二步：选择下一个任务（任务 B）

调度器决定接下来运行哪个任务。第 07 章会实现完整的就绪队列；本章先做最简单的两任务轮换（A → B → A → ...）。

## 第三步：恢复任务 B 的上下文

从任务 B 的 TCB 取出它上次保存的 sp，切换 sp，然后 pop 寄存器，最后用 `movs pc, lr`（或 `subs pc, lr, #0`）跳回任务 B 上次暂停的位置，继续执行。

```text
任务 A 正在运行
      ↓  触发切换
[保存] push {r0-r12, lr}; TCB_A.sp = sp
      ↓
[选择] 调度器选出任务 B
      ↓
[恢复] sp = TCB_B.sp; pop {r0-r12, lr}; movs pc, lr
      ↓
任务 B 继续运行（从上次暂停的地方）
```

这三步完全由汇编完成，因为 Rust/C 编译器不允许你随意操控 sp 和 pc——这正是后续文章 《上下文保存与恢复实现》 的核心内容。

# 练习题

```quiz single
Q: 为什么切换任务前必须保存所有 CPU 寄存器？
- 因为 ARM 规定任务切换时必须清空寄存器
+ 因为 CPU 只有一套寄存器，另一个任务的运行会覆盖它们，不保存就无法恢复原任务的执行状态
- 因为寄存器的值会随时间自动丢失
- 因为调度器需要读取这些寄存器来选择下一个任务
E: CPU 的寄存器是物理电路，不区分"属于哪个任务"。任务 B 运行时会自由读写 r0–r12，这会覆盖任务 A 留下的值。如果事先把 A 的寄存器保存到内存（A 的私有栈）里，切回 A 时再读出来，A 就感知不到自己被暂停过。
```

```quiz single
Q: TCB 中最核心的字段是什么，它的作用是什么？
+ 任务被暂停时的栈指针（sp），用于在恢复时找到保存在栈上的寄存器快照
- 任务入口函数地址，用于反复重启任务
- 任务的优先级，用于调度决策
- 任务的名称，用于调试输出
E: 当任务被暂停时，它的寄存器被 push 到该任务的私有栈里，sp 随之移动。TCB 保存这个 sp 值。恢复时把 sp 赋回去，再 pop 寄存器，就能精确还原暂停那一刻的 CPU 状态。其他字段（优先级、入口地址）是辅助信息，不影响恢复机制本身。
```

```quiz single
Q: context switch 为什么必须用汇编实现，而不能用普通 Rust 函数？
- 因为 Rust 太慢，汇编更快
- 因为 Rust 不支持裸机编程
+ 因为 context switch 需要直接操控 sp 和 pc，而 Rust/C 编译器会自动管理这两个寄存器，不允许代码随意修改它们
- 因为 Rust 的 unsafe 块无法执行这类操作
E: 编译器假设 sp 始终指向当前函数的栈帧，pc 的修改只能通过正常的函数调用/返回。context switch 要把 sp 切换到另一个任务的栈、然后跳转到任意地址继续执行，这完全超出了编译器的假设。唯一的办法是用内联汇编（core::arch::asm!）直接控制这两个寄存器。
```

```quiz single
Q: 一次 context switch 的正确顺序是什么？
- 选择下一个任务 → 保存当前任务上下文 → 恢复新任务上下文
+ 保存当前任务上下文 → 选择下一个任务 → 恢复新任务上下文
- 恢复新任务上下文 → 保存当前任务上下文 → 选择下一个任务
- 保存当前任务上下文 → 恢复新任务上下文 → 选择下一个任务
E: 必须先保存（否则调度器的执行本身会覆盖寄存器），再选择（调度器决策），最后恢复（把 CPU 控制权移交给新任务）。"先恢复再保存"是最危险的错误——新任务一运行，旧任务的寄存器就全丢了。
```
